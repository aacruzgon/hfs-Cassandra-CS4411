# ADR-aacruzgon-0031: `HFS_CASSANDRA_*` configuration names and defaults

- **Date:** 2026-11-06
- **Status:** accepted
- **Context:** Roadmap Step 2 (item 2.1) needs a `CassandraConfig` with contact points, keyspace, local data centre, credentials, pool size and timeouts, and the server must read it from the environment (`start_cassandra` in `crates/hfs/src/main.rs` calls it through `build_cassandra_config`, ADR-aacruzgon-0040). The design names none of these variables. The existing backends differ: MongoDB reads `HFS_MONGODB_URL` (falling back to `HFS_DATABASE_URL` when its scheme is `mongodb://`), `HFS_MONGODB_DATABASE`, `HFS_MONGODB_MAX_CONNECTIONS`, `HFS_MONGODB_CONNECT_TIMEOUT_MS` and `HFS_MONGODB_SERVER_SELECTION_TIMEOUT_MS`, with the reading done in `main.rs` through an injectable `env` closure (`crates/hfs/src/main.rs:870-938` at PR #37's head, `:890-958` from PR #45 on); PostgreSQL takes `HFS_DATABASE_URL` and `HFS_PG_*`. The names are user-facing and hard to change once documented, so this is a decision.
- **Decision:** one prefix, `HFS_CASSANDRA_`, read by `CassandraConfig::from_env()` / `from_env_with(env)` in `crates/persistence/src/backends/cassandra/config.rs`, so the names and their parsing live with the backend and `main.rs` only adds the server's `fhir_version` and `data_dir`:

  | Variable | Default | Why this default |
  | --- | --- | --- |
  | `HFS_CASSANDRA_CONTACT_POINTS` | `127.0.0.1:9042` | Comma-separated `host:port`, the form the driver resolves (`NodeAddress::Hostname`, `lookup_host`). Cassandra's standard port; the local node is `127.0.0.1:59042` (ADR-aacruzgon-0007) and is set explicitly, as `HFS_DATABASE_URL` is for the PostgreSQL baseline. |
  | `HFS_CASSANDRA_KEYSPACE` | `helios` | `keyspace-single-node.cql`. Validated as 1-48 `[A-Za-z0-9_]`, Cassandra's rule for a keyspace name. The driver sends it in a `USE`, which takes no bind marker; the driver quotes the name itself (`cluster/connection_manager.rs:137` at 8.1.9 and 10.0.0), so the name is case-sensitive. |
  | `HFS_CASSANDRA_LOCAL_DC` | `helios-dc1` | ADR-aacruzgon-0003. |
  | `HFS_CASSANDRA_USERNAME`, `HFS_CASSANDRA_PASSWORD` | unset | `PasswordAuthenticator`; both or neither. The project's nodes run `AllowAllAuthenticator` (checked: `system_views.settings` on the shared node, 2026-11-06). The password is redacted from `Debug` and not serialised, and a contact point carrying `user:pass@` is refused without echoing it, so contact points, keyspace and DC are safe to log. |
  | `HFS_CASSANDRA_POOL_SIZE` | `2` | Connections per local node. A v5 connection multiplexes up to 32,768 streams (`cdrs-tokio` 10.0.0 uses 32,767 stream ids, `transport.rs:50`), so one is enough for throughput; two means one broken connection does not stall every request while the driver reconnects. |
  | `HFS_CASSANDRA_CONNECT_TIMEOUT_MS` | `5000` | Bounds DNS resolution, each pooled and control connection, and session construction. At `cdrs-tokio` 10.0.0 a build whose contact points all refuse fails at once with `SessionInitFailed`, but one whose node accepts the connection and then fails the metadata refresh retries without end (`cluster/control_connection.rs:166-176`). |
  | `HFS_CASSANDRA_REQUEST_TIMEOUT_MS` | `10000` | The backend's own per-statement deadline (`cdrs-tokio` has none, at 8.1.9 or at 10.0.0). Above the node's `read_request_timeout` 5 s, `write_request_timeout` 2 s and `cas_contention_timeout` 1 s (shared node, 2026-11-06), so the node reports a typed `ReadTimeout`/`WriteTimeout` with `write_type` before the client gives up; equal to the node's `request_timeout`. |

  An invalid value fails startup (`CassandraConfigError`) instead of falling back silently.
- **Alternatives considered:**
    - **Accept `HFS_DATABASE_URL`, as MongoDB does.** Cassandra has no standard URL scheme, so the backend would invent one (`cassandra://host:port/keyspace`) that no other tool reads, and a PostgreSQL URL left in the environment would have to be ignored by scheme sniffing. Lost: one more source of truth for no gain.
    - **Read the environment in `main.rs`, as MongoDB does:** lost. `main.rs` has one owner (roadmap section 1, "One owner per shared file"), and the names, defaults and validation could not be tested without the server crate. `from_env_with(env)` keeps the injectable closure MongoDB's tests use.
    - **`HFS_CASSANDRA_HOSTS` and a separate `HFS_CASSANDRA_PORT`.** Cannot express nodes on different ports (a test cluster on one host does), and the driver takes `host:port` anyway.
    - **Pool size 1 (the driver default)** or the CPU count. 1 makes one dead connection a full stall; the CPU count opens 11 connections per node on a laptop for no measured benefit. Revisit with the Step 8 benchmarks.
    - **No client deadline:** lost. The design needs one: its unknown-outcome rule names "the backend's own request deadline elapsing around the CAS" (`cassandra-discussion.md`, "When the LWT outcome is unknown"). The driver has none (8.1.9 and 10.0.0). At 10.0.0 a dead connection fails its requests only after the heartbeat, up to about 40 s, and a request with no free stream id waits without bound.
    - **`HFS_CASSANDRA_URL`, matching the test variable `HFS_TEST_CASSANDRA_URL`:** lost. The value is a list of contact points, not a URL.
- **Consequences:** The names go into the book and the persistence README at Step 8. Each new setting later (sweeper interval, candidate cap) uses the same prefix and the same `from_env_with`. The request deadline is a second clock beside the node's: if an operator raises the node's timeouts above 10 s, they must raise `HFS_CASSANDRA_REQUEST_TIMEOUT_MS` too, or a slow CAS becomes an unknown outcome on the client side first. The pool size and deadline are measured in Step 8. The connect deadline's reach widened with 10.0.0, see ADR-aacruzgon-0044 (a silent first contact point uses the whole deadline).
- **AI involvement:** Written up by a Claude Code worker (`s2-backend`, Opus 5.5) for roadmap Step 2, PR #37. It read MongoDB's and PostgreSQL's config code in `main.rs` and `backends/mongodb/backend.rs`, the cdrs-tokio 8.1.9 source (`cluster/config_tcp.rs`, `cluster/node_address.rs`, `cluster/connection_pool.rs`, `cluster/session.rs`), and the shared node's `system_views.settings`; after the upgrade to `cdrs-tokio` 10.0.0 (PR #45, ADR-aacruzgon-0044) it re-checked the two timeout reasons against 10.0.0's `cluster/control_connection.rs` and `statement/`. Verified by the unit tests in `config.rs` (defaults, every variable, bad values, password redaction) and by connecting to the shared node with these defaults plus `HFS_CASSANDRA_CONTACT_POINTS=127.0.0.1:59042`.
    - **What Alan changed:** Alan reviewed every Step 2 decision record on 2026-11-06, before it was committed. From his own review he found that several alternatives were stale, because `cdrs-tokio` 9.1.0 and 10.0.0 (released 2026-11-04) had already fixed driver behaviour the records relied on. He found that some alternatives were not real options or did not make sense: strawmen, restatements of the decision, and the workers' own debugging steps listed as alternatives. And he found that some records cited sources outside the repository. He had a review agent re-audit every alternative against the code, the design documents and `cdrs-tokio` 10.0.0, accepted its recommendations, and had each record rewritten from them. For this entry: of five alternatives, three were kept and two rewritten ("read the environment in `main.rs`" now cites the roadmap's one-owner rule instead of another worker's file; "no client deadline" now gives the 10.0.0 reason, since a heartbeat now fails a hung connection's requests). None was moved or dropped. One alternative was added (`HFS_CASSANDRA_URL`). In the Decision, the reason for `HFS_CASSANDRA_CONNECT_TIMEOUT_MS` was rewritten for 10.0.0, which fails a build at once when every contact point refuses but still retries without end after a failed refresh, and the request-timeout row now says neither driver version has one.
