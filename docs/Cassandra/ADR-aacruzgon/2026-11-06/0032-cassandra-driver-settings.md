# ADR-aacruzgon-0032: `cdrs-tokio` session settings: protocol v5, local-DC routing, no driver re-send of a CAS, and a client deadline

- **Date:** 2026-11-06
- **Status:** accepted
- **Context:** Roadmap Step 2 (item 2.1) builds the backend's `cdrs-tokio` session. It was written on 8.1.9 in PR #37 and moved to 10.0.0 in PR #45 (ADR-aacruzgon-0044); the driver line numbers below are 10.0.0's unless marked 8.1.9, and the session described is PR #45's (PR #37's also held the rebuild, the TCP probe and the remote-DC refusal that ADR-aacruzgon-0044 removes). The design fixes the consistency levels ("Consistency levels": `LOCAL_QUORUM`, Paxos at `LOCAL_SERIAL`), says every CAS is sent as non-idempotent (ADR-aacruzgon-0024) and names the local DC (ADR-aacruzgon-0003), but leaves the driver's own settings open: protocol version, load balancing, retry policy, speculative execution, pool and timeouts. Reading the driver showed that "non-idempotent" alone does not stop every re-send: `DefaultRetrySession` re-sends **any** statement once to the next node after `Unavailable`, idempotent or not (`retry/retry_policy.rs:124-138`; 8.1.9 `:105-119`). ADR-aacruzgon-0024 requires that "the backend's own resolution is the only retry" of a CAS (its line 65). These settings decide failure behaviour, so they are a decision.
- **Decision:** the session in `crates/persistence/src/backends/cassandra/session.rs` is built as follows, and every statement goes through one `execute` that applies its `StatementKind`:
    - **Protocol v5** (`Version::V5`). Cassandra 5.0 serves it as a stable version, and `cdrs-tokio` speaks v3 to v5. It adds checksummed framing and the `contentions` count on a CAS `WriteTimeout`, which v4 lacks.
    - **Routing:** `TopologyAwareLoadBalancingStrategy::new(None, false)` (replicas of the partition first; the prepared statement's partition-key indexes give the token) with the backend's own `LocalDcOnly` node-distance evaluator, which gives nodes in `local_dc` the distance `Local` and every other node **no distance**, so the driver ignores them: no pool, never in a query plan (`cluster/topology/node.rs:353-355`, `is_ignored`). The driver's `TopologyAwareNodeDistanceEvaluator` marks other-DC nodes `Remote` instead. At 10.0.0 the strategy leaves `Remote` nodes out of a plan for a dc-local consistency, but only on a `NetworkTopologyStrategy` keyspace (`load_balancing/topology_aware.rs:264-272`). A `SimpleStrategy` (or unrecognised) keyspace's plan ends with every unignored node, local or remote (`:292-330`). There, a plan whose local nodes are down would reach a coordinator in another DC that runs `LOCAL_QUORUM` and `LOCAL_SERIAL` in its own DC, breaking the single-DC linearizability the design relies on. `LocalDcOnly` makes the guarantee independent of the keyspace's replication class and of every statement's consistency, and opens no pool to another DC. (At 8.1.9 the strategy also kept remote replicas in `LOCAL_*` plans, `topology_aware.rs:190-235` at 8.1.9, which the audit of PR #37 found.) `connect` also checks that `system.local` / `system.peers_v2` list a node in `local_dc`, so a misspelt DC fails at startup with a message naming it.
    - **Consistency per statement**, never the driver default `ONE`: reads and plain writes `LOCAL_QUORUM`; a CAS `LOCAL_QUORUM` with `serial_consistency = LOCAL_SERIAL`; a read that must settle an in-flight proposal `LOCAL_SERIAL` (walkthrough section 1).
    - **A CAS is non-idempotent and carries `FallthroughRetryPolicy`**, which never retries. So no speculative execution (`cluster/session.rs:832-833` runs it only for idempotent statements), no re-send after `Io`/`General`/`Overloaded`/`Server`/`Truncate` (`retry_policy.rs:92-123`), and none of the re-sends the default session makes whatever the idempotence: after `Unavailable`, after `IsBootstrapping`, and on the same node after a `ReadTimeout` that retrieved no data (`:124-182`). The backend's own unknown-outcome resolution (a `LOCAL_SERIAL` read, ADR-aacruzgon-0034) is the only retry. The driver's transparent re-prepare after `Unprepared` stays: `Unprepared` means the node did not execute the statement.
    - **Every other statement** keeps `DefaultRetryPolicy` and is marked idempotent: version and index rows carry a fixed `USING TIMESTAMP`, and an intent row or its delete rewrites the same key.
    - **No speculative-execution policy**, on the session or on any statement.
    - **Prepared statements** for every statement, prepared on first use and cached per CQL text for the session's life.
    - **Pool:** `HFS_CASSANDRA_POOL_SIZE` connections per local node (default 2), each connection's connect bounded by `HFS_CASSANDRA_CONNECT_TIMEOUT_MS` (ADR-aacruzgon-0031).
    - **Client deadline:** each statement's prepare (first use only) and execute share one budget of `HFS_CASSANDRA_REQUEST_TIMEOUT_MS` (default 10 s; `cdrs-tokio` has no request timeout of its own, at 8.1.9 or 10.0.0). Its expiry is `DriverError::Deadline { after, sent }`, where `sent` says whether the statement itself had been handed to the driver (a CAS cut off while preparing was never sent, so its outcome is not unknown); it maps to `BackendError::Timeout` (504) and, around a CAS, is an unknown outcome to resolve (ADR-aacruzgon-0034).
    - **The session keyspace** is set with `with_keyspace` at build time, which the driver recommends over `USE` (`cluster/session.rs:1235-1242`, `with_keyspace` doc), so the statements stay unqualified like `schema.cql`.
- **Alternatives considered:**
    - **Rely on non-idempotence alone, as ADR-aacruzgon-0024 wrote:** lost. `DefaultRetryPolicy` re-sends any statement once, to the next node, after `Unavailable`, idempotent or not (`retry/retry_policy.rs:105-119` at 8.1.9, `:124-138` at 10.0.0). The coordinator raises `Unavailable` before it acts, so that re-send is probably harmless, but a per-statement `FallthroughRetryPolicy` removes the question at no cost.
    - **`FallthroughRetryPolicy` for the whole session:** lost. Reads would lose the default's one retry on the same node after a `ReadTimeout` in which enough replicas answered (at 10.0.0: when the data was not retrieved). Idempotent writes would lose the retry on the next node after `Io`, `General`, `Overloaded`, `Server` or `Truncate`. That retry matters only on the three-node cluster.
    - **Protocol v4 (the driver default):** lost. v5 is Cassandra 5.0's stable version. It adds checksummed framing and the `contentions` count on a CAS `WriteTimeout`, which v4 lacks. Nothing in v4 is needed.
    - **`RoundRobinLoadBalancingStrategy`.** Ignores DC and replica placement; with RF 3 it would send most requests to a non-replica coordinator, and in a two-DC deployment it would cross DCs while using `LOCAL_*` consistency.
    - **The driver's `TopologyAwareNodeDistanceEvaluator`:** at 8.1.9 it let remote-DC replicas into `LOCAL_*` plans (`topology_aware.rs:190-235` at 8.1.9), which is why `LocalDcOnly` was written. At 10.0.0 the strategy drops remote nodes for a dc-local consistency on a `NetworkTopologyStrategy` keyspace (`topology_aware.rs:264-272`), but a `SimpleStrategy` keyspace's plan still takes every unignored node, remote ones included (`:292-330`). `LocalDcOnly` stays: it costs nothing, opens no pool to another DC, and does not depend on every statement's consistency level or on the keyspace's replication class.
    - **Allow DC failover for `LOCAL_*` consistency.** `LOCAL_SERIAL` is linearizable only within one DC (design, data model), so failing over a CAS to another DC would silently weaken the compare-and-swap.
    - **Speculative execution for reads:** not now. The driver offers it for idempotent statements (`cluster/session.rs:832-833`), but it doubles the load on a single node, and the Step 8 benchmarks decide whether tail latency needs it.
- **Consequences:** A CAS that hits `Unavailable` returns 503 at once instead of trying a second coordinator; on the three-node cluster that is a little less available. Whether Step 3 retries a CAS after `Unavailable` (the native protocol defines it as the coordinator refusing before it acts) is Step 3's decision, made in the backend where it is visible, not in the driver. The client deadline is a second clock beside the node's timeouts (ADR-aacruzgon-0031). The settings are measured in Step 8 (pool size, deadline). A unit test (`session.rs`, `statement_params_carry_the_kind_rules`) pins the per-kind rules, so a later change to them fails a test. The design's paragraph on non-idempotent CAS statements ("When the LWT outcome is unknown") and its echoes in roadmap Step 3 and walkthrough 3.1 now name `FallthroughRetryPolicy`, in this entry's commit. The walkthrough edit changes error handling only, so it needs no new sign-off under ADR-aacruzgon-0028.
