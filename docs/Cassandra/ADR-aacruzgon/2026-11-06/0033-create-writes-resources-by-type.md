# ADR-aacruzgon-0033: Step 2's `create` writes the `resources_by_type` row, and `count` is real at Milestone A

- **Date:** 2026-11-06
- **Status:** accepted (decided by the Step 2 orchestrator on 2026-11-06 and approved by Alan the same day)
- **Context:** The roadmap gives Step 2 only `create` and `read`. `count` is in Step 3's task list, whose write path keeps its "index batches under 5 KiB (empty until step 5)", and the index writes, `resources_by_type` included, are Step 5's. But the conformance seeder that every boot runs calls `count(tenant, Some("SearchParameter"))` before it creates anything (`crates/persistence/src/search/seeder.rs:326`, and `:437` for CompartmentDefinition). With `count` stubbed it fails there and seeds nothing, so Step 2's item 2.6 (boot time of about 1,400 LWT creates per tenant) could not be measured until Step 5. `count` reads `resources_by_type` (walkthrough 5.9), so it needs that row to exist. The worker `s2-backend` raised this while building PR #37; the orchestrator decided it.
- **Decision:** in PR #38 (`cassandra/step2-create-read`):
    - `create` writes the `resources_by_type` row (X1) at step 5, `USING TIMESTAMP ts(1)`, with `version_id = 1` and the resource's `fhir_version` (`as_mime_param()`, ADR-aacruzgon-0026 G34), exactly as the walkthrough's create (3.2) and X1 statement say.
    - `K(1)` is therefore `{resources_by_type}`, and that is what the CAS writes into `resources.index_keys` and V1 into `resource_versions.index_keys`: the format-1 blob `0x01 0x01 0x01` (`schema.cql`). The token, date and URI rows of `SearchParameterExtractor::extract` stay Step 5's.
    - `count(tenant, Some(type))` is `SELECT COUNT(*) FROM resources_by_type WHERE tenant_id = ? AND resource_type = ?` at `LOCAL_QUORUM`, with no tag check (walkthrough 5.9, G7). `count(tenant, None)` sums it over every resource type name of every enabled FHIR version (`FhirResourceTypeProvider::get_resource_type_names`, each name once), 8 partitions at a time.
- **Why no work is thrown away:**
    - X1 is one row of the key set Step 5 writes anyway. Step 5 adds rows to `K(V)`; the statement, the timestamp, the `index_keys` blob and the place in the write path stay as they are.
    - The `index_keys` blob uses the final format (`index_keys.rs` encodes and decodes all seven row kinds; `the_worked_example_is_289_bytes_as_the_walkthrough_says` checks the walkthrough's worked example, eight rows of six kinds, and `uri_index` is round-tripped separately), so a resource created now is updated by Step 3 and indexed by Step 5 without migration: Step 3's update reads `K(1) = {resources_by_type}` from `resources.index_keys`, deletes that row and inserts `K(2)`, which is the design's rule.
    - `count` is the design's own statement, not a stand-in. Step 3 keeps it; Step 6's `search_count` without filters calls it.
    - A resource created before Step 5 has no token, date or URI rows. The design already accepts that a resource is found by a parameter only after its next write ("A new SearchParameter does not reindex"); everything written before Step 5 is development and test data, each test under its own tenant.
- **Alternatives considered:**
    - **Keep `count` stubbed until Step 3 and accept an unseeded Milestone A.** The server boots, but the CapabilityStatement and `/SearchParameter` read the stored set, and item 2.6, the measurement that decides whether `create_many` needs a concurrent implementation, slips to Step 5.
    - **Make the seeder skip `count` for Cassandra.** Changes shared code (`search/seeder.rs`) for one backend, and every boot would re-run 1,400 creates that all answer `AlreadyExists`.
- **Consequences:** Milestone A can seed at boot and item 2.6 can be measured in Step 2 (ADR-aacruzgon-0043). Every create costs one more write (X1) than the roadmap planned, whose Step 3 write path has index batches "empty until step 5". `count` uses `COUNT(*)`, one of the two forms walkthrough 5.9 allows; switch to driver paging (`SELECT id`, counted in Rust) if Step 8 shows it reaching `read_request_timeout`. `count` does not tag-check, so it misses a create still between its CAS and X1 (one too few until the sweep, walkthrough G7), and it shares the design's other stated cases (G7). `count(tenant, None)` is about 145 partition reads in an R4 build. Step 3 inherits a real `count` and a `create` whose `K(1)` is non-empty. The roadmap's Step 2 and Step 3 task lists say so, in this entry's commit. The same `resources_by_type` rows are what the stored-SearchParameter reload scans for tenants (ADR-aacruzgon-0041).
- **AI involvement:** Written up by a Claude Code worker (`s2-backend`, Opus 5.5) for roadmap Step 2, PR #38. The worker found the seeder's `count` call (`seeder.rs:326`, `:437`) while writing PR #37 and recommended this option; the Step 2 orchestrator decided it. Verified against the shared 5.0.9 node: `cassandra_count_scans_resources_by_type` (3 Patients + 1 Observation: 3, 1, 0 for Encounter, 4 for `None`), `cassandra_create_many_seeds_through_create` (20 creates through `create_many` count 20), `cassandra_create_writes_every_cell_and_no_null` (X1 present with `version_id` 1, `fhir_version` `4.0`, `writetime` = `ts(1)`; `index_keys` = `0x010101` on both rows), and `index_keys.rs`'s unit test of the worked example (289 bytes).
    - **What Alan changed:** Alan reviewed every Step 2 decision record on 2026-11-06, before it was committed. From his own review he found that several alternatives were stale, because `cdrs-tokio` 9.1.0 and 10.0.0 (released 2026-11-04) had already fixed driver behaviour the records relied on. He found that some alternatives were not real options or did not make sense: strawmen, restatements of the decision, and the workers' own debugging steps listed as alternatives. And he found that some records cited sources outside the repository. He had a review agent re-audit every alternative against the code, the design documents and `cdrs-tokio` 10.0.0, accepted its recommendations, and had each record rewritten from them. For this entry: of four alternatives, two were kept (keep `count` stubbed; make the seeder skip `count`). One was dropped as a strawman: counting `resources` with `ALLOW FILTERING`, a statement the roadmap and `schema.cql` forbid. One was moved to Consequences: driver-paged `SELECT id`, which is walkthrough 5.9's own either/or, not an alternative to writing X1 now. The Consequences now cite roadmap Step 2 instead of a brief outside the repository.
