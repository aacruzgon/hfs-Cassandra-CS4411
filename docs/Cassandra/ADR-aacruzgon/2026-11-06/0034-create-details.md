# ADR-aacruzgon-0034: The choices inside Step 2's `create`: post-CAS retries, every attempt's `write_id`, id and code checks

- **Date:** 2026-11-06
- **Status:** accepted
- **Context:** PR #38 implements `ResourceStorage::create` as the walkthrough's create sequence (3.2): permission check, intent row I1, `INSERT … IF NOT EXISTS` (C1) with `deleted_at = 0`, version row V1, index rows, intent delete I2. The design leaves open how often steps 4 and 5 are retried before the write returns success and leaves its intent for the sweeper ("retry with the same timestamps", G23), whether a client-supplied id is checked, and whether the SearchParameter `code` bound (G38), listed under step 1 of every write, lands now or in Step 3. Its unknown-outcome rule ("exactly like `WriteTimeout`") also leaves a false 409 possible after a dropped connection, which `create` had to close.
- **Decision:**
    - **Steps 4 and 5:** each statement is tried up to 3 times, 10 then 20 ms apart, with its fixed `USING TIMESTAMP`. If either still fails, the create returns success (201) and I2 is skipped, so the intent row stays for the sweeper (G23): after an applied CAS, a 5xx would make a client's retried POST create a second resource.
    - **Unknown CAS outcome on C1** (ADR-aacruzgon-0024, 0026), resolved by R2 (the full R1 SELECT) at `LOCAL_SERIAL`, then, past version 1, R3 on row 1's `write_id`, per the walkthrough's table: our `write_id` at version 1 is applied; no row is a re-run with the same id, a fresh `write_id`, `last_updated` and intent, after a 5 to 25 ms pause, at most twice; another `write_id` is `AlreadyExists` (409); a later version is decided by row 1 (ours: success with steps 4 and 5 skipped; another: 409; unset: undecidable). Undecidable, an R2 that fails, and exhausted re-runs are 504 after a timeout and 503 after a failure. Refinements, from the audit of PR #38:
        - **Which errors are unknown.** Only errors that prove the CAS was not executed are mapped directly: the deadline while preparing, `Error::Timeout` (raised only while connecting), `InvalidProtocol` (raised while opening a node's pool, `cluster/topology/node.rs:294-300`; mapped here from PR #45, commit `9c2e720cb`, ADR-aacruzgon-0044; in PR #38 it still goes to R2), "No nodes available", "No active connections", and the server codes `Unavailable`, `IsBootstrapping`, `Syntax`, `Invalid`, `Unauthorized`, `Config`, `Authentication`, `Protocol` and `Unprepared`. Everything else goes to R2, including `Server` and `Overloaded`, which can be raised after the proposal was accepted, `CasWriteUnknown`, and a CAS answer with no readable `[applied]`. (`CasWriteUnknown` goes to R2 in both: in PR #38 it arrives as `Error::UnexpectedErrorCode(0x1700)`, from PR #45 as `ErrorType::CasWriteUnknown`.) The driver citations are re-checked at `cdrs-tokio` 10.0.0 (`send_envelope.rs:33-75`, `connection_pool.rs:46-56`, `:709-724`, `transport.rs:444-450`).
        - **Every attempt's `write_id` is kept for the whole request.** After a dropped connection or the client deadline the coordinator may still be running attempt 1 (retrying under `cas_contention_timeout`, or still queued). It can apply after R2 reported "no row", so the re-run's C1 misses on attempt 1's row. The decision therefore matches the row's `write_id` against all of this request's attempts, both after R2 and on a re-run's definite miss (`IF NOT EXISTS` returns the whole row): a match is success with that attempt's `last_updated`, and steps 4 to 6 use that attempt's values and its intent. Without this, the request would return a false 409 for a resource it created. A `write_id` that is missing or cannot be decoded decides nothing (undecidable), never "another writer".
        - A `WriteTimeout` with `write_type = SIMPLE` is also confirmed by R2. That is a deviation from the design, recorded in its own entry, ADR-aacruzgon-0035.
    - **Client-supplied id:** checked as a FHIR id, 1 to 64 characters of `[A-Za-z0-9\-.]` (R4 datatypes.html#id), with 400 `InvalidResource` otherwise. The design's key-size bound assumes "the id at 64" (G35); PostgreSQL does not check, but its keys have no such bound. A resource without an id gets `new_resource_id()` (UUID v7), as every other backend.
    - **SearchParameter `code` over 128 bytes:** refused with 400 `InvalidResource` on `create` now (G38), before I1, so nothing is written. Step 3 adds the same check to `update`, `update_with_match` and `create_or_update`. A stored `active` SearchParameter that can change the tenant's overlay (`create_affects_overlay`) is added to the in-process overlay.
- **Alternatives considered:**
    - **No retries for steps 4 and 5, leaving everything to the sweeper.** It would also depart from the design, which says to retry ("retry with the same timestamps", step 6). Correct, but every transient failure would delay search visibility by a poll interval plus the grace period. **Unbounded retries:** a request could hang on a dead index partition.
    - **No id check.** A 1 MB client id would break the design's bound on every key and the 5 KiB batch sizing.
    - **Leave G38 to Step 3.** The seeder creates SearchParameters in Step 2, so the bound would not hold for anything stored before Step 3.
    - **Match the row's `write_id` against the current attempt only:** lost. A late first attempt can apply after R2 reported no row, and the request would answer a false 409 for a resource it created.
- **Consequences:** A request that loses its connection mid-CAS answers correctly even if its first attempt applies late. Both refinements change the design, which is edited in this entry's commit: `cassandra-discussion.md` ("When the LWT outcome is unknown") and walkthrough 3.1 now compare the row against every attempt of the request, and no longer list `Error::Timeout` among the unknown outcomes (it and a deadline before the CAS was sent are mapped directly). Like ADR-aacruzgon-0035's edits, these change the walkthrough's error handling, not a table, key, column type or table option, so they need no new sign-off under ADR-aacruzgon-0028. `create` is complete for its own CAS: definite misses, unknown outcomes and post-CAS failures follow the design, and Step 3 reuses the intent, CAS classification, version-row and index-row helpers in `write.rs` for update, delete and revive. Not yet exercised against a real failure (a killed node mid-CAS); the failure tests are Step 8's. The post-CAS retry count is revisited if the failure tests show it matters.
- **AI involvement:** Written up by a Claude Code worker (`s2-backend`, Opus 5.5) for roadmap Step 2, PR #38, from the design's write path and unknown-outcome sections, walkthrough 3.1 and 3.2, ADR-aacruzgon-0016, 0024, 0026 and 0027, and the cdrs-tokio 8.1.9 / cassandra-protocol 3.3.0 error types (re-checked at 10.0.0 / 5.0.0 in PR #45). Two routine choices of the same code are not part of this entry:
    - the intent row's `shard` is 32-bit FNV-1a over the tenant id, a zero byte and the id, `mod 16`. It is stable across builds, unlike Rust's `DefaultHasher`, whose algorithm is unspecified, and the sweeper polls all 16 shards, so it affects only diagnostics and spread;
    - `enqueued_at` is a version-1 UUID from the request's clock with a random clock sequence and node id (RFC 9562 6.10), through `uuid::Builder::from_gregorian_timestamp`.

  Verified by unit tests (CAS failure classification, including SIMPLE, `Server` and `Overloaded` as unknown, the 504/503 split, intent keys and timeuuids, the shard spread, millisecond `last_updated`, the id and code bounds, no null bind in C1, the 5 to 25 ms pause) and by integration tests on the shared 5.0.9 node (create/read, duplicate 409, 8 concurrent creates of one id give exactly one 201 and seven 409s, the code bound at 128 and 129 bytes, permission refusal before any write, every cell written, no intent row left), and by a manual check after a flush: `sstabledump` showed no tombstone in any test partition of `resources`, `resource_versions` or `resources_by_type`. The decision table is tested against the node (`write.rs`, `node_tests`: no row; version 1 ours, as the only attempt and as the second of two; another's; superseded with row 1 ours or another's; superseded with no row 1), each case under its own tenant. Not tested: an earlier attempt applying late (a row holding attempt 1's `write_id` while a later attempt is current), the definite-miss branch on a re-run, the re-run loop itself and a real mid-CAS failure; the code covers the first two (`attempt_with` searches every attempt), and the rest are Step 8's failure tests.
