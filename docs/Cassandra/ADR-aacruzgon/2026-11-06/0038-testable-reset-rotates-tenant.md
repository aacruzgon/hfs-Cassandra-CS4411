# ADR-aacruzgon-0038: The Cassandra `TestableBackend` resets by rotating to fresh tenants

- **Date:** 2026-11-06
- **Status:** accepted
- **Context:**
    - Roadmap item 2.5 implements `TestableBackend` (`crates/persistence/tests/common/harness.rs:43`) for Cassandra. The trait's `reset` "should clear all data while preserving the schema" (`harness.rs:50-53`), and `seed(&TestFixtures)` takes no tenant (`harness.rs:55-60`), so the backend has to own the tenant it seeds.
    - Every Cassandra test shares one node (ADR-aacruzgon-0020, rule 1): `docker/cassandra` locally, the job's container in CI. Truncating or dropping a table there would destroy the data of tests running in parallel and of other workers on the same node.
    - Deleting only this instance's rows is not available either. A CQL `DELETE` against `resources` must never exist (`development-roadmap.md:170`; `cassandra-discussion.md:117,256`: deletes are soft), `delete` is a Step 3 stub until then, and ADR-aacruzgon-0020 already rejected "cleaning up data between tests instead of isolating it" for the tombstones it makes and the locking parallel tests would need.
    - The fixtures carry fixed ids (`patient-1`, `obs-1`, …; `tests/common/fixtures.rs`), so two instances, or two runs on a reused node, must never seed the same tenant.
    - `TestContext` (`harness.rs:82-97`) holds copies of its tenants, and `TestContext::new` hard-codes `test-tenant-1` and `test-tenant-2` (`harness.rs:105-118`), names every test on the node would share.
    - No backend implements `TestableBackend` today (`git grep "impl TestableBackend"` finds only the doc example), so there is no house pattern to follow.
- **Decision:**
    - A wrapper, `CassandraTestBackend` (`tests/common/cassandra_testable.rs`), holds a `CassandraBackend` and two tenants from `unique_tenant` (`test-<label>-<uuid32>`, ADR-aacruzgon-0029): `tenant()`, which `seed` writes under, and `secondary_tenant()`, for isolation tests.
    - **`reset` replaces both tenants with fresh ones and issues no statement.** The old rows stay on the node under tenants nobody names again, exactly as ADR-aacruzgon-0020's rule 2 already leaves every Cassandra test's rows.
    - `seed` writes every fixture through the backend's real `create`, keeping its id; every fixture is a create, so none needs a stub. Seeding a tenant twice fails with `AlreadyExists`.
    - `backend_kind` is the backend's `kind()`; `supported_capabilities` is `CassandraBackend::declared_capabilities()`.
    - The wrapper forwards **every** `ResourceStorage` method, the defaulted ones included, so the backend's overrides are what runs (`delete_versioned`'s stub, `bulk_write_concurrency` 8, `readiness_check`, and Step 3's later ones), never the trait default over the wrapper. Forwarding only the required methods and today's overrides would let each later override (Step 3's concurrent `read_batch`, for one) silently fall to the default on the wrapper until someone remembered to add it. Other traits are reached through `inner()`.
    - `into_context(fixtures)` builds a `TestContext` from the instance's tenants, and a free `reset_and_seed(&mut ctx)` resets, re-points `ctx.tenant` and `ctx.secondary_tenant`, and seeds. The harness's own `TestContext::reset_and_seed` would seed the new tenant while `ctx.tenant` still named the old one.
- **Alternatives considered:**
    - **Truncate or drop the tables:** lost. It would wipe a shared node under parallel tests and other users (ADR-aacruzgon-0020 rule 1; roadmap row 2.5, "against the Compose single node").
    - **Delete this instance's own rows:** lost. A CQL `DELETE` against `resources` is a statement that must never exist, the soft delete is a Step 3 stub, a soft delete would make the fixtures 410 rather than absent, and the tombstones and locking are why ADR-aacruzgon-0020 chose isolation over cleanup.
    - **Namespace every tenant the caller passes** (map `test-tenant-1` to `<instance>-test-tenant-1` inside the wrapper), which would make `TestContext::new` and its fixed names safe: lost. The suites assert the stored tenant literally (`tests/crud/create_tests.rs:119,366`, `tests/multitenancy/isolation_tests.rs:153`) and `is_system()` (`tests/crud/read_tests.rs:200`), so the wrapper would have to rewrite every returned `StoredResource`, which has no tenant setter, and the system tenant cannot be namespaced while staying `__system__`.
    - **Implement the trait on `CassandraBackend` directly:** lost. It would compile (the trait is local), but the production struct has nowhere to keep a test tenant, and adding one for tests is wrong.
- **Consequences:**
    - `reset` is free (no round trip) and safe on any shared node; instances and re-runs never meet, whatever their fixture ids.
    - Each `reset` leaves a tenant's worth of rows on the node, as every Cassandra test already does. On the Compose node they accumulate until the `helios` keyspace is dropped and applied again (ADR-aacruzgon-0020); the CI node is thrown away after each job. Those tenants also lengthen the stored-SearchParameter load, which reads every tenant that ever stored a SearchParameter (ADR-aacruzgon-0041, 0048).
    - Tests must read the tenants from the backend (`tenant()`, or a context from `into_context` reset with `reset_and_seed`), not from `TestContext::new`. The module docs say so; a Step 3 suite that builds `TestContext::new` would write under the fixed `test-tenant-1` shared by every run.
    - `TenantContext::system()` is one `__system__` partition for every test on the node; a test that writes there must use its own ids (`unique_id`). Step 3's multitenancy suites need to know this.
    - `pending_index_writes` stays the one cross-tenant table (ADR-aacruzgon-0020): a rotated tenant's intents are still visible to a sweeper test, which already asserts only on its own tenant.
    - Step 3 decides how `crud_suite.rs` (today `#![cfg(feature = "sqlite")]`, building its own `SqliteBackend`) reaches this wrapper; nothing here constrains that.
- **AI involvement:**
    - **Tool and model:** Claude Code (Opus 5.5), worker `s2-testable` started by the Step 2 orchestrating session.
    - **What the AI proposed:** the wrapper with tenant rotation, full forwarding, `into_context` and the context-aware `reset_and_seed`; it considered and rejected namespacing after finding the literal tenant assertions in the suites.
    - **What Alan changed:** Alan reviewed every Step 2 decision record on 2026-11-06, before it was committed. From his own review he found that several alternatives were stale, because `cdrs-tokio` 9.1.0 and 10.0.0 (released 2026-11-04) had already fixed driver behaviour the records relied on. He found that some alternatives were not real options or did not make sense: strawmen, restatements of the decision, and the workers' own debugging steps listed as alternatives. And he found that some records cited sources outside the repository. He had a review agent re-audit every alternative against the code, the design documents and `cdrs-tokio` 10.0.0, accepted its recommendations, and had each record rewritten from them. For this entry: of five alternatives, three were kept, one was rewritten and one was moved. "Implement the trait on `CassandraBackend` directly" was rewritten, because it said "not possible" and then that the orphan rule allows it. "Forward only the required methods and today's overrides" was moved into the Decision as the reason for forwarding every method, because it describes how the wrapper is written, not a design that competed with it. "Truncate or drop the tables" cited the orchestrator's brief, which is outside the repository, and now cites roadmap row 2.5. The Links commit is now the restacked head.
