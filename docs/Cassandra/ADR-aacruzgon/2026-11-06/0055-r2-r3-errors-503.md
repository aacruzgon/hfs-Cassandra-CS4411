# ADR-aacruzgon-0055: After an unknown CAS outcome, an R2 or R3 error is 504 for a timeout and 503 for anything else

- **Date:** 2026-11-06
- **Status:** accepted (Alan chose 503 on 2026-11-06, as recommended, and approved this entry on 2026-11-07). It amends ADR-aacruzgon-0050's sub-decision "An R2 error is R2's own timeout or failure"; this entry's "What does not change" is amended by ADR-aacruzgon-0067, and its message rule (only the errors turned from 500 into 503 say the write may have been stored) by ADR-aacruzgon-0077
- **Context:**
    - **When R2 and R3 run.** Only after a compare-and-swap whose outcome is unknown, so the write may have applied. R2 is the `LOCAL_SERIAL` read of the `resources` row (`write.rs`, `serial_read`). R3 is the `LOCAL_QUORUM` read of row `V`'s `write_id`, made when R2 shows a version past the target (`decide`). Both are called from the unknown-outcome branch of `run_cas` and from the late-attempt check (ADR-aacruzgon-0051), and from nowhere else.
    - **Two approved texts disagree.**
        - **The Step 3 plan's D3, sub-decision 4,** which Alan accepted on 2026-11-06, says: "treat any error from R2 as 'R2 timed out' (504) or 'R2 failed' (503)". Never a 500.
        - **ADR-aacruzgon-0050** says an R2 error "is mapped by the table for plain statements (`errors.rs`)". The walkthrough's R2 row (3.1), the design ("The serial read times out, or fails") and the roadmap's Step 3 CAS bullets say the same.
    - **Where they differ.** The plain table (`errors.rs`, `classify`) answers 500 for several errors. `REST` maps `BackendError::Internal` and `QueryError` to 500 (`crates/rest/src/error.rs:1238-1243`). The 500 cases are:
        - `Internal`: a `Server` error, `Protocol`, `Truncate`, `Unknown`, an `Unprepared` the driver could not fix in its 5 re-sends, a decoding error, and a driver `General` message that is not a lost connection, such as "Unmatched stream id", which `cdrs-tokio` 10.0.0 sends to every pending request (`transport.rs`, read in the source during L1's reading, `reading/cdrs.md`);
        - `QueryError`: `Syntax`, `Invalid`, `Unauthorized`, `Config`, `AlreadyExists`, `FunctionFailure`. None of these is expected from a prepared SELECT, but the table maps them all.

      The L1 code (`f46234059`) followed ADR-0050's text, as approved.
    - **Why a 500 is wrong there.** A 500 tells the client and the operator that the server has a bug and the request failed. After an unknown outcome neither is known: the CAS may have applied, I1 is kept, and the sweeper finishes the write if it did (G23, ADR-aacruzgon-0034). The honest answer is the one the walkthrough already gives for an undecidable outcome: 504 after a timeout, 503 otherwise, so the client knows to retry later and to check before retrying a create.
    - **Why it is a decision.** It changes how an error on the write path is mapped, and it amends an accepted entry (ADR-aacruzgon.md, "What counts as a decision worth an entry").
- **Decision:**
    - **The rule.** An error of R2 or R3 keeps the plain table's answer when that is 504 (`BackendError::Timeout`: `ReadTimeout`, `WriteTimeout`, `WriteTimeout`/CAS from Paxos v2's read, `Paxos.java:893-901`, and the backend's own deadline) or 503 (`Unavailable` or `ConnectionFailed`). Everything the plain table would make 500 is `BackendError::Unavailable`, 503.
    - **The code.** One function, `map_lookup_error` in `write.rs`, used by `serial_read` and `decide` instead of `map_driver_error`. It is still never `classify_cas_failure`, so an R2 or R3 error is never taken for a new unknown write (ADR-aacruzgon-0050 unchanged on that point). The 503's message names no host ("the write's outcome could not be read back (serial read failed); it may have been stored"), because REST sends it to the client verbatim (`error.rs`, `Unavailable` doc, #2303). `map_driver_error` still logs the driver's detail at `error` level.
    - **What does not change.** The plain table, for every other statement: the same `Server` error on I1, V1 or the X1 delta is still 500. ADR-aacruzgon-0050's other sub-decisions. The undecidable rows of walkthrough 3.1 (504 or 503 by the CAS's own trigger).
- **Alternatives considered:**
    - **Keep ADR-0050's text (500 for those errors):** lost. It reports a write that may be stored as a server bug, and it contradicts D3 sub-decision 4, which Alan accepted.
    - **504 for every R2 or R3 error:** lost. 504 means a timeout everywhere else in the backend (G26, `error.rs`). A `Server` error or a lost stream is not one, and the walkthrough already separates timeouts (504) from failures (503) for the undecidable case.
    - **Treat an R2 or R3 error as a new unknown outcome and re-run the attempt:** lost. ADR-aacruzgon-0050 rejected it: a re-run spends the request's 2 re-runs on a read that failed, under the overload that probably caused it.
    - **Retry R2 or R3 once before answering:** not taken now. It adds a round trip under the same overload, and nothing in L1's tests or the single node shows it is needed. Step 8 (item 8.3, failure tests on three nodes) can revisit it with numbers.
- **Consequences:**
    - **What it guarantees.** A request whose outcome R2 or R3 could not read answers 504 or 503, never 500, and keeps I1, so the sweeper settles the write.
    - **What becomes harder.** An operator no longer tells a server bug on R2 or R3 from an outage by the HTTP status. The log line at `error` level, and `cas_stats()`'s `serial_read_failures` (for R2), still do.
    - **Tests.**
        - The pure test `an_r2_or_r3_error_is_504_for_a_timeout_and_503_otherwise` (`write.rs`) checks both reads with three timeouts (`WriteTimeout`/CAS, `ReadTimeout`, the deadline) and six other errors (`Server`, `Invalid`, `Overloaded`, "Unmatched stream id", a lost connection, a decoding error). It also checks that the plain table still answers 500 for a `Server` error on another statement.
        - The live fault-seam test for a `WriteTimeout`/CAS on R2 still answers 504.
    - **To revisit.** Step 8's three-node failure tests: if R2 or R3 errors show up there other than as timeouts, record which, and whether one retry would have answered them.
