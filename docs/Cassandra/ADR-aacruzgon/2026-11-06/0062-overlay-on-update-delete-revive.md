# ADR-aacruzgon-0062: Stored SearchParameters stay current in the overlay on update, delete and revive, with removals ordered by `last_updated`

- **Date:** 2026-11-06
- **Status:** accepted
- **Context:**
    - **The overlay as Step 2 left it** (ADR-aacruzgon-0041). Each instance keeps, per tenant, the stored SearchParameters it serves on top of the spec registry. It held one definition per `url`, replaced by precedence. `create` noted a new one; a TTL reload rebuilt it from a scan, keeping the notes made after the reload began. Nothing removed a definition.
    - **What Step 3 adds.** `update`, `delete` and revive all change stored SearchParameters. Without a removal, a deleted or deactivated parameter stays in force on the writing instance until the next TTL refresh, while SQLite drops it at once (`backends/sqlite/storage.rs:821-824`, `:1668-1671`, `:1795-1801`). Step 3 plan D9 compared four designs; the first draft's "remove by id, then note" was shown wrong three ways (it loses another id's definition of the same `url`, a reload that read before the delete puts it back, and an update to a non-`active` body never invalidates).
    - **Two "Major" CodeRabbit threads on PR #50 were left open:** [r4497056726](https://github.com/aacruzgon/hfs-Cassandra-CS4411/pull/50#discussion_r4497056726) (a registry build that began before an invalidation can be cached after it) and [r4497056824](https://github.com/aacruzgon/hfs-Cassandra-CS4411/pull/50#discussion_r4497056824) (a reload misses a SearchParameter whose CAS applied but whose `resources_by_type` row failed).
- **Decision:** D9's option (a′), as layer L2a built it in `crates/persistence/src/backends/cassandra/backend.rs` (PR #58):
    - **One entry per stored id** (`TenantOverlay`, `:105`). Of the definitions sharing a `url`, the one with the highest precedence (newest `last_updated`, then higher `id`, ADR-aacruzgon-0041) is in force, picked each time the registry is built (`in_force`, `:115`). So removing the one in force brings the next one back.
    - **A removal is `(id, at)`** (`Removal`, `:83`), where `at` is the `last_updated` of the delete, or of the update whose body the overlay does not hold (not `active`, a base `url`, or unparseable). A definition of that id at or before `at` is not in force, whoever holds it: a reload that read it before the removal, or an older write's late note. A removal is kept until a newer version of its id replaces it, whether this process notes it (a revive, or an update back to an `active` body) or a reload reads it.
    - **Every removal invalidates** the tenant's registry. A put (create, update, revive) invalidates only when the definitions in force change, which keeps the seeding behaviour of #667.
    - **Who calls what:** `update` and `create_or_update`'s branches b and c call `replace_stored_search_parameter` (`:718`); `delete` calls `forget_stored_search_parameter` (`:739`), unless its compare-and-swap came back superseded; `create` and `create_or_update`'s branch a call `note_stored_search_parameter` (`:687`), as before.
    - **The reload** (`load_stored_search_parameters`, `:585`, and `merge_into_overlay`, `:658`) still takes `since` before its scan and keeps the notes made after it. A refresh reloads the tenants its scan lists plus those whose overlay holds a definition; an overlay holding only removals adds none.
    - **Deviation from D9's wording.** D9 said a removal carries "a sequence number from `note_seq`" that a reload honours. It carries the removal's `last_updated` instead. A resource's versions have strictly increasing `last_updated` (ADR-aacruzgon-0016), so the comparison is exact per id, also across instances, and needs no pruning rule.
    - **Known limitations, left to Step 5:**
        - r4497056726: a registry build that started before an invalidation can be cached after it. The race is in the shared `search/tenant_registries.rs`, and Step 3's new invalidations give it more chances. How to close it is Step 5's decision; the recommendation for its group is a registry generation counter, which a build checks before it caches.
        - r4497056824: a SearchParameter whose compare-and-swap applied but whose `resources_by_type` row failed all its tries is missing from the next reload until the sweeper replays its intent. Until then the writing instance keeps it in its overlay. R8 in the Step 3 CI reports counts such post-CAS failures and expects 0 (ADR-aacruzgon-0059).
- **Alternatives considered:**
    - **(a) Remove by id in memory, then note:** lost, for the three faults above.
    - **(b) Reload the tenant after every SearchParameter write:** lost. A partition scan plus a read per parameter on every such write, and it depends on the `resources_by_type` row, which a failed post-CAS write leaves missing, so it could drop a parameter just written.
    - **(c) Nothing; rely on the TTL refresh:** lost. A deleted parameter stays in force on the writing instance.
    - **D9's literal design, removals ordered by `note_seq` and pruned once no older reload runs:** lost. The audit showed [V], with a pure test, that once a removal is pruned, a late note of an older version (an update whose steps 4 to 6 ran slower than a later delete and a whole reload) puts a deactivated SearchParameter back in force. A reload's reads carry no sequence number, so `seq` could not compare them with a removal anyway.
- **Consequences:**
    - **Memory:** one `Removal` (an id and a timestamp) per deleted or deactivated stored SearchParameter id, for the life of the process, until a newer version of that id appears.
    - **`StoredSearchParameterReload::definitions`** counts every definition held, including those kept behind a newer one of the same `url`. Only a log line reads it (`crates/hfs/src/main.rs:4712`).
    - **An update of a SearchParameter the overlay never held** still records a removal and invalidates, as SQLite invalidates on every SearchParameter update.
    - **Other instances** still converge by the TTL refresh, as ADR-aacruzgon-0041 accepts for `create`.
    - **Step 5** owns both limitations. The second closes with the sweeper, which roadmap Step 5 already plans; the first is open for Step 5's group (a generation counter recommended).
    - **Tests** (PR #58 and L3's PR #59): the `reload_rules` module in `backend.rs` (10 pure tests and 2 async ones, `:1299`); `the_overlay_follows_an_update` and `a_reload_racing_a_deactivation_does_not_restore_it` (`update.rs:1147`, `:1267`); `a_searchparameter_delete_takes_it_out_of_the_overlay` and `a_superseded_searchparameter_delete_leaves_the_overlay_alone` (`delete.rs:1392`, `:1469`); `the_overlay_follows_each_branch` (`upsert.rs:1333`). A mutation disabling the removal rule failed 4 of them.
