# ADR-aacruzgon-0064: The places where Step 3 departs from, or sits uneasily with, the FHIR specification, accepted on purpose

- **Date:** 2026-11-06
- **Status:** accepted
- **Context:**
    - The Step 3 plan's HL7 matrix (90 rows, quotes checked verbatim) left a handful of rows where Cassandra, or the shared REST layer it sits under, does not do exactly what the spec says. Its checklist item 9 asks for each to be recorded, so that a reviewer finds the reason rather than a bug. The plan listed them as §9 #6.
    - **What changed since the plan** (re-checked against layer L4 `b7a7f7be8`, merged as `main` `9c8c8f4f3`):
        - **D8 is no longer a deviation.** The plan recommended keeping 404 for a delete with nothing to delete; Alan chose the spec instead (decisions `:10`, `:74`). The fork carries upstream's fix, HeliosSoftware/hfs#2529, so REST answers 204 (ADR-aacruzgon-0052), and `step3_crud_through_rest` asserts it on Cassandra (layer L4). The backend still returns `NotFound`, as SQLite, PostgreSQL and MongoDB do.
        - **Batch `ifMatch` became a compare-and-swap** when layer L6 merged (PR #57, `main` `dcc21a9ca`): the fork carries HeliosSoftware/hfs#2530 (ADR-aacruzgon-0056), and `batch_if_match_through_rest` asserts it on Cassandra through REST (matrix CC-9, CC-10; `crates/hfs/tests/cassandra_milestone_a.rs:1100`).
        - **The upstream issues are filed** (decisions `:85-94`): #2523 (D8), #2524 (missing body id, batch ids), #2525 (id validation, a proposal), #2526 (`HFS_RETURN_GONE`), #2527 (batch `ifMatch`), #2528 (the low bundle).
    - **One correction to a merged entry.** ADR-aacruzgon-0027 `:167` says `read` answers "410, or 404 with `HFS_RETURN_GONE` false", and so did the walkthrough (`:217`, `:448` on `main` `9c8c8f4f3`). Only the vread handler reads that flag (`crates/rest/src/handlers/vread.rs:81`); `read.rs` passes `Gone` through as 410 whatever it is set to, and so does a batch GET (matrix DS-1, live check; filed as #2526). ADR-aacruzgon-0027 is merged history, so the correction goes here (plan D18).
- **Decision:** each of these is accepted as it is, with the reason (item 6 only until layer L6, which has since merged):
    1. **`check_id` on PUT** (D11; matrix RS1, DS-8). `create_or_update` refuses an id that is not a FHIR `id` (`[A-Za-z0-9\-\.]{1,64}`, [R4 datatypes.html#id](https://hl7.org/fhir/R4/datatypes.html#id)) with 400 `invalid`, before any statement, where SQLite answers 201 for `PUT /Patient/a_b` or a 65-character id. It protects the 64-byte key bound the design's key sizes rely on (G35). The spec backs it ("failed basic FHIR validation rules" is 400); REST validating ids for every backend is upstream's proposal #2525.
    2. **A revive is 201 in every FHIR version** (D16; matrix U-7, U-9, VD-4). [R4 #update](https://hl7.org/fhir/R4/http.html#update) and R4B require it: "a 201 Created status code if the resource was created (or brought back to life/re-created)". R5 drops the parenthetical, and [R5 #upsert](https://hl7.org/fhir/R5/http.html#upsert) adds "A server SHALL not return a 201 response if it did not create a new resource" (the build: SHALL NOT). Whether a revive "created a new resource" is ambiguous, not contrary; HFS has one REST layer for every version, and every backend answers 201 (`created = true` in the trait).
    3. **An `If-Match` PUT that races a delete answers 404** (matrix DS-6). The spec's 404 on update means an unsupported type ([R4 #rejecting-updates](https://hl7.org/fhir/R4/http.html#rejecting-updates)); a 412 or 409 would fit better. It is the shared contract (`crates/rest/src/handlers/update.rs`, every backend's `update` returns `NotFound` for a row deleted in the gap), and the race suite accepts it.
    4. **A `delete_versioned` that loses to another delete answers 404.** With `If-Match`, REST answers 412 from its own read before storage is called, so `delete_versioned` meets `NotFound` only when another delete wins the race between that read and the compare-and-swap (walkthrough 3.4).
    5. **`meta.lastUpdated` can run 1 ms ahead of the clock** (matrix RS5). `lu(N+1) = max(now_ms, lu(N) + 1 ms)` keeps it strictly increasing per resource (ADR-aacruzgon-0016), where [R4 resource.html#Meta](https://hl7.org/fhir/R4/resource.html#Meta) says "the current time on the server". It is ahead only under clock skew or more than one write per millisecond on one resource.
    6. **Batch `ifMatch` was check-then-act until layer L6 merged; it is no longer a tension** (matrix CC-9, CC-10; ADR-aacruzgon-0024's G28). Until PR #57 (`dcc21a9ca`), a batch PUT with `ifMatch` went through `create_or_update`, whose retry could overwrite a version it never saw, and a batch DELETE with `ifMatch` called plain `delete`. ADR-aacruzgon-0056 pins both to the version the gate checked, so nothing is left to accept; the item stays as the record of the window from Step 3's first writes to L6.
    7. **Two batch entries on one resource are not rejected** (matrix B-3). R4 says a batch SHALL have no interdependencies and servers SHOULD validate it; the build names same-resource entries as one. REST does not validate it on any backend. Cassandra survives it: concurrent entries on one id race through the same compare-and-swaps (ADR-aacruzgon-0024).
    8. **`/metadata` over-advertises until Step 7** (matrix G1, CS-4). It lists the three history interactions and every registered search parameter of every type, because `capabilities.rs` hard-codes the interactions and lists all parameters. Step 7's hooks (roadmap 7.1, 7.2) fix it. What it says about Step 3's own interactions is true, and `step3_crud_through_rest` asserts it.
    9. **A PUT with no body `id` is accepted, and a batch PUT's id is never compared** (matrix U-2, B-2). R4: "If no id element is provided, or the id disagrees with the id in the URL, the server SHALL respond with an HTTP 400". It is REST's, the same on every backend, filed upstream as #2524 and not carried in the fork.
    10. **`HFS_REQUIRE_IF_MATCH` answers 412 where the spec names 400** (matrix CC-7), and batch and PATCH bypass it: REST-owned, in upstream's low bundle #2528.
    11. **`HFS_RETURN_GONE=false` changes vread only** (D18, matrix DS-1). `read` of a deleted resource is 410 whatever the flag, which is what R4 wants ("a GET for a deleted resource returns a 410"). The walkthrough's two lines are corrected in this entry's commit, and this entry corrects ADR-aacruzgon-0027 `:167`, whose index status gains a pointer here. The upstream documents that say otherwise are listed in #2526.
- **Alternatives considered:**
    - **For 1, accept the id as SQLite does** (D11 b), or **wait for #2525** (D11 c): lost; either lets a PUT store a key over the bound the design relies on.
    - **For 2, 200 for a revive under R5 and R6 builds** (D16 b): lost; it needs a version switch in the shared REST layer and makes Cassandra differ from every backend. **Configurable** (D16 c): lost; a setting for an ambiguity.
    - **For 3, 4, 7, 9 and 10, change REST in the fork:** lost; each is upstream's file and the same on every backend, so each is filed upstream instead of carried (D22). The exceptions carried are #2529 (ADR-aacruzgon-0052) and #2530 (ADR-aacruzgon-0056).
    - **For 11, fix `read_handler` in the fork** (D18 b): lost, an upstream handler change Cassandra does not need, while the default is already what R4 asks. **Change nothing** (D18 c): lost, the walkthrough would keep telling workers something false.
- **Consequences:**
    - **None of these needs Step 3 code.** Items 1 and 2 are Cassandra's own and tested (`upsert.rs` live tests; `step3_crud_through_rest`'s `invalid_ids_through_rest` and `delete_and_revive_through_rest`, `crates/hfs/tests/cassandra_milestone_a.rs:469-470`); the rest are REST's.
    - **Item 6 closed** when PR #57 merged (`dcc21a9ca`), before this entry's commit; this entry is the record of the window. Item 8 closes when Step 7 lands; items 3, 4, 7, 9, 10 and 11 when upstream decides their issues.
    - **The roadmap's Step 3 "Spec." line** and the design's CRUD row and "Where R4 and the build differ" paragraph are corrected in this entry's commit (matrix DS-2, DS-3, DS-4).
