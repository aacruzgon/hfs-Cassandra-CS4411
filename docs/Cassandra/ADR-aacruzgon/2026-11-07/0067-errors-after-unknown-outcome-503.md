# ADR-aacruzgon-0067: After an unknown CAS outcome, every later statement's error is 504 for a timeout and 503 for anything else

- **Date:** 2026-11-07
- **Status:** accepted (Alan approved it on 2026-11-07). It amends ADR-aacruzgon-0055's "What does not change".
- **Context:**
    - **What ADR-0055 decided.** An error of R2 (the `LOCAL_SERIAL` read) or R3 (the version-row read) after an unknown CAS outcome is 504 for a timeout and 503 for anything else, never the plain table's 500. Its reason: "After an unknown outcome neither is known: the CAS may have applied". Its "What does not change" kept the plain table for every other statement: "the same `Server` error on I1, V1 or the X1 delta is still 500".
    - **What that left out.** After an unknown outcome, R2 or R3 is not the only statement the same request sends. A request whose R2 shows the row unchanged re-runs its attempt (up to 2 re-runs), and every re-run sends its own V3 (the rewrite of row N) and I1 (the intent row) before its CAS. A `delete` that takes its retry, and a `create_or_update` that takes its next turn, send a new R1 (the pre-read). The earlier attempt may have applied, or may still apply, during all of them. But those errors went through `map_driver_error` (`write.rs`, `run_cas` step 2 and `write_intent`; `delete.rs`, `delete_turns` step 0; `upsert.rs`, the loop's R1), so a `Server`, `Protocol`, `Truncate` or `QueryError` there answered 500.
    - **Found by the independent review of Step 3** (finding E2), reproduced with the fault seam on the shared node: attempt 1's C1 timed out and applied late; R2 had seen no row, so the request re-ran; the re-run's I1 got a `Server` error. The request answered `BackendError::Internal` (REST 500) while the resource was stored at version 1, with no version row and no `resources_by_type` row (the sweeper's to finish). A 500 says "server bug, the request failed"; neither was true, and a client that believes it may POST again. The test `a_reruns_intent_error_after_an_unknown_outcome_is_503` is that reproduction, and fails on the parent commit's code.
    - **The module doc disagreed with the code.** `write.rs`'s failure-handling doc said "V3 or I1 fails: its error (503 or 504)"; the plain table gives 500 for the errors above. The design's step 2 says the same as the doc ("return the driver error, which Helios maps to 503 … or 504").
    - **Why it is a decision.** It changes how errors on the write path are mapped, and it amends an accepted entry (ADR-aacruzgon.md, "What counts as a decision worth an entry").
- **Decision:**
    - **The rule.** Once any attempt of a request has had an unknown outcome, the error of every statement the request sends after it (a re-run's V3 and I1, a re-run's or later turn's compare-and-swap that the node refuses before it runs, and a later turn's R1, the decoding of its row included) answers as ADR-0055 maps R2's: the plain table's 504 (`BackendError::Timeout`) and 503 (`Unavailable`, `ConnectionFailed`) are kept, and everything else is `BackendError::Unavailable`, 503. Before any outcome was unknown, nothing changes: the plain table still answers, 500 included.
    - **The code** (`crates/persistence/src/backends/cassandra/write.rs`, `delete.rs`, `upsert.rs`):
        - `CasRequest::statement_error` maps a re-run's V3 and I1 error, and the error of a compare-and-swap that `classify_cas_failure` takes as not applied (`Syntax`, `Invalid`, `Unauthorized`, `Config`, `Protocol`, `Unprepared`, …), which stays unretried as ADR-0050 says; `CasRequest::after_unknown` maps a later turn's R1 result, and the decoding of that row into the next plan (`PreviousVersion::from_row`, in `delete.rs`, `update.rs`'s `update_attempt` and `upsert.rs`'s revive). Both apply the rule only when `had_unknown_outcome()`, and keep any error that is not a backend error (a permission, a validation) as it is.
        - One function, `unavailable_unless_timeout`, holds the 504/503 rule for `map_lookup_error` (R2, R3) and for the new `may_have_applied`. R2 and R3 keep their message ("the write's outcome could not be read back (…) failed; it may have been stored"); the new path says "<statement> failed after an earlier attempt's outcome was unknown; the write may have been stored". Neither names a host, since REST sends the message to the client verbatim.
        - The module doc's failure-handling list says what the code does.
    - **What does not change.** The plain table for a request with no unknown outcome. ADR-0055's rule for R2 and R3. ADR-0050: none of these errors is classified as a CAS, so none starts a new unknown attempt. The intent of the earlier attempt is kept for the sweeper, as before. Steps 4 to 6 after an applied CAS still never fail the write (G23).
- **Alternatives considered:**
    - **Keep ADR-0055's "What does not change" (500 for these errors):** lost. It reports a write that may be stored as a server bug, the case ADR-0055 itself rejected for R2, and the review reproduced it with the resource stored.
    - **Answer the earlier attempt's undecidable status instead (504 if it timed out, 503 if it failed), whatever the later statement's error was:** not recommended. It would tell the client what the earlier attempt did, which is the more accurate cause, but a later statement's own timeout would then read as 503, or its failure as 504, and the backend's other paths map each statement's own error.
    - **Before answering, read the row back at `LOCAL_SERIAL` and run the late-attempt check (ADR-0051), so that a late earlier attempt that applied answers as the success it is:** not taken now. It would turn the reproduced case into a 201, but it adds a serial read on a path where the node is already failing, and it changes a fault path's result from an error to a success, which the tests and the walkthrough's table would have to follow. Step 8's failure tests (item 8.3) can measure whether it is worth it.
    - **Treat a later statement's error as a new unknown outcome and re-run:** lost, for ADR-0050's and ADR-0055's reason: it spends the re-run budget on failures the overload probably caused.
- **Consequences:**
    - **What it guarantees.** A request that has had an unknown outcome never answers 500 for a backend error, whatever statement failed, so the client knows to retry later and to check before retrying a create.
    - **What becomes harder.** As with ADR-0055, an operator cannot tell a server bug on these statements from an outage by the HTTP status. `map_driver_error` still logs the driver's detail at `error` level for a statement the plain table makes 500.
    - **Tests**, in three groups, each from its own commit on PR #64. The first four and the two fault modes came in `d90270edd`, with this entry; each of those tests fails on the parent commit's code:
        - `a_reruns_intent_error_after_an_unknown_outcome_is_503`: the review's reproduction; the resource is stored by attempt 1, and the answer is 503.
        - `a_reruns_previous_version_row_error_after_an_unknown_outcome_is_503`: an update's re-run V3 fails with a `Server` error.
        - `a_later_turns_pre_read_error_after_an_unknown_outcome_is_503`: a plain delete's C3 times out, R2 shows another request's update, and the retry's R1 fails with a `Server` error.
        - `after_an_unknown_outcome_no_statement_error_is_500` (pure): 500 before any unknown outcome, 503 after for `Server` and `Invalid`, 504 kept for a timeout, a permission error kept.
        - Two test-only fault modes in the `cfg(test)` seam (`session.rs`): `FailWithServerError`, and `PassThrough`, which lets a fault land on the second statement of the same text.
        - Added in `dcd520db2` by the independent audit of PR #64 (`pr64-review`), which found the two cases the first change missed; each fails on the parent commit's code:
            - `a_reruns_cas_refused_before_it_runs_after_an_unknown_outcome_is_503`: attempt 1's C1 applies late, and the re-run's C1 is refused with a `Protocol` error; the resource is stored, and the answer is 503, not 500. It adds the fault mode `FailWithProtocolError`.
            - `a_later_turns_undecodable_pre_read_after_an_unknown_outcome_is_503`: a plain delete's retry reads a row whose `index_keys` does not decode; 503, not 500.
        - Added in `8a6e4bbd9`, after that audit's own review (finding A1), for the two other decoding sites; each fails when its own site is reverted:
            - `a_later_turns_undecodable_live_row_after_an_unknown_outcome_is_503`: a `create_or_update`'s turn 1 reads a live row whose `index_keys` does not decode (`update_attempt`); 503.
            - `a_later_turns_undecodable_marker_after_an_unknown_outcome_is_503`: the same on a delete marker (the revive branch); 503.
    - **To revisit.** Step 8's three-node failure tests, with the third alternative above.
