# ADR-aacruzgon-0068: A SearchParameter write whose outcome could not be decided reads its row back, and the overlay follows it

- **Date:** 2026-11-07
- **Status:** accepted (Alan approved it on 2026-11-07). It amends ADR-aacruzgon-0062 ("Who calls what", and its consequence "Other instances still converge by the TTL refresh").
- **Context:**
    - **The overlay** (ADR-aacruzgon-0041, 0062). Each instance keeps, per tenant, the stored SearchParameters it serves. A write that applied records what it wrote: `create` notes, `update` and revive replace, `delete` removes (`forget_stored_search_parameter`). The TTL refresh (default 3600 s) reloads every tenant from Cassandra.
    - **What a write that cannot decide does.** When a write's outcome stays unknown (R2 or R3 fails, or R2 cannot tell, ADR-aacruzgon-0034, 0055), it answers 503 or 504 and records nothing, because it does not know what it wrote. For a SearchParameter `delete` or a deactivating `update` that did apply, the deleted or retired parameter stays in force on the writing instance until the refresh. The client's retried `DELETE` finds the marker in its pre-read and answers `NotFound` (REST 204) before reaching the overlay, so it records nothing either.
    - **Found by the independent review of Step 3** (finding O1), reproduced with the fault seam on the shared node: delete → 503; read → 410; the parameter still in force; retry → `NotFound`; still in force; only a reload cleared it. The test `an_undecided_searchparameter_delete_that_applied_leaves_the_overlay` is that reproduction, and fails on the parent commit's code.
    - **Why it matters.** The design says the overlay is kept "current on every write" (`cassandra-discussion.md`, "What else the server expects", the search parameter registry). Under a fault, a deleted or retired SearchParameter keeps changing search results, and `_search` on its code keeps working, on the instance that was asked to delete it, for up to an hour. PR #61 records it as a third limitation in that paragraph and in the Step 5 handover.
    - **Why it is a decision.** It adds an overlay update driven by a read, which ADR-0062 does not have, and it changes how this instance learns of another instance's delete.
- **Decision:**
    - **The rule.** A SearchParameter write (`create`, `update`, `delete`, `delete_versioned`, `create_or_update`) that answers an error after one of its attempts' outcome was unknown reads its row once at `LOCAL_SERIAL`, which first completes any proposal the replicas already accepted, so it reads at least what a plain read would. The overlay then follows the row with the rules a write that knows what it wrote uses (`follow_stored_search_parameter`, `backend.rs`):
        - a delete marker is a removal at its `last_updated`, as `delete` records it;
        - a live row is put in or removed by its body, as `update` records it (an `active` body with a non-base `url` is put; any other body that parses is a removal; a live row whose `data` is missing or is not JSON changes nothing);
        - no row changes nothing.

      A failed read is logged at `warn` and changes nothing; the refresh, or the next write of that id, settles it then. The request's answer (503 or 504) is unchanged.
    - **The catch-up.** A `delete` or `delete_versioned` whose pre-read (R1) finds a SearchParameter already deleted records the removal at the marker's `last_updated` before it answers `NotFound`. That covers the client's retry when the read above also failed, and a delete another instance made before this delete's pre-read, which this instance would otherwise learn only at the refresh. A removal the overlay already holds, at or after the marker, while it holds no definition of that id at or before the marker, is not recorded again, so a repeated `DELETE` does not drop the tenant's registry each time.
    - **A delete that meets another writer's delete in the gap** (added 2026-11-07, Alan's choice). When another instance's delete lands between this delete's pre-read and its C3, the C3 misses with `deleted_at > 0` and the call answers `NotFound` (REST 204) with no unknown outcome, so neither the serial read nor the catch-up above runs. On that miss, for a SearchParameter, the delete reads the row once with R1 at `LOCAL_QUORUM`, and the overlay follows it with the same rules, the "already holds a removal at or after the marker" rule included. R1 is enough here, with no serial read: the miss came from a Paxos round on this partition that read the marker as committed, and Paxos v2's prepare first brings a quorum up to the latest commit: it goes ahead only once a consensus quorum of its responses holds the latest commit (`PaxosPrepare.java:617-618`), and otherwise first refreshes the stale participants with it (`:852-857`, as the design's G39 bullet cites), so a quorum read sees the marker, or a newer version, which the overlay follows as well. A failed read is logged at `warn` and changes nothing; the answer (`NotFound`, REST 204) is unchanged. After an unknown outcome this case does not run, since the serial read at the end of the call already reads the row.
    - **Code:** `serial_read_resource_row` (`read.rs`); `follow_stored_search_parameter` and `settle_overlay_after_unknown` (`backend.rs`); the calls at the end of `create` (`write.rs`), `update` (`update.rs`), the delete loop (`delete.rs`) and `create_or_update` (`upsert.rs`), each over the whole request, so every error path passes through it; the catch-up in `delete_turns` step 0; and `catch_up_with_a_deleted_miss` (`delete.rs`), on a `CasMiss::Deleted` of `delete_turns`.
- **Alternatives considered:**
    - **Record the removal speculatively whenever a SearchParameter delete is undecided:** lost. If the delete did not apply, the live parameter would be hidden: the removal at the attempt's `last_updated` is newer than the live version, so even a reload that reads it back cannot bring it back, until a newer version of the id is written.
    - **Reload the whole tenant after an undecided SearchParameter write:** not recommended. It decides the same thing, from a scan of the tenant's `resources_by_type` partition plus one read per stored SearchParameter, where one read of the row is enough; and a reload reads at `LOCAL_QUORUM`, so it does not first complete a proposal the replicas accepted, as a serial read does.
    - **Reload in the background, with retries, until it succeeds:** not taken. `CassandraBackend` is not `Clone` and holds the overlay by value, so a spawned task would need the backend restructured behind an `Arc`; and the TTL refresh already is that retry, at a longer interval.
    - **Only the catch-up on R1 (the review's first suggestion):** lost alone. It fixes nothing until a client retries, and the requirement is that an undecided delete not stay in force until the refresh.
    - **Nothing; record it as a limitation for Step 5:** what PR #61 did, pending this decision.
    - **Leave the in-gap case (another instance's delete between the pre-read and C3) as a limit that heals at the TTL refresh:** lost, Alan chose to close it on 2026-11-07.
    - **For the in-gap case, take the marker's `last_updated` from C3's own answer, with no read:** not taken. A missed C3 returns `deleted_at`, which C3 sets equal to the marker's `last_updated`, so it would save the read; but `CasMiss::Deleted` carries no value, and every operation's miss handling and its tests would change for one rare path.
- **Consequences:**
    - **What it guarantees.** After an undecided SearchParameter write, the writing instance's overlay matches the stored row as the serial read found it, so a delete or retirement that had applied by then takes effect at once and one that did not apply leaves the parameter in force. An undecided create or revive that applied is put in, as an applied one is.
    - **Cost.** One `LOCAL_SERIAL` read, only for a SearchParameter write that already failed with an unknown outcome. The catch-up is a check of the R1 row the delete already read. The in-gap case costs one R1, only for a SearchParameter delete whose C3 met another writer's delete.
    - **What it does not change.** ADR-0062's two Step 5 limitations (a registry build begun before an invalidation can be cached after it; a SearchParameter whose `resources_by_type` row failed after its CAS is missing from reloads until the sweeper replays it). Other instances still converge by the TTL refresh, except when they are asked to delete the same parameter: then the catch-up, or the in-gap read, takes it out here too. A proposal its coordinator is still running when the serial read runs can still apply after it (ADR-aacruzgon-0034); the overlay is then stale until the refresh or the next write of that id, as every undecided write's is today, but only in that narrower case.
    - **Documents changed after PR #61 merged** (it carried ADR-0062, the design's registry paragraph and the Step 5 handover): ADR-0062's status line and index row read "amended by ADR-aacruzgon-0068"; the registry paragraph in `cassandra-discussion.md` lists two Step 5 limitations, not three, and says what this entry does and leaves open; the Step 5 handover's O1 line says this entry closes it, with the same open cases. All three changed in commits on PR #64 after its merge of `main`.
    - **Tests**, from two commits on PR #64. The first five came in `65c42199b`, with this entry; each but the guard fails on the parent commit's code. The last, the in-gap test, came in `4dd6f7f03`:
        - `an_undecided_searchparameter_delete_that_applied_leaves_the_overlay`: the review's reproduction; out of force at once.
        - `an_undecided_searchparameter_delete_that_did_not_apply_stays_in_force`: the guard; a C3 that did not apply leaves it in force (it passes before and after).
        - `a_retried_searchparameter_delete_catches_the_overlay_up`: both serial reads fail; the overlay is unchanged until the retried `DELETE`, which takes it out.
        - `a_delete_of_a_parameter_another_instance_deleted_catches_up`: a second backend deletes it; this one's `DELETE` takes it out here.
        - `an_undecided_deactivating_update_leaves_the_overlay`: an update to `status: retired` whose C2 applied with R2 failing.
        - `a_searchparameter_deleted_in_the_gap_by_another_instance_leaves_the_overlay` (the in-gap case): a second backend deletes the parameter between this `delete`'s, and then this `delete_versioned`'s, pre-read and C3; the call answers `NotFound`, and the parameter is out of force at once. It fails on the parent commit's code.
