# ADR-aacruzgon-0070: The persistent target dirs carry cargo's `CACHEDIR.TAG`, so `cargo llvm-cov clean` really cleans the coverage dir; the coverage report also runs `step3_crud_through_rest` and gets a `crates/rest` section

- **Date:** 2026-11-07
- **Status:** accepted (Alan approved it on 2026-11-08). It amends ADR-aacruzgon-0047: its clean now works, and its report gains a `crates/rest` section beside the backend's unchanged scope. The ADR commit appends "; amended by ADR-aacruzgon-0070" to 0047's Status line, keeping its text, and 0047's index row links this entry, as 0058's does 0066.
- **Context:**
    - **What ADR-0047 relies on.** The coverage workflow (`.github/workflows/cassandra-coverage.yml`, ADR-aacruzgon-0047) keeps a persistent target dir, `target/cassandra-coverage`, like the other jobs (ADR-sam-michaels-0002). It runs `cargo llvm-cov clean --workspace` before the build, "so the report counts this run only".
    - **The clean did nothing but remove profiles.**
        - The reset step makes the dir with `mkdir -p` and writes `.stamp` into it.
        - Cargo writes `CACHEDIR.TAG` only into a target dir it creates itself. In cargo 1.99.1 (`5f94df478`), `create_dir_all_excluded_from_backups_atomic` returns early for an existing dir (`crates/cargo-util/src/paths.rs:747-751`).
        - Since cargo 1.97 (rust-lang/cargo#16712, its CHANGELOG "Cargo 1.97"), `cargo clean` with an explicit `--target-dir` refuses a dir whose `CACHEDIR.TAG` is missing, a symlink, or doesn't start with `Signature: 8a477f597d28d172789f06886806bc55` (`src/ops/cargo_clean.rs:72-88`, `:155-183`).
        - cargo-llvm-cov 0.9.1 runs exactly that, as `cargo clean --target-dir <dir> --package <every workspace member>`. It only `warn!`s when that fails, and exits 0 (`src/clean.rs:106-121`).
        - So every run from the first one on ADR-0047's final workflow logged `cannot clean …: missing or invalid CACHEDIR.TAG file`: 63 of the 64 successful coverage runs before PR #66's first one (42445138021), on both runners, counted from every one of their logs. The exception, 42253148327, is from before the audit moved the clean. Profiles and profdata were removed (`clean.rs:125-147`), so the workflow's profile check passed. The workspace's test binaries, `hfs` and rlibs stayed.
    - **Why that can change the figures.** `cargo llvm-cov report` passes to `llvm-cov` every executable under `target/debug` whose name is a workspace package or target name plus an optional hash (`src/report.rs:240-470`, `:578-593`). Nothing ties it to this run. A reproduction (cargo 1.99.1, cargo-llvm-cov 0.9.1, a one-crate workspace; `evidence/repro-scenario*.log` in the run folder) showed:
        - **The figures move.** A test binary left under another hash, built from code that has since moved, is counted. The file went from 14 regions at 50% to 22 at 31.82%, and from 4 functions at 50% to 6 at 33.33%, with no warning from `llvm-cov`.
        - **The same name changes nothing.** A binary of the same name is overwritten.
        - **The same locations change nothing.** A stale binary whose code sits at the same lines leaves the figures as they were, because `llvm-cov` merges instantiations at one location.
    - **When the hash changes.** Cargo's file-name hash (`unit_id`) mixes in the features, the profile, RUSTFLAGS, rustc and the dependencies (`src/compiler/build_runner/compilation_files.rs:738-880`). rustc and `Cargo.lock` already reset the dir through the stamp. So a stale binary needs a feature, profile or RUSTFLAGS change that leaves `Cargo.lock` alone. None of the 15 branches that ran the workflow changed a `Cargo.toml`, `.cargo/config` or `rust-toolchain`. The workflow's RUSTFLAGS and features haven't changed since `05c0cd573`.
    - **The coverage report left out the Step 3 REST test** (Alan added this to the task on 2026-11-07). The roadmap records it under "Known gaps in what CI runs" (`development-roadmap.md:347` on `main` `29c8de3e6`). `cassandra-coverage.yml` ran the Milestone A round trip and the readiness test, but not `step3_crud_through_rest` (`crates/hfs/tests/cassandra_milestone_a.rs:447`), which the required Cassandra job runs (`fmt-clippy-cassandra.yml`, "Step 3 CRUD through hfs against this node").
    - **The other five reset steps make their dirs the same way:** `r4b-compile-check.yml`, the three in `fmt-clippy-cassandra.yml`, and `upstream-canary.yml` (ADR-sam-michaels-0005). None of them runs `cargo clean`, so nothing fails there today.
- **Decision:**
    - **Every reset step writes `CACHEDIR.TAG` on every run, right after its `mkdir`,** with cargo's exact text (`paths.rs:801-815`, byte-identical to the tag cargo 1.99.1 writes, checked with `cmp`). An existing dir without the tag gets it on its next run, with no reset. The stamp and the cap still reset the dir as before.
    - **The coverage build step checks the clean.**
        - It prints the dir's file count before and after `cargo llvm-cov clean --workspace`.
        - It fails if any of the test binaries the report reads survived the clean (`hfs`, `helios_persistence-*`, `cassandra_tests-*`, `backend_capability_contract-*`, `cassandra_milestone_a-*`), as it already failed on a surviving profile.
    - **The working clean stays as cargo-llvm-cov documents it,** `cargo llvm-cov clean --workspace`, at its cost of about 2–2.5 minutes a run (Alan's choice, as recommended). **The surviving-binary check stays** (Alan's choice, as recommended).
    - `upstream-canary.yml` changes only by the same three lines, for the same reason, and its decision in ADR-sam-michaels-0005 stands.
    - **The coverage job runs `step3_crud_through_rest`,** in a step of its own between the round trip and the readiness test, as the required job runs it:
        - **The same as the required job:** the command; the checks that the test exists and ran exactly once (`--exact` on a missing name passes with 0 tests); `timeout-minutes: 10`; `HFS_TEST_CASSANDRA_URL` as its only setting.
        - **What this job adds:** `LLVM_PROFILE_FILE` with `%c`, as the other two Milestone A steps set it, since the test kills its `hfs` with SIGKILL; and an `EXIT` trap that lists the profile files the step adds. The trap ends in `|| true`, because under `bash -e` a failing command in an `EXIT` trap would fail the step even when the test passed.
        - **When it runs:** when the round trip passed (`!cancelled() && steps.round-trip.outcome == 'success'`), like the readiness test. Its failure fails the job, but hides neither the readiness test nor the report steps. Those run `if: !cancelled()` and `always()`, so the coverage report is still written.
        - **No collision:** the test starts its own `hfs` under a fresh `test-` tenant (`unique_tenant("step3-rest")`) with unique ids (`unique_suffix`), so it can't meet the round trip's rows. It needs no `HFS_*` variable from the job: `Hfs::start` clears every `HFS_*` and sets its own.
        - **Elsewhere in the job:** its log goes to the tests report with the others; the measured-tests line names it; the coverage section counts three Milestone A steps' profile files.
    - **The coverage report gets a `crates/rest` section** (Alan's choice, as recommended). It widens ADR-0047's scope by a section of its own, and leaves the backend's section, its regex, its files and its figures unchanged:
        - **Exports:** a step after the backend report runs a second `cargo llvm-cov report --json` on the same profiles, with its own ignore regex keeping only `crates/rest/src`. A third export sets the Step 3 step's profiles aside, into `$RUNNER_TEMP` and back. The Step 3 step lists the profile files it adds, from an `EXIT` trap, so the list exists when the test fails too.
        - **The script:** `.github/scripts/cassandra-coverage-rest-summary.py` (standard library, with `test_cassandra_coverage_rest_summary.py`, 14 tests) builds the section. It shows the totals with every test and without Step 3, the files Step 3 changes, six named REST paths with their counts with and without Step 3, and the functions only Step 3 reaches.
        - **Naming:** a function is the `fn` item whose span, in the checkout, holds the first line of its code. Closures, async bodies and generic instances fold into it without a demangler. Two items of one name in one file stay two (the 11 `fn from` in `error.rs`). An item spans from its `fn` line to its closing `}` alone at its own indentation, as rustfmt writes it. Code outside every item, such as a static's initializer or a `fn $name` that a `macro_rules!` writes, counts in lines and regions only.
        - **Report-only:** the step is `continue-on-error` and runs unless the run is cancelled, so it can fail neither the job nor the backend report.
    - **The required fmt job runs the script's tests by module name** (Alan's choice, as recommended, 2026-11-08). Its step "Test the CI report script" (`fmt-clippy-cassandra.yml`) ran `unittest discover -s .github/scripts -p 'test_ci_report.py'`, so the new tests ran in no required check. It now runs `PYTHONPATH=.github/scripts python3 -m unittest -v test_ci_report test_cassandra_coverage_rest_summary`, from the repository root as before, and its comment says a new script's tests are added there by name. The job and step names are unchanged. Names rather than a `test_*.py` glob, because a glob's reach depends on files upstream owns: `.github/scripts/fhir-bench/` holds upstream's `test_*.py` files, and only its missing `__init__.py` keeps discovery out of it today.
- **Alternatives considered:**
    - **(b) Let cargo create the dir:** lost. It would mean moving `.stamp` out of the dir, as a `$TARGET_DIR.stamp` beside it, and dropping the `mkdir`.
        - It changes the reset logic, and the build-size report's `TARGET_DIR_*` lines, in all six steps.
        - Every existing dir would reset once, since its stamp is no longer where the step looks: one cold build per dir per runner.
        - Until the first build, the coverage job's profile checks would run against a dir that doesn't exist.
        - Writing the tag is three lines and keeps everything else as it is.
    - **Write the tag only when it's missing,** as cargo does: not adopted. Writing it on every run is one line shorter, and also repairs a tag with the wrong content. Nothing but these steps writes it in these dirs.
    - **`cargo llvm-cov clean --profraw-only`, accepting the stale binaries:** lost. It is what the job did by accident, and the reproduction shows how it skews the figures.
    - **A narrower clean** (delete only the stale workspace executables `report` reads, keep the rlibs and warm builds): lost. It would be this repository's own variant of cargo-llvm-cov's documented flow, and the cost it saves is about 2–2.5 minutes of a report-only job that blocks no merge.
    - **No surviving-binary check:** lost. The clean failed silently in 63 of the 64 successful runs before PR #66's first one; the check turns that into a failed job at once.
    - **Widen the backend's scope to `crates/rest`:** lost. It would change the backend figure that every report since ADR-0047 gives, so the two could no longer be compared. A section of its own keeps that figure as it is.
    - **Leave REST out:** lost. Step 3's REST paths, batch `ifMatch`, PATCH and the 410/404 mappings, would show nowhere, since the backend lines they reach are already covered by `cassandra_tests`.
    - **Leave the other five steps alone:** lost, but only narrowly; nothing fails in them today. The tag keeps each dir as cargo itself would have made it, so a later `cargo clean --target-dir` works. Backup tools that honour the tag skip the build output: tar `--exclude-caches`, borg, restic `--exclude-caches`.
    - **A `test_*.py` glob in the fmt job:** lost. It would run the same 75 tests today, since discovery skips `fhir-bench/`, which has no `__init__.py`. But an upstream sync that added one would pull upstream's 224 `fhir-bench` tests into a required check, and one of them fails in the fork: `test_compare_legs.test_canonical_matches_workflow` reads `.github/workflows/fhir-benchmark.yml`, which the fork doesn't have. The fmt check would turn red on a sync that changed nothing of ours.
