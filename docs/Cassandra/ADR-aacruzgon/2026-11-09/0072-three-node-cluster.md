# ADR-aacruzgon-0072: The three-node Compose cluster: RF 3 without touching the schema, two profiles, topology, and what RF 3 accepts

- **Date:** 2026-11-09
- **Status:** accepted (Alan approved it on 2026-11-09, as drafted). It amends ADR-aacruzgon-0050's reason that the "Partition, RF 3" failure test expects 503: the test now expects `WriteTimeout` first and then 503 (decision 3). The commit that adds this entry appends that note to 0050's Status line and index row.
- **Context:**
    - **Requirement.** Roadmap row 0.3 and the Step 0 Compose bullet ask for a second Compose file: three nodes on one host, RF 3, `GossipingPropertyFileSnitch`, one DC matching the keyspace's `NetworkTopologyStrategy` map. Section 6's cluster failure tests (row 8.3) run on it.
    - **Why these are decisions.**
        - The schema is signed off (ADR-aacruzgon-0028), so RF 3 has to arrive some other way.
        - ADR-aacruzgon-0003 left the rack layout to this item.
        - The per-node limits have to fit the laptops, and ADR-aacruzgon-0002 rejected 2 CPUs for the single node.
        - Roadmap section 1 said the cluster runs only on the 32 GB machines.
        - Running the cluster showed that two written expectations do not hold at RF 3: section 6's "Partition" row (`Unavailable` from the first moment) and the race suites' assumption that a loser is only ever told it lost.
    - **Memory on the laptops.** OrbStack's VM on Alan's Mac has 8.79 GiB, shared by several workers.
- **Decision:** Alan decided the five points below on 2026-11-09, all as recommended.
    1. **RF 3 lives in `docker/cassandra/keyspace-three-node.cql`, and `schema.cql` is unchanged.** The file holds the same `CREATE KEYSPACE` as `keyspace-single-node.cql` with `'helios-dc1': 3`, applied in its place, before `cqlsh -k helios -f schema.cql`.
        - *Measured:* `helios` has `{'helios-dc1': '3'}` and 10 tables, and `Owns 100.0%` on each node. `git diff main...HEAD -- docs/Cassandra/schema/` is empty.
    2. **Two profiles.** The defaults are per node 2 CPUs, `MAX_HEAP_SIZE=768M`, `MAX_DIRECT_MEMORY_SIZE=384M`, 2 parallel and 2 concurrent GC threads, 2.5 GiB with swap disabled, 7.5 GiB in all. They are for functional checks. `docker-compose.cluster.heap2g.yml` (4 CPUs, 2G, 1G direct, 5 GiB per node, 15 GiB in all) is for measured numbers on the 32 GB machines.
        - *Measured at the defaults:* `cpu.max` 200000 100000, `memory.max` 2684354560, `memory.swap.max` 0, `-Xms`/`-Xmx` 768M, 2 GC and 2 concurrent threads by kernel thread name. Boot from clean 3:27. At the 2.5 GiB limit, idle 1.30 to 1.31 GiB per node (the audit's report gives 1.33 to 1.35, and kept no file of it) and `memory.peak` 1.42 GiB, over the boot alone.
        - *Measured by the author at a 2 GiB limit per node, the rest as above:* idle 1.31 GiB per node, `memory.peak` 1.47 GiB over the failure procedures and the backend tests, no OOM kill.
        - *Not measured:* the 2G override is rendered with `docker compose config` and has not been booted (it needs 15 GiB).
    3. **Section 6's "Partition" row is reworded:** `WriteTimeout` for about 20 s, and a timed-out write may have applied, then `Unavailable`.
        - *What it changes in ADR-aacruzgon-0050.* That entry gave as one reason for no CAS retry after `Unavailable` that "the three-node 'Partition, RF 3' failure test expects 503". The test now expects `WriteTimeout` first. The decision itself stands: no retry after `Unavailable`, which is still 503.
        - *Measured by the audit, with T=0 at the disconnect:*

          | Statement on the isolated node | `WriteTimeout` | `Unavailable` | OK again after reconnect at T=40.8 s |
          | --- | --- | --- | --- |
          | Plain `LOCAL_QUORUM` | T=0.2 to 19.9 s, 2.0 s each | T=20.1 to 41.1 s | T=41.3 s |
          | LWT, `LOCAL_SERIAL` | T=0.2 to 18.1 s, 1.0 s each | T=18.3 to 41.3 s | T=41.5 s |

        - All nodes `UN` at T=42.6 s. The other coordinator answered 657 of 657 statements. A plain write that timed out was present afterwards at `LOCAL_QUORUM`; the two timed-out LWTs that were checked were not.
    4. **Row 8.3 on RF 3 accepts 504 as a possible answer and checks the invariants instead:** no history gap, one winner per version, no lost write. There is no backend retry. The race suites need a cluster-aware outcome check, which also verifies the history, before Step 8.
        - *Measured by the audit, 12 runs of `cassandra_tests` (167 to 171 of 172; heap 512M, 1800 MiB per node, 2 CPUs):* race failures in 9 of 12 runs, all 18 errors the same text, `serial read: CAS operation timed out: received 0 of 2 required responses after N contention retries` (N 0 or 1). That is R2 at `LOCAL_SERIAL` superseded with `hadSideEffects == MAYBE` (`Paxos.java:884-894`), 504 under the design and ADR-aacruzgon-0050 and 0055. It is raised at once, not after a wall-clock timeout. A winner can receive it: seven of eight concurrent creates got `AlreadyExists` and the eighth got the 504.
        - *Measured by the author:* one race test, the plain-delete race, failed 9 and 12 of 20 runs at 4 CPUs per node and 11 of 20 at 2, on a host at load 14 to 18 by `uptime`. The author put that load down to other workers' builds, but no process list was kept for those runs, and the load includes the cluster and the test itself. The CPU limit did not change the rate in those runs; what an idle host does is unmeasured.
    5. **Two seeds of three,** `cassandra-1` and `cassandra-2`.
        - *Measured:* with `cassandra-3`, then the seed `cassandra-1`, stopped, `LOCAL_QUORUM` writes and LWTs carried on from the other two. Both seeds log "will not auto bootstrap"; `cassandra-3` bootstraps. All three use the replication-aware token allocator, so a seed's tokens are not random.
    - **Also decided here, without a separate question to Alan:**
        - **Racks, the item ADR-aacruzgon-0003 left open:** one per node, `helios-rack1` to `helios-rack3`; one DC, `helios-dc1`; cluster `helios`.
        - **Compose project:** `hfs-cassandra-cluster`, the same image digest and `entrypoint.sh` as row 0.1, nodes started one at a time behind a CQL healthcheck.
        - **Ports:** `127.0.0.1:59342`, `59343`, `59344`, overridable.
        - **Fixed subnet:** `172.29.59.0/24`, overridable with `CASSANDRA_CLUSTER_SUBNET_PREFIX`, addresses `.11` to `.13`.
- **Alternatives considered:**
    - **RF 3 by `ALTER KEYSPACE` after `keyspace-single-node.cql`:** lost. That file also runs the `system_traces` step, which its own comment says the cluster must not run, and raising RF needs a full repair afterwards ([repair](https://cassandra.apache.org/doc/5.0/cassandra/managing/operating/repair.html#full-repair-example)).
    - **RF 3 as a variable in `schema.cql`, or a CQL template:** lost. It is a change to the signed-off file, and ADR-aacruzgon-0008 keeps replication out of it on purpose.
    - **The new keyspace file under `docs/Cassandra/schema/`:** lost (decision 1). That directory is the signed-off set.
    - **All three nodes in `helios-rack1`:** lost. `batchlog_endpoint_strategy: dynamic_remote` avoids the local rack when it can, which needs other racks, and one rack per node is the layout of a real three-AZ deployment. Racks cannot be changed later ([production recommendations](https://cassandra.apache.org/doc/5.0/cassandra/getting-started/production.html#configure-racks-and-snitch)).
    - **One seed:** lost (decision 5). With `cassandra-1` the only seed, a node bootstrapping while it is down has nobody to contact, and the failure tests stop nodes on purpose.
    - **Three seeds:** lost. No node could bootstrap, so no node could be replaced without the extra step.
    - **4 CPUs per node by default:** lost for the default profile. 12 CPU limits on 8 to 11 core laptops only moves the contention. The override has them, for the machines that report numbers.
    - **The cluster on the 32 GB machines only (the roadmap's text):** lost (decision 2). The failure procedures and the RF 3 functional checks need no measured numbers, and laptop runs are how the team finds out what the cluster does. Laptop numbers never go in the report (ADR-aacruzgon-0002).
    - **Limits through environment variables:** lost, as in ADR-aacruzgon-0002: the roadmap asks for the limits to be recorded in the file.
    - **One published port:** lost. A host client whose only contact point is the stopped node cannot open a session, which is what the failure tests do.
    - **Addresses assigned by Docker:** lost. A node's address would depend on start order and could change over a stop, and `docker network connect` would pick a new one.
    - **Sharing `CASSANDRA_HOST_PORT` with the single node:** lost. CI exports it, so it could silently move the cluster onto 59142.
    - **A backend retry of the serial read, or of the whole request, on RF 3:** lost (decision 4). ADR-aacruzgon-0055 left "retry R2 once" to Step 8 with numbers. Alan chose not to retry and to accept the 504, which is honest about an outcome the backend cannot read.
    - **Using `-Dcassandra.allow_unsafe_replace=true` to replace a seed:** lost. The seed would join on the dead node's tokens with no data and no streaming, and section 6 requires a replacement that bootstraps from the others.
- **Consequences:**
    - **Easier.** Section 6's cluster failure tests have a cluster. The same keyspace name, DC and tables work on one node and on three; only the keyspace file differs.
    - **The 2-CPU default differs from ADR-aacruzgon-0002 on purpose.** That entry rejected 2 CPUs for the single node because LWT benchmarks at concurrency 32 would be CPU-bound, and the single node's limits are the benchmark envelope. The cluster's default profile reports no numbers. It exists so a laptop can run the procedures. The measured profile has the single node's 4 CPUs per node.
    - **Memory: the cluster can take other containers down.** At the defaults the limits add up to 7.5 GiB, and the three nodes use about 4 GiB at idle. On 2026-11-09 the single node on 59042 was OOM-killed at 05:05:46 UTC while the audit booted this cluster beside it, on the 8.8 GiB VM with about 3.7 GiB free (cause inferred from the timing; the kernel log was not readable). The README now says to add up the running limits first. On Alan's Mac the agents working there follow that as a rule: the limits of everything running, plus what is about to start, stay at or under 8.3 GiB.
    - **Seed replacement, from decision 5.** A seed never bootstraps (`StorageService.java:1132`), and Cassandra refuses to replace without bootstrapping (`:750`). Addresses are fixed, so a replacement keeps its address and stays in the seed list. Measured: replacing `cassandra-3` took 65 s and the data read back at `ONE`; a replacement `cassandra-2` exited with code 3 in 6 s. So `cassandra-3` is the node to replace, or a seed comes off its own `CASSANDRA_SEEDS` for its first boot. The delta audit (`pr72-delta`) ran that second route on 2026-11-09, once on each seed, on this Compose file in its own project: 512M heap, 256M direct memory, 1700 MiB per node, 2 CPUs, RF 3, 300 rows. With the seed list unchanged the node exited with code 3. Off its own list, `cassandra-2` was healthy in 65 s and `cassandra-1` in 76 s, on the volume a refused first attempt had left. Each logged a bootstrap, held the rows before any repair, and kept them when recreated from the normal file and repaired. It has not been run at the default limits or with a large data set, so row 8.3 should run it if it replaces a seed.
    - **The fixed subnet [I, not reproduced].** `172.29.59.0/24` sits inside Docker's default `172.29.0.0/16` pool, so a daemon that has already handed out that /16 would refuse the network. This Mac is not affected (OrbStack allocates from 192.168.x), and the override variable handles it where it happens.
    - **The race suites cannot gate RF 3 until they change.** A failing run panics on the outcome before it checks the version history. Decision 4's cluster-aware check has to exist before Step 8, and it is new work.
    - **Backend clients and an isolated coordinator.** `docker network disconnect` also removes the node's published port, so a host client cannot be the isolated node's client, and neither can one on the cluster network: the isolated container has only `lo`, and `cqlsh` from `cassandra-2` timed out (measured by the delta audit). Row 8.3 runs the client inside the isolated container. The backend's answer in the first 20 s is 504 by the walkthrough's step 2 table [I, not run].
    - **One host is not a failure domain.** The cluster tests node and network failures, not disk or host failures. Benchmarks on it share one machine's CPU and disk.
    - **Compaction threads.** `concurrent_compactors: 8` is kept as shipped, above the 2-CPU limit, as in ADR-aacruzgon-0001.
    - **Docker Desktop.** Container addresses are not routable from the host there, so `cdrs-tokio` can use only the contact-point node from the host. OrbStack (checked with `nc` to `172.29.59.12:9042`) and Linux are fine [Docker Desktop part inferred, not run].
    - **`system_auth` stays at `SimpleStrategy` RF 1** and `system_traces` at RF 2, unchanged: nothing in this project uses authentication. `TRACING ON` at `LOCAL_QUORUM` works on three nodes.
    - **To be revisited.** Row 8.3 may want a load-driven memory figure. Section 7's 504 trigger is for 4 clients or fewer, and the 12 runs had 8 writers, so that case is unmeasured.
