# ADR-aacruzgon-0074: The demonstration script is a Python standard-library client under `docs/Cassandra/demo/`, against a server started separately on port 58080; a transaction's 501 on Cassandra is an accepted departure

- **Date:** 2026-11-09
- **Status:** accepted (Alan approved it on 2026-11-09, as drafted). It amends ADR-aacruzgon-0064: the transaction 501 joins its accepted departures.
- **Context:** Roadmap row 0.9 asks for a demonstration script passing against PostgreSQL, and row 8.6 later runs the same script on Cassandra and PostgreSQL in CI. The roadmap fixes what it covers (`development-roadmap.md:565`) and its pass rule, "every step returns the documented status", but not what it is written in, where it lives, or who starts the server. Each is a choice between workable designs. Three further points came up while building and auditing it:
    - The backends are documented to answer three requests differently, so the script needs a rule for that.
    - Cassandra's refusal of a transaction is 501, where R4, R4B and R5 all say "Servers that don't support the batches or transactions SHOULD return an HTTP 400 error" ([R4](https://hl7.org/fhir/R4/http.html#transaction), [R4B](https://hl7.org/fhir/R4B/http.html#transaction), [R5](https://hl7.org/fhir/R5/http.html#transaction)). `schema/coverage.md` section 6 documents the 501, but ADR-aacruzgon-0064, which records the accepted departures, does not list it.
    - The HTTP API does not name the storage backend, so a run cannot show which backend answered: against a SQLite HFS, `--backend postgres` passed every step and its report said `"backend": "postgres"`.
- **Decision:**
    1. **Language:** Python 3.9 or later, standard library only.
    2. **Location:** `docs/Cassandra/demo/demo.py` and `README.md`.
    3. **Server:** the script starts nothing. It takes `--base-url` (default `http://127.0.0.1:58080`), and `--wait` retries `GET /metadata`. The caller starts the database and HFS on host port 58080, with `HFS_BASE_URL` set to the same URL.
    4. **Backend differences:** a required `--backend` selects the expected answer. A step whose documented answer differs states both, with a citation for each, and checks only the selected one; no step accepts either answer. Three steps differ: a transaction bundle (PostgreSQL 200, Cassandra 501), reading that transaction's entry back (PostgreSQL 200, Cassandra 404), and `:exact` on a string parameter (PostgreSQL 200, Cassandra 400).
    5. **The transaction 501 on Cassandra is kept and is an accepted departure from R4's SHOULD 400.** The refusal is the shared REST layer's, the same as on S3 (`crates/rest/src/handlers/batch.rs`, `AtomicityUnsupported`). It meets the SHALL in the transaction rules, "reject all resources and return an HTTP 400 or 500 type response", and misses only the SHOULD. This entry adds it to ADR-aacruzgon-0064's list, by a note on that entry's Status line.
    6. **`--backend` chooses answers and does not verify the server.** `--server-log` reads HFS's last `Starting Helios FHIR Server` line and adds a step requiring its `storage_backend`, `public_base_url` and `port` to match the run; the summary reports `backend_confirmed`. That line says what HFS was started with, not who answers on the port, because HFS writes it before it binds. So row 8.6's job checks five things, and a run passes only with all five. It refuses to start HFS unless the port is free, where only `curl`'s exit 7, connection refused, counts as free. It uses a new log for each run. It requires `"backend_confirmed": true`. It checks that the HFS it started is still running when the script ends. And it **must count the run's rows in the backend** (Alan's decision, 2026-11-09). The job makes that count, because the script talks only to the URL it is given: on PostgreSQL, `SELECT count(*) FROM resources WHERE tenant_id LIKE 'demo-<run id>-%'` must be 16, with the `run_id` from the report's summary. On Cassandra the count applies once Step 8 runs it: the job counts `helios.resources` for the run's two tenants and Step 8 sets the number it requires (a run on 2026-11-09 left 15, PostgreSQL's 16 less the transaction's entry, which Cassandra refuses).
- **Alternatives considered:**
    - Language:
        - **Bash with `curl` and `jq`:** the shortest for single requests, but following `next` links, comparing id sets and writing a report need awkward shell, and CI's use of `jq` is only through `gh --jq`, so `jq` itself is an unproven dependency on the runners.
        - **`hurl`:** the most readable request files, but no CI job installs it, it is a new tool for all five team members, and set comparison across pages does not fit it.
        - **A Rust test in `crates/hfs/tests/`:** the best fit with `cassandra_milestone_a.rs`, but it needs a compile before every run, is less readable as a demonstration, and adds a new file under `crates/`, which goes on section 8's list.
        - Python was chosen because `python3` already runs in every required job (`fmt-clippy-cassandra.yml`, `ci-report.py`), it needs no install, and it reads top to bottom as the demonstration.
    - Location:
        - **`docker/demo/`:** the script is not a container definition, and `docker/` is on section 8's list.
        - **`utils/`:** an upstream directory, on section 8's list.
        - **`crates/hfs/tests/`:** only for a Rust test, and also on section 8's list.
        - `docs/Cassandra/` is the fork's own, already holds files CI uses (`schema/*.cql`), and never conflicts at an upstream sync.
    - Server:
        - **The script starts HFS and the database:** a single command, but the script would then need to know each backend's build, Compose project and schema step, and row 8.6's job starts those itself. It would also no longer talk only to the URL it is given.
    - Port: 8080 and 8090 are used in `docker/` and in `.github/disabled-workflows/`, and in no enabled workflow. 58080 appears in neither directory, nor in `.github/workflows/`. It follows the reasoning of ADR-aacruzgon-0007, which decides only the two database host ports.
    - The transaction status:
        - **Change REST to answer 400:** lost. It is the shared layer's answer for every backend without transactions, so the change belongs upstream, and 501 already meets the SHALL.
        - **A separate ADR for the 501:** lost. One departure, found by this work and pinned by this script.
    - Confirming the backend:
        - **Read it from `/metadata` or `/health`:** not possible. Neither names it (`crates/rest/src/handlers/capabilities.rs:302-306`, `health.rs:44-51`). Adding it would change a shared handler for this script's sake.
        - **Count the run's rows in the database from the script:** the strongest check, but the script would need a client for each database and would no longer talk only to the URL it is given. Lost for the script; row 8.6's job must make this count itself, from the report's `run_id` (Decision 6).
        - **Compare `started_at` from `GET /health` with the timestamp on the log's startup line, in the script:** lost. Alan left it out on 2026-11-09. The required row count catches a wrong server on another backend or another database, including one that started inside this check's margin. Both values come from HFS's own clock, so the server that answers should have started just before the log's line: 0.20 to 0.21 s on three normal starts, against 11.5 s for an older HFS left on the port, which a scratch copy of the script caught. Its gap: with a margin M (5 s was tried), a holder passes if it started no more than M before the new HFS's log time, because its `started_at` then looks like the new HFS's. Neither this check nor the row count catches a second HFS on the same database that answers in place of the one the job started. With the started HFS held back by `SIGSTOP`, standing in for a busy machine, and a second PostgreSQL HFS bound just after the refusal, the run was 74 of 74 with `backend_confirmed` true and 16 rows, and the job exited 0. The second HFS's `started_at` was 0.227 s before the log's line, the same as a normal start, so this check would have passed it too.
        - **The log check alone, without the port refusal, the process check and the row count:** lost. HFS writes the startup line before it binds, so the line does not show who answers. An HFS that cannot bind writes it and exits 1 while the port's holder keeps answering, and an old HFS can answer a whole run while the new one is still starting; in that case the run was 74 of 74 with `backend_confirmed` true and no rows in PostgreSQL. Both were reproduced.
- **Consequences:**
    - Row 8.6 needs a workflow step that starts HFS for each backend, runs the script with `--report` and `--server-log`, and counts the run's rows; the JSON Lines report gives CI its measurement artifact.
    - The 16 becomes a number row 8.6's job depends on. If a section of the script changes what it creates, the number in the README and in the Step 8 bullet changes with it.
    - Until Steps 6a to 6d land, the script fails on Cassandra in the search steps. On 2026-11-09, on `main` at `9c7b8e6ba` plus this PR, 18 of its 61 steps failed there, every one from the 501 search answers today.
    - `HFS_BASE_URL` must match `--base-url`, or the paging steps fail and say so.
    - HFS must log at `info`, the default, for `--server-log` to find its line; otherwise the step fails rather than passes.
    - `--server-log` is for a server the script reaches directly: through a proxy on another port, its step fails and says so.
    - The startup line's wording and field names become something this script depends on. If upstream changes them, the step fails and says what it did not find.
    - The README and script carry their citations by section name, so they can go stale when those documents change.
