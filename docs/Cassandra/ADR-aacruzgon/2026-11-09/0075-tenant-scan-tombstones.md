# ADR-aacruzgon-0075: the stored-SearchParameter reload falls back to `resources` when tombstones stop its reads

- **Date:** 2026-11-09
- **Status:** accepted (Alan approved it on 2026-11-09, as drafted)
- **Context:**
    - **The failure (issue #74).** After a delete workload `hfs` cannot restart on Cassandra. `stored_search_parameter_tenants` runs `SELECT DISTINCT tenant_id, resource_type FROM resources_by_type` (ADR-aacruzgon-0041, R5), and the error stops startup.
    - **Why it fails.** `DISTINCT` queries each partition to its first live row (`SelectStatement.java:814-822`, 5.0.9), and the table clusters newest first (`schema.cql`), so a deleted row newer than every live row is read and counted. The counter is per read command and replica across all partitions it touches (`ReadCommand.java:525-602`), and fails above 100,000 (`tombstone_failure_threshold`).
    - **What triggers it.** Only rows deleted at the head of a partition: 50,001 create-update-delete cycles (two tombstones each) or 100,001 create-deletes. Update-only workloads, including 101,000 updates of 1,000 resources and a mass update of 101,000 resources, leave a live row at the head and do not fail.
    - **How long it lasts.** The counter skips purgeable tombstones (`ReadCommand.java:460-461`), so the scan works again as soon as `gc_grace_seconds` (10,800 s) has passed, with no compaction needed. `nodetool flush` and `compact` before that change nothing. One create of the affected type ends the tenant scan's refusal sooner, because it puts a live row at the partition's head; it does not end the refusal of the per-tenant id read below, which reads the whole partition (measured on a 5.0.9 node: after 101,120 create-deletes and one create, `origin/main` exits on `operation="stored SearchParameters"`).
    - **The same limit on a second read (issue #79).** The reload's per-tenant id read, `SELECT id FROM resources_by_type WHERE tenant_id = ? AND resource_type = 'SearchParameter'`, reads the whole partition and not only its head, so updates count as much as deletes. Updates leave the head live, so the tenant scan passes and only this read is refused. On a 5.0.9 node (real REST, debug `hfs`): 101,120 updates of 32 SearchParameters in one tenant, in 32 s, with no delete, and `origin/main`'s restart exits with `operation="stored SearchParameters"` and `READ_TOO_MANY_TOMBSTONES`, for every tenant, because the startup load is fail-fast.
    - **The constraints.** ADR-aacruzgon-0041: no tenant registry, the schema is signed off, and a failed load must stop startup rather than serve the wrong compartment rules.
- **Decision:** When a replica refuses the partition-key scan with `READ_TOO_MANY_TOMBSTONES`, list the tenants from `SELECT DISTINCT tenant_id, resource_type, id FROM resources` instead, at startup and on every refresh. When a replica refuses a tenant's SearchParameter id read the same way, take that tenant's ids from the same scan, keeping only its SearchParameter rows; the point reads that follow drop the soft-deleted ones. Any other failure still stops startup. No table, key, write path or trait changes.
    - **Alan's choices (2026-11-09, each as recommended):**
        - This design now, over a tenant registry table. The registry stays ADR-aacruzgon-0041's named follow-up.
        - The fallback's trigger is `READ_TOO_MANY_TOMBSTONES` only, not read timeouts.
        - The CI opt-in of the 101,000-tombstone test on the required job stays.
        - Issue #74's text is updated at merge, with the corrections and the update-only result.
        - Option 1 of issue #79: the per-tenant id read gets the same fallback, in PR #78, before it merges (2026-11-09). It runs one scan per affected tenant rather than one per reload, because each scan must come after that tenant's `since`.
- **Alternatives considered:**
    - **A smaller page size, or token-range slices.** Each page and slice is a new read command, so this fixes tombstones summed across partitions [V], but not one partition over the limit [V], which is what a real delete workload builds (50,001 cycles on one type).
    - **A tenant registry: a new table, or a reserved partition in `resources_by_type`.** The clean long-term answer, and ADR-0041's named follow-up. It changes the write path of every SearchParameter write, needs a backfill for data written before it (or misses tenants silently), and a new table needs schema sign-offs. It is not needed to restore startup. Revisit if tenant scans must get cheaper or the fallback's cost shows up.
    - **Always scan `resources`.** Simpler, one code path, but startup and every hourly refresh then cost one row per resource instead of one per tenant and type (upstream's PostgreSQL hit the same on a whole-table refresh, #939). Rejected.
    - **For the per-tenant read, keep the limit and document it (issue #79, option 2).** No code, but one tenant's 100,000 SearchParameter writes in 3 h would stop every tenant's restart. Lost: Alan chose the fallback.
    - **For the per-tenant read, tolerate the failure for that tenant only (issue #79, option 3).** Others are unaffected, but that tenant serves with an empty overlay, which ADR-aacruzgon-0041 rejected.
    - **One scan per reload, shared by both fallbacks, with `since` taken once beforehand (issue #79's option 1 as written).** Not chosen (Alan, 2026-11-09). It would save a scan per affected tenant after the first. Without the single `since` it is wrong: a tenant's reload reads `note_seq` before its id read (ADR-aacruzgon-0041, decision 5), so a scan taken for an earlier tenant could miss a SearchParameter noted before that tenant's `since` and drop it from the overlay. Taking `note_seq` once before the scan would make it safe, but the saving applies only when more than one tenant has over 100,000 SearchParameter writes within 3 h.
    - **Non-fatal failure at boot.** Serving with an empty overlay is what ADR-aacruzgon-0041 rejected: compartment rules are silently wrong. Loading on first use needs an async hook at 31 sync call sites.
    - **Raise `tombstone_failure_threshold`.** A node-wide setting that defers the failure and raises the heap risk for every query. Rejected.
    - **Do nothing and document it.** Any restart within 3 h of a real delete workload would fail to start. Not acceptable before Step 8 and any demo that deletes.
- **Consequences:**
    - **Easier:** startup survives any tombstone count in `resources_by_type`, on either read; a poisoned node needs no operator action.
    - **Harder:** a second access path to keep correct; `resources` is no longer "point reads only".
    - **Cost of the fallback:** one row per resource, linear in the table, about 5 to 11 s per million rows. Measured in the independent audit of PR #78, on one 5.0.9 node with a debug client: 5.2 s at 1.05 million rows with 1 KB compressible bodies (45 MB on disk); 7.2 s at 1.04 million rows with 2 KB incompressible bodies (2.07 GB on disk), and 11.3 s on that table's first scan. A truly cold page cache was not measured. It runs only while the fast scan is refused, at startup and on each hourly refresh: about 3 h after a burst of deletes, and longer while deletes keep a partition's head dead. Only `SearchParameter` rows are held, per page, so memory does not grow with the table.
    - **The per-tenant read no longer stops startup (issue #79).** Measured on a 5.0.9 node, same reproduction as in Context: `origin/main` exits; with this change the restart is healthy, loads `tenants=3 stored=33` (the 32 updated SearchParameters and another tenant's), and logs the fallback. After 50,001 delete cycles on top, both fallbacks run in one boot, `stored=33`, 720 ms. Reaching the limit by 101,120 deletes alone, or by a mix of updates and deletes, behaves the same, and each tenant's overlay was checked through `/metadata`. Its cost is one more scan of `resources` per affected tenant per reload, and one point read per id, soft-deleted ones included: with a debug `hfs` on one node, 101,120 soft-deleted ids took the whole load to 7.2 to 8.2 s, against 90 ms after 101,120 updates of 32 live SearchParameters.
    - **Must be revisited:** `count` and paged reads on a poisoned partition still fail or are slow (G8, Step 8's case).
