    2. **`read_repair = 'NONE'` on `resources_by_type` is not set now.** It is a Step 8 measure-first switch: roadmap section 7 gains its row. IW9's guarantee is restated as it holds:
        - each replica applies one partition's rows together, so an update alone never lets a quorum read count the resource twice once its batch has reached a quorum;
        - `count` is off by one either way, twice or not at all, in two cases:
            - **after a write that reached fewer than a quorum, on RF 3.** Blocking read repair, the default, repairs only the rows a read covered, so it can copy half of the batch onto another replica. A read covering only N+1 copies N+1 onto a replica that still holds N, and a quorum `COUNT(*)` returns 2. A read covering only N copies N's tombstone onto a replica that never got N+1, and a quorum `COUNT(*)` returns 0 for a live resource. Both reproduced on three 5.0.9 nodes; with `read_repair = 'NONE'` the same sequences return 1. This lasts until the batch's retry, a hint, a batchlog replay or the sweeper reaches the other replicas;
            - **after a write whose index step was skipped or did not finish** (G23; 0006, Decision 1 and Decision 2), on one node too, until the sweeper or repair finishes it. `read_repair` does not change this case.
        - `count`'s internal paging (10,000 rows per page) can also miss a resource updated between pages; `resources_by_type` is `last_updated DESC`, so a paged count can only miss, never double.

      Section 7's trigger: in row 8.3's RF 3 failure tests, a `count` off from the live resource count, twice or not at all, in the window after a sub-quorum write and before its retry, a hint, a batchlog replay or the sweeper reaches the other replicas, confirmed by re-running the case with `read_repair = 'NONE'`; how long and how often counts as too much is set when row 8.3 measures it. Section 6 already says that no failure test asserts an exact `count` right after a failed write (`development-roadmap.md:612`). No schema changes.

- **Alternatives considered:**
    - **Pointers in each old entry's own text, not a new entry.** This lost: the log is append-only, and status-line notes plus one entry is how ADR-aacruzgon-0078 updated 0067 and 0077.
    - **Waiting until Step 5 is built, and one entry then.** This lost: PRs 2 to 8 cite 0006 from the start, and the rules above changed when PR #86 merged.
    - **`read_repair = 'NONE'` on `resources_by_type` now.** This lost, for now. It restores partition-level write atomicity, so read repair could never make `count` show one resource twice or not at all. But:
        - it gives up monotonic quorum reads on that table: a row seen at one quorum read can be missing from the next, until the write reaches more replicas. The 5.0 docs: NONE "Provides partition level write atomicity, but not monotonic quorum reads";
        - it changes the signed-off schema (ADR-aacruzgon-0028);
        - it does nothing for the other case, a write whose index step did not finish, which only the sweeper or repair closes;
        - the failure it fixes needs a write that reached fewer than a quorum, and the RF 3 failure tests (Step 8, row 8.3) have not measured how often, or for how long, `count` is off.
      The search content is protected either way by the tag check.
    - **`read_repair = 'NONE'` on every index table.** This lost: only `count` reads `resources_by_type` without the tag check. Every search result is tag-checked against `resources`, so a half-applied index batch can hide or delay a hit, but never return wrong content.
