# ADR-aacruzgon-0085: Step 7 starts before Step 6, in phases; Cassandra answers `supports_search() == false` until Step 6; the parameter hook takes #2593's per-parameter shape

- **Date:** 2026-11-22
- **Status:** accepted; phase 5 superseded by ADR-aacruzgon-0087 (upstream-first as HeliosSoftware/hfs#2775, without the history hook)
- **Context:**
    - **The defect.** A Cassandra server's `GET /metadata` advertises what the backend refuses (roadmap CS-4 / G1, ADR-aacruzgon-0064 item 8). Reproduced through `hfs` on a single node, with the code of `main` `c9ff363d7` for each half (see "Verified"):
        - `history-instance` and `history-type` on every resource type (`crates/rest/src/handlers/capabilities.rs:443-461`) and `history-system` at system level (`:222`). Cassandra answers all three `501` by design (design scope table; ADR-sara-lahourpour-0002 (PR #102) keeps the history suites out of Step 4).
        - `search-type` and 30 `searchParam` entries for `Patient`, 46 for `Observation`, because Cassandra keeps the trait default `supports_search() == true` (`crates/persistence/src/core/search.rs:563`). Every search answers `501` until Step 6.
    - **The spec.** [R4 http.html#capabilities](https://hl7.org/fhir/R4/http.html#capabilities): "Servers SHALL provide a Capability Statement that specifies which interactions and resources are supported." R5 has the same sentence. The interaction codes come from the required value sets [type-restful-interaction](https://hl7.org/fhir/R4/valueset-type-restful-interaction.html) and [system-restful-interaction](https://hl7.org/fhir/R4/valueset-system-restful-interaction.html). R5 and the build add codes to the code system (`search-compartment`, the abstract `history` and `search`, and in the build the conditional and delete-history codes), but none of the codes this change drops or keeps is renamed. [`readHistory`](https://hl7.org/fhir/R4/capabilitystatement-definitions.html#CapabilityStatement.rest.resource.readHistory) is "able to return past versions as part of the vRead operation" in R4, R4B and R5, and the build only changes "operation" to "interaction", so ADR-aacruzgon-0025 holds in all four. [`searchParam`](https://hl7.org/fhir/R4/capabilitystatement-definitions.html#CapabilityStatement.rest.resource.searchParam): "Search parameters for implementations to support and/or make use of"; [`searchInclude`](https://hl7.org/fhir/R4/capabilitystatement-definitions.html#CapabilityStatement.rest.resource.searchInclude): "If this list is empty, the server does not support includes". [R5 search.html#modifiers](https://hl7.org/fhir/R5/search.html#modifiers): "Servers SHALL support any modifiers present in search parameters the server advertises support for." Upstream's Discussion #28: the statement "must accurately reflect the union of what's available and identify gaps".
    - **The order.** The roadmap runs Step 7 "after step 6 lands" (`development-roadmap.md:550`). Only one part of it needs search: Cassandra's final answer, token, date and URI parameters, plus `_list` (and `_in` from R5), which REST resolves into `_id` (row 7.2). The hooks, the handler, the history half and the tests don't.
    - **Upstream already has a design for the parameter hook.** HeliosSoftware/hfs#2593 (filed by Alan on 2026-11-17, open, no comments yet) proposes `SearchProvider::serves_search_param(&self, resource_type, code, param_type) -> bool`, defaulting to `true`, and argues against a type-level hook: "it cannot express `special`: `_text` is served on SQLite and `near` is not". The roadmap and the design (`cassandra-discussion.md:390`) name a type-level `supported_param_types()`, written before #2593. For the history half, #514's open comments say the per-resource `interaction` array is still a literal, and #1384/#1401 set the pattern this follows: a defaulted per-capability method, read by the statement builder.
- **Decision:**
    - **Step 7 starts now, in five phases**, each in its own commit or commits so the generic REST patch can be lifted out:
        1. `InstanceHistoryProvider::supports_history()`, default `true`; `CompositeStorage` answers from its history providers (`false` when it has none, which is when it answers history `501`); `build_capability_statement`, and `create_minimal_routes`, which serves `/metadata` too, gain `InstanceHistoryProvider` in their bound and, where the hook is `false`, drops `history-instance` and `history-type` from every resource entry (the `AuditEvent` entry included) and `history-system` from `rest.interaction`. `vread`, `versioning: versioned` and `readHistory: true` stay (ADR-aacruzgon-0025). Cassandra answers `false`.
        2. `SearchProvider::serves_search_param(resource_type, code, param_type)`, default `true`, #2593's signature; `CompositeStorage` forwards it on the same route as `supports_search`. `build_search_params` drops every parameter, common ones included, the storage doesn't serve; `searchInclude` and `searchRevInclude` drop each `Type:code` whose reference parameter isn't served. No existing backend overrides it, so every existing backend's `/metadata` is unchanged.
        3. Cassandra answers `supports_search()` from its declared `BackendCapability::BasicSearch`, as S3 does (#514). It doesn't declare `BasicSearch` yet, so its `/metadata` lists no `search-type`, `searchParam`, `searchInclude` or `searchRevInclude` until Step 6 declares it.
        4. **After Step 6 (not now):** Step 6's last commit declares `BasicSearch` (which flips `supports_search()` with no other change) and overrides `serves_search_param` with `SUPPORTED_PARAM_TYPES.contains(&param_type)`. That keeps `_list` and, from R5, `_in`, because the handler asks about both as `_id` of type token (PR #105), and drops `_text` and `_content`, which it asks about as `special`. That closes row 7.2.
        5. **The upstream pull request (row 7.3, not now):** phases 1 and 2's generic commits, PR #105's branch cherry-picked onto `upstream/main`, opened only with Alan's permission, as "Part of #2593". It would deliver #2593's hook and `/metadata` filter (with SQLite's, PostgreSQL's, Elasticsearch's and MongoDB's overrides for `near`, `_text` and `_content` added there, or left to a follow-up), and the history half of #514.
    - **The hook names and defaults:** `supports_history() -> bool`, default `true`; `serves_search_param(&str, &str, SearchParamType) -> bool`, default `true`. Both are on traits already in the server bound, so no existing backend changes.
    - **Separability:** the generic commits touch only upstream files (`core/history.rs`, `core/search.rs`, `composite/storage.rs`, `capabilities.rs`, `routing/fhir_routes.rs`, the REST tests and their stub, and `book/src/ch14-contributing.md`) and mention no Cassandra type, path or decision; the Cassandra overrides and their test are separate commits.
    - **Two fork pull requests**, as section 8's "**Separate PR:**" line and Step 7's task "Kept on its own branch and submitted upstream as its own pull request" (`development-roadmap.md:542`) require:
        - **PR #105, the generic hooks** (phases 1 and 2), branch `cassandra/step7-capability-hooks-rest` from `main` `c9ff363d7`: the four generic commits and section 8's line, cherry-picked unchanged. It builds and passes its tests without the Cassandra commits. Its branch is the one phase 5 lifts upstream.
        - **PR #104, the Cassandra overrides** (phase 3, and phase 1's Cassandra half), branch `cassandra/step7-capability-hooks`: `4b427a092`, `e4feb8262`, and this entry's commit. Its pushed history keeps the generic commits it was first opened with (no force-push or rebase), so its diff shrinks to the Cassandra part only once #105 merges and `main` is merged into it.
        - **Merge order:** #105 first, then `main` into #104, then #104. #104 can't merge before #105: it would bring the generic commits in under the Cassandra pull request.
        - **This entry goes in #104**, with the roadmap, `cassandra-discussion.md` and README edits: the ADR rules (`ADR-aacruzgon.md:23`, CLAUDE.md "Decision records") only require the entry and those document edits in one commit, and #105 stays the upstream-shaped patch, with no fork decision record in it.
    - **It amends the roadmap's Step 7 "Who"** from "**W**, after step 6 lands" to "**W**: phases 1 to 3 before Step 6, phase 4 with Step 6's last commit, phase 5 when Alan decides (ADR-aacruzgon-0085)", and `cassandra-discussion.md:390`'s `supported_param_types()` bullet to the per-parameter hook.
- **Alternatives considered:**
    - **Wait for Step 6, as the roadmap says:** lost. Cassandra's `/metadata` would keep claiming history and every search parameter until then, and the hooks don't need search.
    - **`supported_param_types() -> Vec<SearchParamType>`, as the roadmap and design say:** lost to #2593's shape. It can't express a backend that serves some parameters of a type and not others (`_text` but not `near`, both `special`), which is #2593's whole case on SQLite and MongoDB, so the upstream pull request would need a second hook. Cassandra's answer is the same either way, a check of `SUPPORTED_PARAM_TYPES`. The design's "two hooks delegate to the same `SearchCapabilityProvider` data" still holds through that constant.
    - **An include hook (`supports_include()`), as the design's bullet implies:** lost for now. #2593 keeps `searchInclude`/`searchRevInclude` "unless a backend cannot serve the reference parameter they name", and filtering each `Type:code` through `serves_search_param` does exactly that. For Cassandra every reference parameter is unserved, so both lists vanish. An upstream backend that serves reference search but not `_include` doesn't exist; if one appears it needs its own hook.
    - **Cassandra keeps `supports_search() == true` and phase 4's parameter filter is applied now:** lost. The statement would still list `search-type` and the token, date and URI parameters, which answer `501` until Step 6.
    - **A literal `fn supports_search() -> bool { false }` in Cassandra:** lost to the declaration. Deriving it from `BasicSearch` keeps one source, which `backend_capability_contract.rs`'s `assert_supports_search_matches_declaration` already checks for the other backends, and makes phase 4 one line.
    - **Three history hooks (instance, type, system):** lost. Every backend either serves all three or none, the traits are a hierarchy (`SystemHistoryProvider: TypeHistoryProvider: InstanceHistoryProvider`), and the roadmap and ADR-aacruzgon-0025 name one hook.
- **Consequences:**
    - **Easier:** Cassandra's `/metadata` stops over-advertising history now and search until Step 6; Step 6's last commit is two small changes; the upstream pull request is ready when Alan wants it.
    - **Harder:** the roadmap's and design's hook name changes, and #2593's follow-up overrides (`near`, `_text`, `_content`) become upstream work on top of the hook rather than part of it.
    - **It narrows ADR-aacruzgon-0037 for `BasicSearch`:** since `supports_search()` follows the declaration, `BasicSearch` is declared only with phase 4, in Step 6's last commit, never at Step 6a or before; and 0037's premise that "no client sees the claim" no longer holds, because `/metadata` now reads `BasicSearch` and `InstanceHistory`.
    - **To revisit:** at Step 6, whether `_include`/`_revinclude` need their own hook (they don't for Cassandra); whether the search handler should refuse unserved parameters from the same hook (#2594).
    - **Tests:** the REST stub tests in `crates/rest/tests/` (run by the report-only Code Coverage job, and locally); `metadata_through_rest` in `crates/hfs/tests/cassandra_milestone_a.rs`, in the required `Cassandra schema (single node)` job and in the report-only all-versions job.
