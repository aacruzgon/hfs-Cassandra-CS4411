# ADR-aacruzgon-0087: #2593 is fixed upstream-first as HeliosSoftware/hfs#2775, which upstream merged unchanged; the fork takes it with the upstream sync of 2026-11-24, not a cherry-pick, and the history hook stays fork-only

- **Date:** 2026-11-24 (worked on from 2026-11-22; upstream merged, and the fork synced, on 2026-11-24)
- **Status:** accepted
- **Context:**
    - **The defect, upstream.** `GET /metadata` listed search parameters the configured backend
      refuses (HeliosSoftware/hfs#2593, filed by Alan on 2026-11-17; on 2026-11-22 it was open,
      with no assignee, no comment, no linked PR, and no open upstream PR or branch touching
      `capabilities.rs`, `SearchProvider` or the backends' search code). Reproduced on
      `upstream/main` `3ee95eff8` through `hfs`, R4 and R5, on each backend:
        - `Location.near` on SQLite, PostgreSQL, MongoDB and `sqlite-elasticsearch`, where a search
          answers `400`;
        - from R5, `Location.contains` and `Composition.section-text`, also `400`, which #2593
          didn't name;
        - `_text` and `_content` on every type on MongoDB, where a search answers `501`.
    - **The spec.**
      [CapabilityStatement.rest.resource.searchParam](https://hl7.org/fhir/R4/capabilitystatement-definitions.html#CapabilityStatement.rest.resource.searchParam):
      "Search parameters for implementations to support and/or make use of".
      [R5 search.html#modifiers](https://hl7.org/fhir/R5/search.html#modifiers): "Servers SHALL
      support any modifiers present in search parameters the server advertises support for".
    - **What the fork already had.** PR #105 (merged 2026-11-23 as `e90814507`) carries the
      parameter hook as `08a685bd0`, with `be1049b35` and `ba444b259` (`_list` and `_in` asked
      as `_id`), and no backend overriding it. It also carries the history hook
      `supports_history()` (`b7a1da483`, `3b46684ee`), which Cassandra answers `false`. PR #104
      (Cassandra's overrides) merged the same night as `83e61668a`. ADR-aacruzgon-0085 planned
      phase 5 (row 7.3) as #105's branch lifted upstream, with the backends' answers "added
      there, or left to a follow-up".
    - **What upstream did with it.** HeliosSoftware/hfs#2775, "fix(rest): /metadata lists only the
      search parameters the storage serves (#2593)", was opened from Alan's account on
      2026-11-23. A maintainer (smunini) built `hfs` from its head and from its base, ran both on
      PostgreSQL 16, MongoDB 7.0.48 and Elasticsearch 7.17.29 in R4 and R5, and found that only the
      statement changes: 19 searches per backend and version answer the same on both builds.
      #2775 merged on 2026-11-24 at 23:56 UTC, head `1f6feff10` unchanged, as `3a99196d1`, which
      closed #2593.
    - **The fork and upstream.** Fork `main` (`0339bd7c2`) last merged upstream in #92
      (2026-11-18, merge `dbe7a79ee`, upstream `8999b3f53`). `upstream/main` `3a99196d1` is 194
      commits past that (57 pull requests and the 0.2.10 release on its first-parent line), #2775
      the last of them.
    - **Why it is a decision.**
        - It changes what the server says on the wire for every backend the fork shares with
          upstream.
        - It replaces phase 5's plan (#105's branch lifted upstream as it stands) with an
          upstream-first branch that leaves the history hook out.
        - It decides how the fork takes an upstream fix this project wrote: a cherry-pick (as
          ADR-aacruzgon-0049, 0052 and 0056 carried #2518, #2529 and #2530 ahead of upstream) or
          the next sync.
- **Decision:**
    - **Upstream-first, done.** The branch `fix/2593-serves-search-param` was cut from
      `upstream/main` `3ee95eff8`. It has two signed commits, and upstream merged both unchanged
      in #2775:
        - `e28b5d446` is the parameter hook as #105 has it, without the history hook:
          `08a685bd0` adapted by hand (the pick didn't apply on its own, because the stub and the
          unit-test helpers came from `b7a1da483`), plus `be1049b35` and `ba444b259`;
        - `1f6feff10` holds each backend's answer, taken from where its search refuses:
            - SQLite, PostgreSQL and Elasticsearch: an `EVALUATED_SPECIAL_PARAMETERS` list in the
              query builder, read by both `serves_search_param` (`false` for any other `special`
              parameter) and the builder's refusal, so the two read one declaration; the names a
              builder builds whatever their type (`_id`, `_lastUpdated`, and `_in` on SQLite) are
              not gated, so no input the builder accepted before is refused;
            - MongoDB: `false` for every `special` parameter, since it refuses the whole type;
            - S3 is unchanged;
            - `/metadata` keeps a composite only when each component resolves in the registry and
              is served, so nothing it lists is refused (`Composition.section-code-text` and the
              R5/R6 composites whose component definitions the spec bundles don't publish go;
              searching those is upstream #2774).
    - **The fork takes it with the sync of 2026-11-24, with no cherry-pick.** On
      `sync/upstream-2026-11-24` from `main` `0339bd7c2` (fork PR #113):
        - `git merge -S --no-ff upstream/main` (`3a99196d1`), message as #92's: merge
          `d670b026b`, signed;
        - one fork commit after it, `0fdf34ef9`, moves the one workflow the sync adds (below);
        - then one fork-only commit with this entry, its index row and the roadmap edits.
    - **How the merge's eight conflicts resolve:**
        - **The six files #2775 and #105 share** (`book/src/ch14-contributing.md`,
          `composite/storage.rs`, `core/search.rs`, `handlers/capabilities.rs`,
          `tests/capabilities_search_params.rs`, and `tests/common/capability_hooks.rs`, add/add):
          upstream's content plus exactly #105's history half. No upstream commit since `8999b3f53`
          but #2775's two touches them. `core/search.rs` is upstream's file. The others keep only
          `supports_history` (the composite's forwarding and its test), the handler's
          `supports_history` argument and clause, `InstanceHistoryProvider` in the handler's
          bound, the stub's history field and history traits, and item 4's sentence on
          `supports_history`. The two include comments `d399c331b` had reworded in
          `capabilities.rs` take upstream's wording.
        - **`crates/persistence/Cargo.toml`:** upstream's `postgres` feature (the TLS dependencies
          of #2746) and its version bump to 0.2.10; the fork's `cassandra` feature and pin
          (`cdrs-tokio` 10.0.0, no `cdrs-tokio-helpers-derive`, ADR-aacruzgon-0044).
        - **`.github/dependabot.yml`** (add/add): the fork's file (PR #3) stays unchanged, and
          upstream's (#2591) is not taken. Its `docker` and `github-actions` entries for `/`
          duplicate the fork's, and Dependabot refuses two entries for one ecosystem and
          directory. Its `/.github/actions/*` directory is left out because no active workflow
          uses those composite actions: only archived ones do (`ci.yml` uses `cargo-target-gc`,
          `renormalize-eol` and `rust-lint-setup`; `ci-extended.yml`, `release-build.yml` and
          `windows-nightly.yml` use `cargo-target-gc`; `keycloak-smoke.yml` and
          `ui-tests-matrix.yml` use `docker-host-gc`), and the fork's file maintains only active
          workflows.
        - **`Cargo.lock`** merged without a conflict and resolves with `--locked`; it differs from
          upstream's only by the Cassandra driver (`cdrs-tokio` 10.0.0, `cassandra-protocol` 5.0.0,
          and `cdrs-tokio-helpers-derive` 5.1.0 and its five dependencies gone).
    - **The sync's new workflow is archived.** Upstream's `.github/workflows/docker-lint.yml`
      (#2591) is moved to `.github/disabled-workflows/` (ADR-aacruzgon-0022). It would run on this
      very sync's pull request, which changes `Dockerfile`, on GitHub-hosted `ubuntu-latest`, and
      the repository's SHA-pinning setting would fail it at "Set up job" (`actions/checkout@v7`).
    - **The history hook stays fork-only.** #2593 leaves the history interactions to #514, and no
      upstream backend that can be a primary lacks history, so there is no upstream reproduction
      for it. No upstream issue names it (searched on 2026-11-24). It goes upstream only with its
      own issue, if I choose to file one.
    - **#2594 stays separate** (open). It changes how a request for an unserved parameter is
      answered, which the maintainers may want to decide on its own.
    - **Phase 4 is unchanged.** `_list` and `_in` are asked as `_id` of type token and `_has` is
      never asked, so ADR-aacruzgon-0085's type check (`SUPPORTED_PARAM_TYPES.contains`) keeps
      `_list` and `_in` wherever token is served, with no special case.
- **Alternatives considered:**
    - **Lift #105's branch upstream as it stands (phase 5 as planned):** lost.
        - It carries the history hook, which #2593 puts out of scope and which has no upstream
          reproduction.
        - It overrides no backend, so on its own it changes no upstream statement and closes
          nothing.
    - **Hook only, backend answers in a follow-up:** lost. The issue's expected behaviour is the
      backends' answers. Without them the PR would be "Part of #2593" with nothing visible.
    - **One PR with #2594:** lost for now. #2594 changes request handling (`400`/`501` to an
      ignored-and-reported parameter under lenient handling), a behaviour change the maintainers
      may want to decide separately.
    - **A type-level `supports_param_type`:** lost, as in ADR-aacruzgon-0085. It can't express
      `_text` served and `near` refused.
    - **Leave composites with unserved or unresolved components listed, and allow their refusal
      in the test:** lost, after the independent audit (S1). They are refused, or matched on fewer
      components than defined, on every backend, so listing them is #2593's defect. Adding the
      missing component definitions to the registry is #2774.
    - **Count `_list` and `_has` as served in each backend (a shared helper):** lost, after #105's
      audit. REST asks about `_list` and `_in` as the `_id` filter they become, and never asks
      about `_has`, so the backends need no special case.
    - **Cherry-pick `1f6feff10` onto `main` (skipping the empty pick of `e28b5d446`), as
      ADR-aacruzgon-0049 did for #2518:** lost. Upstream had already merged, so there was nothing
      to carry ahead of; a pick would leave the fork 194 commits behind with one of them
      duplicated, and the next sync would have to match it again. The pick was made and checked
      locally (`9921a1d63`: the same hunks as `1f6feff10`) and dropped unpushed.
    - **Resolve the six shared files to the fork's side:** lost. The fork's copies differed from
      upstream's by more than the history hook (`d399c331b`'s comments), which every later sync
      would conflict on again.
    - **Resolve them to upstream's side:** lost. It would drop #105's history hook, which the
      fork's Cassandra statement depends on.
