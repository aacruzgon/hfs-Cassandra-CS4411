# ADR-aacruzgon-0091: A token with a real system and an empty code keeps its `token_system_index` row, and gets no code row (amends ADR-sam-michaels-0006, IW2, and the premise in ADR-aacruzgon-0027, G18/P5)

- **Date:** 2026-11-25
- **Status:** accepted
- **Context:**
    - **The rule being amended.**
        - ADR-sam-michaels-0006 IW2 (`docs/Cassandra/ADR-sam-michaels/2026-11-16/0006-step-5-design.md:188`) says: "`TokenCode` and `TokenSystemCode` rows for every non-empty code; a `TokenSystem` row only for a real system (not IMPLICIT, not `''`); booleans get system `''`. Drop empty codes and empty URIs. Only invalid content makes a row with a system and an empty code (`"code": ""` in a CodeableConcept's coding, `converters.rs:470`); SQLite and PostgreSQL would match it with `system|` (`token.rs:101`), and dropping it is still fine."
        - Decision 9 of the same entry repeats the reason (`:59`).
        - ADR-aacruzgon-0027 G18/P5 (`docs/Cassandra/ADR-aacruzgon/2026-11-05/0027-step-1-open-items-decided.md:68`) records as a given: "It skips a Coding without a code and an Identifier without a value (`converters.rs:444-445`, `502`)".
        - The code is `index_keys_from` (`crates/persistence/src/backends/cassandra/index_keys.rs:449-451`): `if code.is_empty() { continue; }`, before any key is made.
    - **What the spec says.** Neither entry cites the token form that decides this. 0027 cites R4 #token only for the pipe rule on ContactPoint and boolean (`:298`).
        - R4, https://hl7.org/fhir/R4/search.html#token: "[parameter]=[system]| : any element where the value of [system] matches the system property of the Identifier or Coding". It defines the form; it is not a SHALL. R4 https://hl7.org/fhir/R4/datatypes.html#Identifier has `system` 0..1 and `value` 0..1, with no invariant; #Coding has `code` 0..1.
        - R4B, https://hl7.org/fhir/R4B/search.html#token: the same sentence. https://hl7.org/fhir/R4B/datatypes.html#Identifier has the same cardinalities.
        - R5, https://hl7.org/fhir/R5/search.html#token: the same sentence. https://hl7.org/fhir/R5/datatypes.html#Identifier has `value` 0..1 with `ident-1`, a **warning**: "Identifier with no value has limited utility. If communicating that an identifier value has been suppressed or missing, the value element SHOULD be present with an extension indicating the missing semantic". A warning does not make the resource invalid.
        - So valid content, an Identifier with a system and no value or a Coding with a system and no code, is a match for `[system]|`. IW2's "only invalid content" holds for what today's shared converter emits, but not for the content itself.
    - **What was observed** (base `2ae41258e`; the `validate-108-findings` run, `evidence/`):
        - `Patient.identifier = [{"system": "http://hospital.example/mrn"}]` is missed by `Patient?identifier=http://hospital.example/mrn|`. The control, with value `123`, matches. This is on SQLite through REST (R4, R4B, R5; `evidence/sqlite/<V>/summary.txt`), and as Cassandra rows on R4, R4B and R5 (`evidence/cassandra/<V>/cql-rows.txt`: no `identifier` row in any token table).
        - The same holds on upstream `main` at `fb7d12ed5` (`evidence/upstream-fb7d12ed5/sqlite/<V>/summary.txt`).
        - There are two causes. The first is in the shared converter, which emits no token for an Identifier with no value (`converters.rs:528-566`) or a Coding with no code (`:493` for a bare Coding, `:509` for a CodeableConcept's coding; `:509` does emit a CodeableConcept coding whose `code` is `""`); that is upstream's to fix (HeliosSoftware/hfs#2965).
        - The second is IW2. With a throwaway converter edit, SQLite found the resource, but Cassandra still wrote no `token_system_index` row for it (`evidence/cassandra-c4-converter-fix/<V>/cql-rows.txt`, R4, R4B, R5). With IW2 also mutated as the rule below says, the row `(identifier, http://hospital.example/mrn, p-sysonly, code '')` appeared, and no code row did (`evidence/cassandra-c4-iw2-fix/<V>/cql-rows.txt`; `evidence/throwaway-c4-iw2.diff`). Both edits were reverted.
- **Decision:**
    - A token value with an empty code and a real system (not `IMPLICIT`, not `''`) gets its `TokenSystem` key, with `code ''`, and no `TokenCode` or `TokenSystemCode` key. No `code`, `system|code` or `|code` form can match an empty code, so those rows would never be read.
    - A token with an empty code and no real system is still dropped, as P5 says (display-only text).
    - Every other IW2 and P5 drop stays.
    - The code change is in `index_keys_from` (`index_keys.rs:450-468`, PR #117): when `code` is empty, insert `IndexKey::TokenSystem { param, system, code }` if the system is real, then `continue`.
    - It lands in its own Cassandra pull request.
    - Values reach it only once the shared converter emits them (HeliosSoftware/hfs#2965). Until then it changes no write made through REST. Every REST write path removes an empty `code` before extraction (`drop_empty_elements`, HeliosSoftware/hfs#2554, in the fork since the sync of 2026-11-18; `crates/rest/src/validation.rs:212-214`, `crates/persistence/src/core/patch.rs:157`). The one exception, `$meta-add`, adds only bare Codings to `meta.tag` and `meta.security`, and the converter skips those when their code is empty (`converters.rs:500`). Only a direct caller of the storage API can pass an empty code: a CodeableConcept coding with `"code": ""` (`converters.rs:509`), or a ContactPoint with system `phone` or `email` and `"value": ""` (`converters.rs:569-580`; on a Patient it gets two keys, `phone` and `telecom`). Each then gets its `TokenSystem` key, which the pipe form on ContactPoint that ADR-aacruzgon-0027 C4 serves (`telecom=phone|`) reads, as SQLite's `value_token_system = ?` does.
- **Alternatives considered:**
    - **Keep IW2's drop.** Lost: once the converter is fixed, every backend but Cassandra would answer `system|` for these resources, and the drop rests on a premise the spec does not support.
    - **Write all three token rows for an empty code.** Lost: no query form reads a code row with an empty code, so they are dead rows and tombstones.
    - **Wait for the upstream converter fix and do nothing here.** Lost: the drop would then hide the fixed values on Cassandra alone.
- **Consequences:**
    - `system|` on Cassandra will match what SQLite, PostgreSQL and MongoDB match, once the converter change is in.
    - Rows: one `token_system_index` row per such value, which is rare.
    - **Tests it needs** (in the same pull request):
        - `token_forms_map_to_the_three_tables` (`index_keys.rs:954`) pins IW2. Its input has `token("code", Some("http://loinc.org"), "")` and it expects 15 keys. It must expect the new `TokenSystem { param: "code", system: "http://loinc.org", code: "" }` (16 keys).
        - A new unit test: a real system with an empty code gives exactly one `TokenSystem` key; the `IMPLICIT` marker or `''` with an empty code gives none.
        - A REST-level test once Step 6 serves `system|`.
    - Rows written before the change are not rewritten. Since the converter emits no such value yet, and REST removes an empty `code` before storing (HeliosSoftware/hfs#2554), there are none to fix, except a resource stored with `"code": ""`, or a ContactPoint with `"value": ""`, before the sync of 2026-11-18 or through the storage API, which a reload or its next REST write cleans (`crates/persistence/README.md`, "Keyspaces written before index writes").
    - **What PR #117's tests cover:** a CodeableConcept coding with a system and `"code": ""`, through the storage API, in the node tests `a_system_with_an_empty_code_keeps_its_system_row` and `an_empty_code_beside_a_real_code_of_its_system_shares_its_partition` (`write.rs`); and `index_keys_from` called directly on a synthetic Identifier token with a system and an empty value, in the unit test `an_empty_code_keeps_only_a_real_systems_row` (`index_keys.rs`).
    - **Not tested end to end:** a Coding or Identifier with a system and no `code` or `value` key. It cannot reach `index_keys_from` until HeliosSoftware/hfs#2965 fixes the shared converter.
        - That converter half was observed on SQLite through REST, in R4, R4B and R5 (`validate-116-findings`, D1): `code=http://loinc.org|` misses a coding stored as `{"system": "http://loinc.org"}`.
        - That was one independent run, not confirmed by a second.
