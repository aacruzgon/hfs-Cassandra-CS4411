# ADR-aacruzgon-0096: A full repair also deletes the older versions' `resources_by_type` rows, at each found row's `last_updated` and at each version's read from `resource_versions` (amends ADR-sam-michaels-0006 RV1 and ADR-aacruzgon-0017)

- **Date:** 2026-11-26
- **Status:** accepted (Alan confirmed the entry on 2026-11-26)
- **Context:**
    - **The rule as written.**
        - ADR-sam-michaels-0006 RV1 (`0006-step-5-design.md:233`): "Re-run step 5 for the current version through the shared writer (insert all of K(current), delete the stale rows found), as ADR-aacruzgon-0017 says."
        - ADR-aacruzgon-0017, this log: "A key the current version does produce is upserted with the current tag, never deleted", and "Repair writes exactly what the writer would."
        - The code followed RV1: in `plan_from`, a full plan's `next` is K(current) whole, and `previous` held only the found rows.
    - **The rule it breaks.** The design's step 5 (`cassandra-discussion.md:273`): "**All the rows of one partition, its inserts and its deletes, travel in one batch and are never split**, so once the batch has reached a quorum a reader never sees both of an updated resource's `resources_by_type` rows." The writer for version V deletes V−1's type row at `lu(V−1)` in the same batch as it inserts V's at `lu(V)`. A full repair inserted V's type row, but deleted V−1's only if the search happened to find that row.
    - **How it shows (CodeRabbit on PR #106, thread `PRRT_kwDOVAIJX868UFkt`, D1).** A Patient goes from `gender` male to female, and the update stops after its version row. A `gender=male` search finds the stale token row, not the type row. The full repair inserts the version 2 type row, and the version 1 type row stays. `count` now sees the resource twice, on one node.
    - **Evidence, L1, on a 5.0.9 single node.**
        - On PR #106 at `0b3af4577` (`validate-106-findings`, `report-coderabbit.md` D1): with only the version 1 `gender` row queued, `Repaired { full: true, rows_inserted 5, rows_deleted 1 }`, and `count(Patient)` went **1 → 2**. The control, with the version 1 type row queued, kept `count` at 1.
        - On this branch, `a_full_repair_from_a_token_row_moves_the_type_row_and_count_stays` with the rule removed fails on `count` **2 against 1**.
        - **Not shown:** the REST effect, since Cassandra search answers 501 until Step 6, and RF 3.
    - **The specs.**
        - **FHIR.** `Bundle.total` is 0..1 in R4, R4B and R5: "If a set of search matches, this is the total number of entries of type 'match' across all pages in the search" (R4 and R4B `bundle-definitions.html`); R5 adds "(potentially estimated)". `_total=accurate` asks for "an exact total of the number of matching resources" (R4, R4B and R5 `search.html`). R5 `search.html` (3.2.1.3.4) also says "entries are unique (not allowed to repeat)". So no SHALL is broken today, since Cassandra search answers 501 and `count` is internal, but a type row counted twice is a wrong total, and a resource found twice through two type rows would repeat an entry. The rule makes repair agree with the spec, not depart from it.
        - **Cassandra.** `resources_by_type` is keyed `((tenant_id, resource_type), last_updated, id)` (`schema.cql:233`), so the insert and the new delete share one partition and travel in one single-partition batch, which is "isolated only within a single partition" (`cassandra-discussion.md:341`), as step 5 requires.
        - **The design documents.** `cassandra-discussion.md:273` (above) and `:360`; `development-roadmap.md:441` and row 5.3; `schema/walkthrough.md`, 5.1 step 4. `crates/persistence/README.md`'s capability matrix lists Cassandra search as not yet served, and Discussion #28 (HeliosSoftware/hfs) fixes no repair rule; neither conflicts.
    - **ADR-sam-michaels-0008** (Step 5's implementation choices, on #109's branch `cassandra/step5-crash-tests`, not yet on `main`). Its pull request 7 item 1 sets the partial plan's rule ("A found row whose key K(current) still produces moves to `lu(R1)`"), and its alternatives reject "Partial repair, always keep `ResourcesByType`" because "it writes a second type row when only a token row was found". This entry applies the same concern to the full plan, which writes the type row always: it keeps the insert and adds the matching delete. It changes no item of 0008, and the partial rule stays as 0008 sets it.
    - **Why it is a decision.** It changes what a repair writes, a write-path change, and it deviates from RV1 as written. RV1 is in Sam's log, which only Sam edits (CLAUDE.md, "Decision records"). Alan co-authored PR #106, so the amendment is recorded here.
- **Decision:**
    - **What a full plan writes.** A full repair plan (at most 64 keys in K(current)) still inserts all of K(current) at `lu(R1)`. It also deletes the `resources_by_type` row each older version may have left, each `last_updated` once:
        - at the `last_updated` of each found row that has one;
        - at the `last_updated` of each version from `MAX_TYPE_ROW_VERSIONS` (8) below R1, or version 1, up to R1, whatever the found tags, read from `resource_versions`.
    - **The read.** It is ADR-aacruzgon-0097's version read, widened to one single-partition range read at `LOCAL_QUORUM`: `SELECT version_id, last_updated FROM resource_versions WHERE tenant_id = ? AND resource_type = ? AND id = ? AND version_id >= ? AND version_id <= ?`, from the lower bound above up to R1's version. R1's row must be in it (0097). A partial plan reads only R1's row.
    - **Which versions add a delete.** A version whose tag a found row with a `last_updated` carries adds none, since an index row tagged V is always at `lu(V)`, so that row already names V's type row. The others add one each: a found date row, whose key has no `last_updated` (the audit's G1), names none; a version between the found tag and R1 is named by no found row (G2); and neither is one below the lowest found tag (the re-audit's H1: version 2's token batch applied and its type batch didn't, so version 1's type row stays, and a search finds only version 2's token row).
    - **The budget.** Admission reserves one delete for each such version, so the 512-row budget bounds what the repair writes, whatever the read returns.
    - **Beyond the cap.** A full repair deletes the type rows of the versions it reads, from 8 below R1 up to R1. A type row that an unfinished type-row batch left more than 8 versions below R1 stays: one failed type-row batch of version V+1 leaves V's row, and later writes that finish move only their own predecessor's row, never V's. It stays until the sweeper replays version V+1's intent, or until a search that finds that row repairs it, since its found `last_updated` names it. The write whose type-row batch failed kept its intent (the request path keeps it when the index step fails), and the sweeper's replay of V+1 deletes V's type row (SW11; ADR-aacruzgon-0094 for a superseded replay). Until then, or if that intent expired after 24 h, `count` reads one too many for that resource, the same exposure as a resurrected type row (`cassandra-discussion.md:370`).
    - **Why it is safe.**
        - Every deleted `last_updated` is a version below R1's, or a found row's, which is tagged below R1. So the type row there belongs to an older version. If it exists it is stale; if it doesn't, the delete is a tombstone.
        - `index_delta` compares rows by row identity (IW7). So a found `last_updated` equal to R1's is upserted, not deleted, and the tie that ADR-aacruzgon-0017 guards against cannot arise.
        - The insert and the deletes share the `(tenant, type)` partition, so they travel in one batch at R1's timestamp, as step 5 requires. That timestamp is above every older version's, so each delete wins over the row it names.
    - **Partial plans** (more than 64 keys) are unchanged. They write no type row unless one was found, so they never add one.
    - **The new RV1 text:** "Re-run step 5 for the current version through the shared writer: insert all of K(current), delete the stale rows found, and, in a full repair, delete the `resources_by_type` row at each found row's `last_updated` and at the `last_updated` of each version from 8 below R1 (or version 1) up to R1, read from `resource_versions` (ADR-aacruzgon-0096)."
- **Alternatives considered:**
    - **Write the type row only when the old type row was found (CodeRabbit's rule):** lost.
        - It fixes the case: `count` 1 → 1, and the version 1 type row stays at tag 1 for the sweeper or a type search's repair.
        - But a full repair then no longer restores a missing type row: after an unfinished revive found through a resurrected token row, `count` stays 0 until the sweeper.
        - Measured on `0b3af4577`, 4 tests failed as written, against 2 for the chosen rule.
    - **Keep RV1 as written:** lost. `count` is wrong after a repair that a search triggered, and the design's step 5 invariant fails on one node.
    - **Only the found rows' `last_updated` (this entry's first rule, as Alan confirmed it):** lost after the independent audit of #124. It misses a repair started only from date rows (G1: `count` 1 → 2, type rows tagged `[2, 1]`), and an older type row at a `last_updated` no found row has (G2, after two unfinished writes: `count` 1 → 2, `[3, 2]`). A date search's found set is only date rows, so every repair it starts was G1's case.
    - **A range from the lowest found tag (this entry's second rule):** lost after the re-audit of #124 (H1). A type row below the lowest found tag was never read: after version 2's token batch applied and its type batch didn't, and version 3 crashed, a repair from version 2's token row turned `count` 1 into 2 (type rows `[3, 1]`).
    - **Read the type rows at those times first, and delete only the ones present** (`(last_updated, id) IN (…)` on `resources_by_type`): lost. It would add no tombstone, but it costs a second read per repair, in the type partition that `count` and every type search read.
    - **An uncapped range:** lost. The read and the reserved deletes would grow with the resource's history (a resource with thousands of versions and one stale row of version 1). With the cap, the read is at most 9 rows and the reservation at most 8 deletes.
    - **A second read only when needed** (for date-only found sets): lost. The range read replaces 0097's point read, so it costs no extra statement in any case.
    - **Leave the type row to the sweeper in every repair:** lost. It is CodeRabbit's rule plus giving up the found-type-row move, which is the case `repair_heals_a_crashed_update_at_the_first_search` pins.
- **Consequences:**
    - **Built** in `fix(cassandra): a full repair also deletes the type row at each found row's last_updated` and widened in `fix(cassandra): a full repair finds the old type rows from a range read of resource_versions`, on `fix/cassandra-repair-type-and-version-rows`:
        - the case gives `Repaired { full: true, rows_inserted 5, rows_deleted 2 }`, with `count` 1 → 1 and one type row, at tag 2; the control gives `rows_deleted 1` and the same type row;
        - the new tests: `a_full_repair_from_a_token_row_deletes_the_old_type_row`, `a_found_row_at_r1s_last_updated_never_deletes_the_current_type_row`, `a_partial_repair_from_a_token_row_writes_no_type_row` (pure) and `a_full_repair_from_a_token_row_moves_the_type_row_and_count_stays` (node, with its control). With the rule removed, those that test it fail, and the limit tests pass.
    - **The audit's cases, built** (5.0.9 single node):
        - `a_full_repair_from_a_date_row_only_moves_the_type_row`: only version 1's date row found, `count` 1 and type rows `[2]`; on the found-rows rule, `count` 2 and `[2, 1]`. Its control also finds version 1's `gender` row.
        - `a_full_repair_deletes_a_type_row_no_found_row_names`: version 2's type batch applied and its token batch not, version 3 crashed after its version row, version 1's `gender` row found: `count` 1 and `[3]`; on the found-rows rule, `count` 2 and `[3, 2]`. Its control finds version 2's type row itself.
        - `a_full_repair_deletes_a_type_row_below_the_lowest_found_tag` (the re-audit's H1): version 2's token batch applied and its type batch not, version 3 crashed after its version row, version 2's `gender` row found (tag 2): `count` 1 and `[3]`; with the range from the lowest found tag, `count` 2 and `[3, 1]`. Its control also finds the type search's rows.
        - `a_full_plan_reads_back_eight_versions_and_reserves_the_unnamed_ones` and `the_version_read_reaches_back_at_most_the_cap` (pure) pin the range and the cap; the cap test fails with the cap removed.
        - `the_reserved_type_row_deletes_decide_whether_a_repair_fits` (pure): a repair whose delta fits the 512 rows but whose reserved deletes do not is skipped as `Budget`; with the reservation not counted, it fails.
    - **Tests changed.** Two pure tests plan from made-up token rows at `lu(1)`, so under RV1 each full plan was one insert plus its found rows: `a_repair_over_the_row_limit_is_skipped_and_a_later_smaller_one_is_admitted` and `once_32_repairs_are_admitted_later_entries_still_run_the_checks_before_budget`. Each plan now also deletes the type row at `lu(1)`, so the fixtures are resized to keep each repair where it meant to land against the 512-row limit: the sizes became `[501, Budget, 3, Budget, 8, Budget]` and 32 × 3.
    - **More tests changed by the range read.** `repair_retags_a_date_row_the_current_version_still_produces` found a date row tagged 1, so on the found-rows rule its repair deleted nothing; it now deletes the type row at version 1's `last_updated`, a tombstone, since the update had moved it, and expects `rows_deleted` 1. The two resized budget tests are unchanged by the range read: their found token rows name version 1, the only version below R1.
    - **Cost:**
        - no extra statement: the range read replaces 0097's point read, one per admitted repair, at most 32 per search, 4 in flight, inside the phase deadline; it returns at most 9 rows, from one partition of `resource_versions`, which holds no tombstones (G39);
        - at most one more delete per distinct found `last_updated`, plus at most 8 for the versions read, each reserved in the 512-row budget. The reservations also fill that budget sooner: up to 8 rows per full repair, so up to 256 of a search's 512 rows across its 32 repairs, which means fewer repairs fit in one search for resources with long histories; a repair skipped as `Budget` is repaired at a later search (`the_reserved_type_row_deletes_decide_whether_a_repair_fits` pins the admission);
        - **tombstones.** Most of those deletes find no row, since a finished write already moved its predecessor's type row, so each is a tombstone. The worst case is 8 per repair and 32 × 8 = 256 per search, in one `(tenant, type)` partition. That is below `tombstone_warn_threshold` (1,000) and far below `tombstone_failure_threshold` (100,000) (`cassandra-discussion.md:370`), and they are purged after `resources_by_type`'s 3 h `gc_grace_seconds` (ADR-aacruzgon-0009). Every update already leaves one type-row tombstone, and `count` and the type scans read through them, as through these (G8).
    - **Also fixed by the same rule, not measured:** the unfinished-revive case (`count` 0 → 1), and ADR-aacruzgon-0081's multi-version case (versions 1, 3 and 5 left by unfinished 2 and 4), where the range from a found row of version 1 or 3 deletes those versions' stranded type rows. Both follow from the same code path.
