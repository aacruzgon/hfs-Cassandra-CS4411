# ADR-aacruzgon-0099: A SearchParameter follow is stamped before its read, and a reload that began after the stamp wins over it (amends ADR-sam-michaels-0006 SW19 and ADR-aacruzgon-0068)

- **Date:** 2026-11-26
- **Status:** proposed
- **Context:**
    - **The overlay and the follow.** Each instance keeps, per tenant, the stored SearchParameters it serves (ADR-aacruzgon-0041, 0062). The TTL refresh (`HFS_SEARCH_PARAM_CACHE_TTL`) reloads them: it lists the tenant's ids from `resources_by_type` (`stored_search_parameter_ids`, `backend.rs`) and reads each one. Between reloads, `follow_stored_search_parameter` makes an id's entry follow a row read from `resources`. It is called by the sweeper after it replays a SearchParameter intent (ADR-sam-michaels-0006 SW19: "After replaying a SearchParameter, call `follow_stored_search_parameter` with the row it read", `0006-step-5-design.md:221`), and by the writes of ADR-aacruzgon-0068 (the serial read-back after an unknown outcome, the delete's catch-up on R1, and its catch-up after a missed C3).
    - **The gap (#107 V1, and CodeRabbit's C7).** A follow applies a row read earlier, and a reload can complete between that read and the follow. A delete removes the id's `resources_by_type` row, so a reload after the delete does not list the id, reads nothing for it, and records no removal; `merge_reload` drops A's old definition without trace. The follow then puts the row it read before the delete back in force, until the next reload. It also happens for an id the instance never held, as when its sweeper finishes another instance's create. `22a75941d` (on #107) closed the retirement case, because a retired row is still listed and read and becomes a removal, and narrowed `merge_reload`'s doc to say the delete case is open.
    - **Evidence.** The validator `validate-107-findings` reproduced it at L1 with two backends on one node at `f0d890bf1`, `8569c663b` and Sam's `7cd433265`: after B deletes and A reloads, A's stale follow is "back in force" (A held it) or "in force" (A never held it), and the retirement control is out (`runs/validate-107-findings/report-v.md` §1.1; CodeRabbit's C7 is the same mechanism, `report-coderabbit.md` §C7). This session reproduced it again on `origin/main` (`04c2db43a`), as the new node tests run against the unguarded code (below).
    - **The recommendation** (the validator's fix (c), approved by Alan on 2026-11-26 as long as it follows the specs): "a follow whose row was read before the tenant's last reload began changes nothing."
    - **Two gaps in it, found while checking it against every caller.**
        - **A reload in flight.** The guard as written checks only a reload that has already merged. With a reload that began after the read but merges after the follow, the follow is noted after the reload's `since`, and `merge_reload` keeps every definition noted after `since`, so the deleted definition stays. That order is as likely as the other: both windows are a reload's length against an intent's.
        - **SW19's own case.** The sweeper reads the row (R1), replays the index rows, then follows. A reload that begins during the replay can scan `resources_by_type` before the replay writes the id's row, so it does not list a SearchParameter whose request's index write failed. That is the case SW19 exists for (`cassandra-discussion.md`, the registry paragraph: "a SearchParameter whose `resources_by_type` row failed after its compare-and-swap is missing from every reload until the sweeper replays the intent"). The guard, keyed to R1, would then skip the follow, so the definition stays out until the next reload.
    - **What the spec says.** FHIR leaves the server's use of stored SearchParameters to the server; what it does say points the same way as the fix:
        - **Delete, R4** (`http.html#delete`): "subsequent non-version specific reads of a resource return a `410` HTTP status code" and "the resource is no longer found through search interactions" (descriptive). **R4B** (`http.html#delete`): the same two sentences. **R5** (`http.html#delete`): "A delete interaction means that the resource can no longer found through a search interaction", and 410 only "when the server wishes to indicate that the resource is deleted" (descriptive).
        - **Status, R4, R4B and R5** (`valueset-publication-status.html#expansion`, the same wording in each): `retired`, "This resource has been withdrawn or superseded and should no longer be used"; `active`, "This resource is ready for normal use" (descriptive). `SearchParameter.status` is bound Required ("SHALL be from the specified value set", `searchparameter.html#resource`).
        - **Server-defined parameters, R4 and R4B** (`search.html#parameters`): "Servers are not required to implement any of the standard search parameters … Servers may also define their own parameters" (descriptive, permissive). **R5** (`search.html`): "Servers SHALL declare what features of search they require through their CapabilityStatement search declarations"; I did not read R5's sentence on server-defined parameters verbatim.
        - **So:** no version has a SHALL about how fast a stored SearchParameter's delete or retirement takes effect on another instance. A deleted or retired definition staying in force contradicts the descriptive meaning of `retired` and of a delete, and the design's own rule that the overlay is current on every write. Nothing in the spec argues for keeping the stale definition.
    - **What the other backends do.** No other backend has a follow, so none has this gap. SQLite builds a tenant's registry from `SELECT data FROM resources WHERE resource_type = 'SearchParameter' AND tenant_id = ?1 AND is_deleted = 0` (`sqlite/backend.rs:26-27`), and a delete invalidates the cached registry (`sqlite/storage.rs:1886-1889`). PostgreSQL reloads its whole stored cache from `is_deleted = FALSE` rows on every SearchParameter delete (`postgres/storage.rs:2903-2908`, `reload_stored_cache`, `postgres/backend.rs:1383`), and sees another process's writes by a fingerprint probe within `HFS_PG_SP_FINGERPRINT_TTL_MS` (`crates/persistence/README.md`, under PostgreSQL). In both, a definition read before a delete never outlives the next load of the table. That is the property this entry gives Cassandra's follow.
    - **Why it is a decision.** It changes SW19, in Sam's log, and adds a statement to the sweeper's SearchParameter path, and it amends the follow of ADR-aacruzgon-0068.
- **Decision:**
    - **The stamp.** Each caller takes `search_parameter_read_stamp()`, a fresh `note_seq` value, **before** it reads the row it will follow, and passes it to `follow_stored_search_parameter`. A definition the follow puts in is noted at the stamp, not at the put.
    - **A reload that began after the stamp wins, in both orders.**
        - **The reload merges after the follow:** the follow's definition is noted at or below the reload's `since`, so `merge_reload` drops it, as it drops any definition the reload did not read and that was noted before it began.
        - **The reload merged before the follow:** each overlay keeps `reloaded_since`, the latest `since` merged into it, and `TenantOverlay::put` refuses a definition noted at or below it.
        - An overlay that holds nothing but `reloaded_since` is kept, so the rule also covers a tenant whose SearchParameters are all gone, and an id the instance never held.
        - This process's own writes are noted under the overlay's lock when they are put, so they are always above any merged `since`, and nothing changes for them.
        - A removal needs no stamp: it is ordered against every version of its id by `last_updated` (`Removal::at`).
    - **The sweeper reads the row again for the follow (SW19 amended).** After a SearchParameter intent's replay, the sweeper takes the stamp, reads the row again at `LOCAL_QUORUM` (`read_row`, `StatementKind::Read`), and follows that read, not R1's row. The stamp is then later than the replay's `resources_by_type` write. So any reload that began after it lists the id and reads the row itself, and SW19's case keeps working. If the read fails, the intent is kept and replayed on its next try, which is idempotent, and it is logged and counted as R1's failure is. SW19 now reads: "After replaying a SearchParameter, read its row again at `LOCAL_QUORUM` and call `follow_stored_search_parameter` with that row, stamped before the read (ADR-aacruzgon-0099)."
    - **The write paths of ADR-aacruzgon-0068** take the stamp before their read: `settle_overlay_after_unknown` before its `LOCAL_SERIAL` read, `catch_up_with_a_deleted_miss` before its R1, and the delete loop before its pre-read. Their reads are already just before the follow, so nothing else changes.
    - **One fix closes both V1 and C7.** C7, the retirement, was already closed by `22a75941d`'s removals, and the stamp holds it too. V1's deleted and never-held cases close only with the stamp.
- **Alternatives considered:**
    - **The recommendation as written** (skip a follow whose read is older than the last merged reload): not taken alone. It leaves the in-flight order open, and keyed to R1 it would lose SW19's own case (Context). This entry keeps its rule, a reload that began after the read wins, and applies it in both orders.
    - **(a) A reload also reads every id the overlay holds that the scan did not list:** lost. It closes the deleted case for an id the instance held, but not for an id it never held (the validator's `delete-unheld` row), nor a follow that lands while the reload runs. It costs a read per such id on every reload.
    - **(b) Leave the hole and narrow the texts:** what #107 merged with (`merge_reload`'s doc on `04c2db43a`). It leaves a deleted SearchParameter in force on another instance for a further TTL interval.
    - **Keep SW19's R1 row, stamped before R1, and accept the narrower loss:** not taken. It saves one read per replayed SearchParameter intent, a path that runs only for a crashed or failed SearchParameter write. In exchange, a definition the replay has just indexed would stay out until the next reload, whenever a reload's scan falls inside the replay.
    - **Re-read only when a reload overlapped:** not taken. It saves that same read in the common case, but needs a second record of reloads in flight, and still leaves a window between the check and the put. Always re-reading has one rule and no extra state.
- **Consequences:**
    - **What it guarantees.** On one instance, a row read before a reload of its tenant began never overrides that reload, deleted ids included. A SearchParameter deleted or retired on another instance is out of this instance's registry from its first reload after the change, and stays out, whatever replays or catch-ups were in flight.
    - **What it leaves.** A follow whose read began after the reload began, of a row changed by another instance between that read and the reload's scan, is still a race between two readers. The window is the time from the reload's `note_seq` load to its scan, not a reload's length. The overlay then holds whichever read is newer by `last_updated`, or the follow's live row until the next reload, as any concurrent change would. ADR-aacruzgon-0068's limits (a proposal still running after the serial read, a read-back that fails) are unchanged.
    - **Cost.** One `LOCAL_QUORUM` read of `resources` per replayed SearchParameter intent; one atomic increment per follow; one `u64` per tenant overlay, which an overlay with nothing else now keeps.
    - **Tests** (on `fix/cassandra-searchparameter-stale-follow`):
        - **Node tests, two backends on one node:** `a_stale_replay_read_does_not_bring_back_a_deleted_searchparameter` and `a_stale_replay_read_does_not_put_in_a_searchparameter_deleted_elsewhere` are new. `a_stale_replay_read_does_not_bring_back_a_retired_searchparameter` now runs through the same helper. Each pairs the stale read with a fresh read as the control. The first two fail with the stamp ignored, which is `origin/main`'s behaviour; the retirement passes both ways.
        - **Pure test:** `a_follow_of_a_read_older_than_a_reload_loses_to_it`, for both orders, with controls.
        - **SW19's case:** `a_searchparameter_replay_puts_it_back_in_the_overlay_and_the_reload` still passes through the re-read.
