# ADR-aacruzgon-0100: Startup refuses a request timeout that is not longer than the connect timeout

- **Date:** 2026-11-26
- **Status:** proposed
- **Context:** `CassandraConfig::validate` (`crates/persistence/src/backends/cassandra/config.rs`) checked only that `HFS_CASSANDRA_CONNECT_TIMEOUT_MS` and `HFS_CASSANDRA_REQUEST_TIMEOUT_MS` are each at least 1 ms; nothing related the two (ADR-aacruzgon-0031 set them as independent settings, 5,000 ms and 10,000 ms). The audit of PR #107's branch found that gap (`pr107-branch-audit`, A9), and `validate-107-findings` confirmed it at L1 on base `5bcbf093756d3c20ca1b6a4104931e3f1fa80689`:
    - `cdrs-tokio` 10.0.0 wraps every connection attempt in `tokio::time::timeout(connect_timeout, …)` (`cluster/connection_pool.rs:39-61`), and the backend gives the pool the whole `HFS_CASSANDRA_CONNECT_TIMEOUT_MS` (`session.rs`, `session_builder`, `.with_connect_timeout`). So one attempt to a node that does not answer waits up to the connect timeout.
    - A statement reaches that attempt through the driver's send loop, which takes each node of the query plan's connection in turn and moves to the next node on an error (`cluster/send_envelope.rs:44-70`); taking it opens the node's connection pool (`cluster/topology/node.rs:279-303`), whose connections are each opened under the connect timeout (`cluster/connection_pool.rs:645-678`, `new_connection` at `:659-665`). The control connection's attempts (`connection_pool.rs:223-237`) are ADR-aacruzgon-0044's case, not this one. A statement waits on the connect timeout only while the node's pool is being opened, at startup or for a node new to the driver. The pool is opened once per node and per driver session, in a `OnceCell` (`node.rs:279-292`, `get_or_try_init`). It is kept even when every attempt failed (`connection_pool.rs:670-700`). Every statement that reaches the node during the opening waits for it, not only the first: tokio 1.54.1's `get_or_try_init` "will wait for that other task to finish" (`sync/once_cell.rs:390-392`). An opening that is cancelled is not kept: "If the provided operation returns an error, is cancelled or panics, the initialization attempt is cancelled", and a waiting task starts another (`:394-397`). HFS's `within` (`session.rs`) drops the statement's future at the request deadline, which cancels the opening with it. So with the request timeout at or below the connect timeout, each statement can start the opening again and wait again. With the request timeout longer, as this entry requires, one attempt cannot use up the deadline. Once the pool is open, a node whose connections are all broken answers "No active connections" at once, and the pool refills in the background. The measurement below started a new driver session for each run, so it does not test the once-per-node behaviour; why runs started more than about 10 s after the stop passed is still unexplained.
    - Every statement runs under the request timeout (`session.rs`, `request_timeout`, `within` → `DriverError::Deadline`), and `connect` itself runs two statements under it (`backend.rs`, `verify_local_dc`).
    - With the request timeout at or below the connect timeout, one such attempt inside a statement can use up the statement's whole deadline before the driver tries another node. On three 5.0.9 nodes on `acruzdebian` with one stopped (2026-11-25, `validate-107-findings` V2), `CassandraBackend::connect` with both at 5,000 ms failed 4 of 5 times when started within about 10 s of the stop ("local data centre check exceeded the backend's request deadline of 5000 ms"); with a 2,000 ms connect timeout it passed 34 of 34.

  The README's and the book's `HFS_CASSANDRA_CONNECT_TIMEOUT_MS` rows already said "Keep it below `HFS_CASSANDRA_REQUEST_TIMEOUT_MS`" and "Nothing checks this at startup yet". Refusing to start is a change to config validation and failure handling, so it is a decision (CLAUDE.md, "Decision records"). Neither source that could decide it speaks to it: HL7 FHIR's http.html (R4, R4B and R5 alike) says nothing about a server's backend timeouts, its startup or its configuration; Cassandra 5.0's `cassandra.yaml` defines only server-side request timeouts and no client connect timeout. The rule comes from the driver's behaviour and from the measurement above.
- **Decision:** `validate` refuses `request_timeout_ms <= connect_timeout_ms`, so `hfs` (through `CassandraConfig::from_env`) and `CassandraBackend::connect` fail at startup with `HFS_CASSANDRA_REQUEST_TIMEOUT_MS (<value>) must be longer than HFS_CASSANDRA_CONNECT_TIMEOUT_MS (<value>): one attempt to connect to a node that does not answer waits up to the connect timeout, inside a statement's deadline`. The check is strict (`>`) and has no margin. The defaults (10,000 ms against 5,000 ms) pass, as does every configuration in the repository's tests (2,000 against 10,000, 2,000 against 3,000, 2,000 against 5,000).
- **Alternatives considered:**
    - **Document it only, in the README's `HFS_CASSANDRA_CONNECT_TIMEOUT_MS` row** (`validate-107-findings`' second option). It already was documented, and the plausible setting that causes it, `HFS_CASSANDRA_REQUEST_TIMEOUT_MS=5000` with the default connect timeout, still starts and fails only later, while a node is down. Lost: an invalid value already fails startup for every other `HFS_CASSANDRA_*` setting (ADR-aacruzgon-0031), including the sweeper grace's relation to the request timeout.
    - **Require a margin, for example a request timeout of at least twice the connect timeout,** so a statement always has room for a second connection attempt. The measurement shows equal values failing and 2,000 against 5,000 passing; it does not show where between them the failures stop, and a margin would refuse configurations that have not been shown to fail. Lost for now: revisit with Step 8's failure tests, which can measure it.
    - **Log a warning and start anyway,** as `hfs` does for PostgreSQL's count budget against `HFS_REQUEST_TIMEOUT` (`count_budget_race_warning` in `crates/hfs/src/main.rs`). That warning covers a choice between two status codes (408 or 504), both correct answers; here the failure is the backend failing to start, or a statement failing, while one node of three is down. Lost.
    - **Derive one from the other** (for example a per-attempt connect timeout of the request timeout divided by the number of contact points, as ADR-aacruzgon-0044 lists for Step 8). A larger change to the driver configuration, outside this item. Not taken here; ADR-aacruzgon-0044's open question stays open.
- **Consequences:** An operator who sets `HFS_CASSANDRA_REQUEST_TIMEOUT_MS` to 5,000 ms or less without lowering the connect timeout now gets a startup error naming both variables and values, instead of a backend that may fail to start while a node is down. Raising `HFS_CASSANDRA_CONNECT_TIMEOUT_MS` to 10,000 ms or more alone now fails startup too. Nothing changes for the defaults. The README's and the book's rows now say the check exists. A margin between the two, if Step 8 measures one, would be a new entry.
