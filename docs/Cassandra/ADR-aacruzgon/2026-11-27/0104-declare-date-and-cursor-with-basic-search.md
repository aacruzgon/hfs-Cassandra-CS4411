# ADR-aacruzgon-0104: `DateSearch` and `CursorPagination` are declared with `BasicSearch`, in Step 6's last commit, not at 6b and 6d (amends ADR-aacruzgon-0037)

- **Date:** 2026-11-27
- **Status:** accepted (Alan confirmed the entry on 2026-11-27)
- **Context:**
    - **What 0037 says.** ADR-aacruzgon-0037 declares each Cassandra capability "in the step that implements it". It puts `BasicSearch`, `DateSearch` and `CursorPagination` "at Steps 6a to 6d", and `cassandra-discussion.md:135` says the same. ADR-aacruzgon-0085 then narrowed this for `BasicSearch` alone: it moves to Step 6's last commit, Step 7's phase 4, because `supports_search()` follows it and `/metadata` reads that (`C/search.rs:82`; `crates/rest/src/handlers/capabilities.rs:155`). 0085 says nothing about the other two. Roadmap Step 7 phase 4 (`development-roadmap.md:551`) and Step 6's "Last commit" task (`:502`) name only `BasicSearch`.
    - **Anna's request.** On #128, Anna (anastasiabryz) asked that 6b and 6d declare nothing, and that the phase-4 commit declare all three. Her reasoning is in ADR-anastasiabryz-0003 (draft PR #133, head `6d0ef6d18`). Alan agreed in principle on 2026-11-27, and asked for the request to be checked against the spec, the architecture and the project's documents first. The check is on `main` `29e6b0941`:
    - **The crate's rule.** `crates/persistence/src/core/backend.rs:67-68`: "A capability must never be declared for aspirational, planned, or implemented-but-unwired behavior". #127 ("The order", item 2) merges 6b and 6d each on its own, alongside the framework's engine. So when either merges, `search()` may still answer 501 and not reach its module. Diya's branch `cassandra/step6b-date-search` (`c85ee5080`) adds `C/search/date.rs` and changes no `search()` path. A declaration at 6b or 6d, as 0037 words it, would then break that rule.
    - **What the two variants mean.** `BasicSearch` is documented as "`search` is really implemented, not answering `UnsupportedCapability`" (`core/backend.rs:95-101`). `DateSearch` (date range search) is a property of that same `search()`. No backend declares `DateSearch` without `BasicSearch`: SQLite, PostgreSQL, MongoDB and Elasticsearch declare all three, and S3 declares neither search variant. S3 does declare `CursorPagination` without `BasicSearch` (`backends/s3/backend.rs:124-137`), because it pages history with cursors. Cassandra serves no history (`InstanceHistory` ✗, design scope table), so its only cursor is search's (6d).
    - **What a client sees.** No REST or `hfs` code reads `DateSearch` or `CursorPagination`. `/metadata` reads `supports_search()`, `supports_history()`, `serves_search_param`, `modifiers_for_param_type` and `supports_contained_search()` (`capabilities.rs:147-192`), and none of them is derived from either variant. Date parameters appear in Cassandra's `searchParam` lists through `BasicSearch` and the `serves_search_param` override (`SUPPORTED_PARAM_TYPES`, which includes `Date`), both in phase 4. Under every option below, date search shows in `/metadata` at phase 4 and not before. FHIR has no CapabilityStatement element for paging or cursors in R4, R4B or R5 ([R4 capabilitystatement-definitions](https://hl7.org/fhir/R4/capabilitystatement-definitions.html), [R4B](https://hl7.org/fhir/R4B/capabilitystatement-definitions.html), [R5](https://hl7.org/fhir/R5/capabilitystatement-definitions.html); [R4 http.html#paging](https://hl7.org/fhir/R4/http.html#paging), "Servers SHOULD support paging for the results of a search or history interaction", with the same sentence in R4B and R5). So the spec ("Servers SHALL provide a Capability Statement that specifies which interactions and resources are supported", [R4 http.html](https://hl7.org/fhir/R4/http.html), the same in R4B and R5) doesn't decide when these two are declared. The crate's rule does.
    - **Routing (Anna's point 2).** #128's "Open choices" item 6 says `CompositeStorage`'s analyzer routes by these two, so declaring them changes routing. It doesn't. `composite/analyzer.rs:111` and `:127` map a query feature to a capability. The router then filters `BackendEntry`s by their configured capabilities (`composite/router.rs:353`; `composite/config.rs:197-208`, `:587-594`), explicit or from the role, never by a backend's `declared_capabilities()`. A `Primary` entry already lists both (`composite/config.rs:77-95`). Cassandra is a standalone primary only (`composite/mod.rs:23-25`), and `hfs` builds no composite with it.
    - **The readers are tests only.** These read the two variants: the contract test's `GOLDEN` and `LATER` (`tests/backend_capability_contract.rs:839`, `:849`, and the `LATER` loop at `:933`); `declared_capabilities_are_exactly_those_implemented` (`C/backend.rs:1526`); the harness's `supported_capabilities()`, which is `declared_capabilities()` (`tests/common/cassandra_testable.rs:197-201`); and `cassandra_tests.rs:501-504`. No test gates on them: `require_capability!` (`tests/common/harness.rs:364`) has no caller, and `search/pagination_tests.rs` checks no capability.
- **Decision:** `DateSearch` and `CursorPagination` are declared in the same commit as `BasicSearch`: Step 6's last commit, Step 7's phase 4 (ADR-aacruzgon-0085), made by W (Alan) on Anna's branch. 6b and 6d declare nothing. This amends ADR-aacruzgon-0037 for these two capabilities. 0037's rule, that each capability is declared in the step that implements it, stays. For `search()`, that step is the one that makes it answer.
- **Alternatives considered:**
    - **0037 as written: declare each at 6b and 6d.** Lost. Under #127's order a module can merge before `search()` reaches it, so the declaration would describe implemented-but-unwired behaviour, which `core/backend.rs:67-68` forbids. Upstream added that rule after #369, and our work meant for upstream doesn't weaken it (0037's own reason).
    - **Declare each as soon as `search()` really serves it, before phase 4.** Workable: the rule allows it, and no client sees it. Lost because it leaves `DateSearch` or `CursorPagination` declared while `BasicSearch` is not, and so while `supports_search()` is `false` and `/metadata` says the backend doesn't search. No backend declares `DateSearch` without `BasicSearch`. It also spreads one switch over up to three commits, each touching Sam's `C/backend.rs` and Sara's contract test (#127, file table), before Step 6's gate has passed.
    - **Declare them at phase 4, and also add a contract assertion that `DateSearch` or `CursorPagination` implies `BasicSearch` on Cassandra.** Not decided here. It would pin this decision against a future early declaration. It belongs in Sara's file, and phase 4 can propose it to her.
- **Consequences:**
    - **Easier:** the three search capabilities turn on together, in one commit, when search works end to end. That is also when `/metadata` starts listing date parameters. The phase-4 commit already asks Sam and Sara for `BasicSearch`, so the two others need no extra request.
    - **What phase 4 now also changes:**
        - `declared_capabilities()` (`C/backend.rs:573-580`), its doc comment (`:549-572`, "at Steps 6a to 6d") and its unit test's expected and absent lists (`:1526-1555`), through Sam (5s).
        - In `tests/backend_capability_contract.rs`: `GOLDEN` gains all three; `LATER`, its loop (`:933`) and the doc comments that say "at Steps 6a to 6d" and "when Step 6d empties it" (`:827-829`, `:846-848`) go. That file is Sara's.
        - `tests/common/capabilities.rs`'s Cassandra row: `BasicSearch`, `DateSearch` and `CursorPagination` move from `Planned` to `Implemented` (`:240-241`, `:263`), and its comment (`:225-226`, "Steps 2 to 6d") changes. Also Sara's.
    - **Harder:** until phase 4, a test gated on `DateSearch` or `CursorPagination` through the harness would skip on Cassandra without failing. So 6b's and 6d's copies in `tests/cassandra/` must not gate on either. Their exit rows (`development-roadmap.md:517`, `:519`) are met by tests that run, not by the declaration. Offset cases still skip on `OffsetPagination`, which is never declared (`:610`).
    - **Until phase 4,** the code comments listed above still say "at Steps 6a to 6d", unlike the design and roadmap after this commit. They are in Sam's and Sara's files, so phase 4 changes them rather than this commit.
    - **#128's "Open choices" item 6** is corrected on the issue: declaring the two changes no routing (see Context).
    - **No README change.** The matrix's Cassandra cells for Date and Cursor stay ○ until Step 8 updates the README's Cassandra column (row 8.10 and Step 8's README task, `development-roadmap.md:117`, `:581`). `/metadata` and the README don't read the declaration.
    - **To revisit:** if Cassandra ever becomes a composite primary whose `BackendEntry` capabilities come from `declared_capabilities()`, the declaration starts to affect routing. Nothing builds one today.
