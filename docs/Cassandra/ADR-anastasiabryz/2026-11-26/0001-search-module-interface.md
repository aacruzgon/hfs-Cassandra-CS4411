# ADR-anastasiabryz-0001: The Cassandra search modules implement one `ParamPlan` trait; the framework plans, intersects and counts, and only `paging.rs` touches cursors

- **Date:** 2026-11-26
- **Status:** accepted
- **Context:**
    - Step 6 is split across four people (#127, Alan's split of 2026-11-26): the framework `C/search.rs` and 6d `C/search/paging.rs` are mine (#128, #129), 6a `token.rs` and 6c `uri.rs` are Sara's (#130, #131), and 6b `date.rs` is Diya's (#132). `C/` is `crates/persistence/src/backends/cassandra/`.
    - For the modules to be written in parallel, the contract between them and the framework has to be merged first, in an interface PR that changes no behaviour (#127, "The order", item 1). #128 ("Interface PR") gives a proposal for me to decide.
    - The design fixes what a search does (`docs/Cassandra/schema/walkthrough.md` 5.1: validate, stream in `(last_updated DESC, id DESC)`, collapse, tag check, residuals, stop at `_count + 1`, cap), the driver order (5.8, C5, ADR-aacruzgon-0027) and the cursor (5.7, 5.10), but not how the code is divided between files. That division is a choice between workable designs.
- **Decision:**
    - **Layout.** `C/search.rs` stays the framework file (no rename to `search/mod.rs`) and declares `mod token; mod date; mod uri; mod paging;` in `C/search/`.
    - **One trait per parameter.** Each module turns one `SearchParameter`, with all its comma values, into a `Box<dyn ParamPlan>` through a `compile(&SearchParameter, &CompileCtx)` function. `ParamPlan` has:
        - `param()`, the parameter's name;
        - `drive()`, its rank in C5's order (below);
        - `order()`, the `Order` its stream is in, `Order::Default` unless the plan overrides it; a date plan returns `DateStart`, `DateEnd` or `DateStartThenEnd`. The framework passes it to `decode` and starts the first page with it (#128, item 4: "the plan says which"), and reads it from the driving plan only: a date plan beside a token, or a second date, still returns its date order, which the framework ignores. #128's trait sketch leaves this method out, and `Drive::DateOnly` cannot stand in for it, because it does not say which date table a plan reads;
        - `stream(ctx, from)`, its candidates strictly after `from`, in `from`'s order, already merged across its partitions and OR values and collapsed on the order key, read with `LIMIT` batches through `CassandraSession::rows` (`C/session.rs:506`);
        - `contains(ctx, last_updated, id)`, the clustering point reads at `last_updated = ? AND id = ?` used when another plan drives (walkthrough 5.8);
        - `residual(&LoadedResource, Option<&OrderKey>)`, a check on the tag-checked resource, `true` by default (dates use it). The `OrderKey` is where the candidate sits in the stream's order: `Some` only for the plan that drives the search, `None` for a plan checked beside another driver. Without it, two rows of one resource give a date plan identical inputs, so it could not apply walkthrough 5.7's "first matching row" rule (the design's, ADR-aacruzgon-0027; whether `residual` is where it is enforced is open choice 4, Diya's), on a page, on a resumed page or across `ne`'s two tables. A plain `&OrderKey` would not do: a second date's residual would get the first date's position and drop a real match. `LoadedResource` is the R1 row (`ResourceRow`, `C/read.rs:93`) with the values the framework extracts from it once per candidate, under the resource's own `fhir_version` and the tenant's registry, on the large-stack thread the write path uses in debug builds (`C/index_keys.rs:539`-`:560`); the date and compartment residuals both read that one extraction (#128, item 3).
    - **Shared types in `C/search.rs`.** `FoundRow { key: IndexKey, last_updated: Option<DateTime<Utc>>, version_id: i32 }` (`None` for the two date tables), `Candidate { order, id, rows: Vec<FoundRow> }` (every row of the resource at that order key, for the tag check and repair), and `ReadCtx` (tenant, resource type, session, candidate budget).
    - **Driver rank.** `enum Drive { Id, SystemCode, IdentityUri, Shared, SystemOnly, LastUpdated, DateOnly }`, which is C5's order. The planner takes the lowest rank across the whole query, ties going by query order. A date plan drives only when every parameter is a date or `_lastUpdated` (G20).
    - **Cursors only in `paging.rs`.** `Order { Default, DateStart, DateEnd, DateStartThenEnd }`, `Position { First(Order), After { order, at, id, table } }`, `decode(cursor, expected) -> Result<Position, SearchError>` (`InvalidCursor` on any mismatch) and `mint(last, order)`. No other file encodes or decodes a `PageCursor`.
    - **The cap is counted in the framework only**, at the one place R1 is read for a candidate (a `CandidateBudget` in `ReadCtx`, distinct `(resource_type, id)`; G27). Modules never count, and neither their index reads nor their `contains` point reads are candidates point-read. Over the cap it returns `SearchError::TooManyResults { count, max }` (`crates/persistence/src/error.rs:354`), and the repair phase still runs.
    - **Each module parses its own values**, after `split_unescaped_commas` (`crates/persistence/src/search/value_parser.rs:28`), and applies `index_text` once (ADR-aacruzgon-0079).
    - **Left to the interface PR:** `OrderKey`, `CompileCtx` and `DateTable`, which #128 names but does not define. The interface PR (#133) defines them as `OrderKey { at: DateTime<Utc>, table: Option<DateTable> }` (the instant a candidate is ordered by, and its date table, `None` in the default order), `DateTable { Start, End }` (`date_index` and `date_index_by_end`, the cursor's `"start"` and `"end"`) and `CompileCtx { resource_type, definition: Option<&SearchParameterDefinition> }` (the registered definition, by which a URI plan recognises an identity URI). `mint` returns `StorageResult<String>`, where #128 sketched a plain `String`, so that it can refuse a candidate whose order key does not belong to the requested order.
    - **The interface PR** holds these types and the trait, the four module files with a `compile` that returns `UnsupportedCapability` and a module doc naming its issue, and one compile-only unit test. `search()` still answers 501.
    - **Left to the module owners** (recorded in their logs, and announced on #128 before I merge the interface): where the shared k-way merge lives (proposed: `paging.rs`; Sara has to agree), the rank of a token comma list that mixes forms (Sara), and whether the date plan's `residual` enforces "first matching row" (Diya).
- **Alternatives considered:**
    - **Each module writes its own whole search (`search_token(query) -> SearchResult`), and the framework dispatches by type.** Lost because a search with several types (`code=…&date=…`) needs one driver and point reads into the others' tables (walkthrough 5.8), so each module would need the others' code; and the tag check, cap and repair would be written four times, while G27's cap counts distinct candidates across the whole page, which no single module sees.
    - **Modules return CQL statements and the framework runs them.** Lost because the token forms need one query per partition merged in Rust (walkthrough 5.2: `IN` with `ORDER BY` cannot page on 5.0.9), date `ne` reads two tables one after the other (5.7), and the date residual needs the extracted values. The framework would have to know every module's read shape.
    - **Every module encodes its own cursor.** Lost because a cursor minted by one order must fail as `InvalidCursor` in another (5.7), which needs one place that knows all the orders.
- **Consequences:**
    - Easier: the modules can be written and reviewed in parallel against fixed signatures; the tag check, cap, repair queue and residual extraction exist once.
    - Harder: a change to `ParamPlan` touches four files owned by three people, so it goes through #128 and is announced on every module issue before merging.
    - `stream` returns a boxed stream (`futures::stream::BoxStream`) and `contains` is an `#[async_trait]` method; `async-trait` and `futures` are already dependencies (`crates/persistence/Cargo.toml:54`, `:68`). The box costs one allocation per plan; to be measured in Step 8 if it shows.
    - To revisit if a module finds it cannot meet the contract; that is a request on #128.
