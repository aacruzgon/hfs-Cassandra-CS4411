# ADR-anastasiabryz-0002: The candidate cap is `HFS_CASSANDRA_SEARCH_MAX_CANDIDATES`, default 100,000 distinct R1 reads per page or count

- **Date:** 2026-11-26
- **Status:** accepted
- **Context:**
    - Every Cassandra search counts the distinct candidates it point-reads (R1) for one page, or for one `search_count`, and past a configured cap fails with 422 `SearchError::TooManyResults`, never a partial result (G27, ADR-aacruzgon-0027; `docs/Cassandra/schema/walkthrough.md` 5.1 step 7). Stale rows the tag check hides count too.
    - No document gives the cap's value or setting name. ADR-aacruzgon-0031 fixes only the `HFS_CASSANDRA_*` prefix and the `from_env_with` reader in `C/config.rs`. #128 makes recording them part of the framework issue ("Open choices", item 5).
    - Row 6.4's `large_id_set_suite.rs::large_id_set_search_count_cursor_not_and_tenant` (`crates/persistence/tests/search/large_id_set_suite.rs:42`; the query at `:24`-`:40`) searches with one `_id` parameter of **70,003 values** (70,000 absent ids and 3 hits), and expects a count, two pages joined by a cursor, and the same in a second tenant. `_id` is served by one R1 read per id, absent ids included (walkthrough 5.4), and G27 and 5.1 step 7 count every distinct candidate point-read with no exception for `_id`. So each page and each count reads 70,003 candidates, and a cap below 70,003 fails that suite with 422.
    - For comparison, MongoDB caps its id sets at a fixed 300,000 (`MAX_RESULT_ID_SET`, `crates/persistence/src/backends/mongodb/search_impl.rs:341`), sized by its 16 MB BSON document limit (the comment at `:340`), with no setting.
- **Decision:**
    - The setting is `HFS_CASSANDRA_SEARCH_MAX_CANDIDATES`, read in `C/config.rs` through `from_env_with` like the others, a positive integer; 0 or garbage refuses to start, as the other numeric settings do.
    - The default is **100,000**: above the 70,003 `_id` values of the required suite with room to spare, and at the scale of the benchmark dataset (100,000 resources, release `benchmark-datasets-2026-11-09`).
    - `_id` reads count, as G27's rule is written ("distinct candidates point-read"); no exception. The design introduces the limit for "a date-only or otherwise unbounded search" (`cassandra-discussion.md:388`) but gives the same counting rule, and no document exempts `_id`.
    - The setting itself goes to `C/config.rs`'s owner, Sam (#127, file table), with this entry as the reason.
- **Alternatives considered:**
    - **10,000, a smaller default.** Lost because it fails row 6.4's required 70,003-id suite with 422.
    - **Don't count `_id` reads, and keep a small cap for the index-driven paths.** Lost because it departs from G27's rule as written, which ADR-aacruzgon-0027 decided, so it would need Alan's agreement and a design change, and a large `_id` list (which the shared chain resolver produces, the suite's module doc at `:1`) costs the same R1 reads as any other candidate.
    - **300,000, MongoDB's figure.** Lost because MongoDB's number comes from its 16 MB document limit, which Cassandra doesn't have, and a page at the cap would make three times the R1 reads of 100,000 before it answers 422.
    - **No configurable setting, a constant like MongoDB's.** Lost because the roadmap and the design call the cap configurable (`development-roadmap.md:494`, `cassandra-discussion.md:388`) and ADR-aacruzgon-0031 plans it as an `HFS_CASSANDRA_*` setting, and an operator on a small node may want it lower.
- **Consequences:**
    - The required suite passes under the default.
    - A page or a count may do up to 100,000 `LOCAL_QUORUM` R1 reads before it gives up, plus the index and `contains` reads, which the cap does not count; that may take longer than a client waits. How long is not measured. Step 8 measures it, with how often the 422 fires (already on ADR-aacruzgon-0027's "To measure" list), and this default is revisited then.
    - A filtered `search_count` (`_count=0`, `_summary=count`, `_total=accurate` or `estimate`) that point-reads more than 100,000 distinct candidates answers 422, never a partial count. Hidden stale rows and candidates a residual drops count too, so this can happen with fewer than 100,000 matches. An unfiltered `search_count` uses `count` and has no cap (walkthrough 5.9). On the benchmark dataset the largest type, Observation, has 99,789 resources, so a filtered count over nearly all of them has little room.
    - Tests lower the cap through `CassandraConfig` to cross it with a handful of resources. MongoDB's tests do the same with a test-only override, `with_result_id_cap` (`search_impl.rs:361`).
- **AI involvement:** Claude Code (Claude Opus 5.5) found the 70,003-value `_id` query in `large_id_set_suite.rs` and MongoDB's 300,000 cap (code read), and proposed the name and the default. An independent audit agent (Claude Code, Claude Opus 5.5) checked every citation against `883f9b1e0`: it corrected the suite's line (`:42`, not `:21`) and what the suite asserts, narrowed the `search_count` consequence to filtered counts of distinct candidates point-read, noted the reads the cap does not count, fixed the MongoDB test comparison, added the 300,000 alternative and the design's "unbounded search" wording, and confirmed that no document exempts `_id` reads. Reviewed and accepted by me (Anastasia Bryzgalova) on 2026-11-26.
