# ADR-anastasiabryz-0003: `DateSearch` and `CursorPagination` are declared in Step 6's last commit, with `BasicSearch`, not at 6b and 6d

- **Date:** 2026-11-26
- **Status:** accepted
- **Context:**
    - ADR-aacruzgon-0037 declares each capability in the step that implements it, and puts `BasicSearch`, `DateSearch` and `CursorPagination` "at Steps 6a to 6d" (`docs/Cassandra/cassandra-discussion.md:135`, on `883f9b1e0`).
    - ADR-aacruzgon-0085 later moved `BasicSearch` to Step 6's last commit (Step 7 phase 4; Alan makes it on my branch, #127), because `supports_search()` follows that declaration and `/metadata` reads it, so declaring it early would list `search-type` and every registered parameter while search still refuses. It says nothing about `DateSearch` and `CursorPagination`. Roadmap Step 7 phase 4 (`development-roadmap.md:552`, on `883f9b1e0`) named only `BasicSearch`.
    - The crate's rule (`crates/persistence/src/core/backend.rs:67-68`): "A capability must never be declared for aspirational, planned, or implemented-but-unwired behavior". 6b and 6d each merge on their own, in parallel with the framework's engine (#127, "The order", item 2), so when one merges, its module may not yet be reachable through `search()`. Serving search doesn't depend on `BasicSearch`: only `/metadata` reads `supports_search()` (`crates/rest/src/handlers/capabilities.rs:155`).
    - No REST or `hfs` code reads `DateSearch` or `CursorPagination`, so `/metadata` doesn't change either way. #128 ("Open choices", item 6) says `CompositeStorage`'s analyzer routes by them. It maps query features to them (`crates/persistence/src/composite/analyzer.rs:111`, `:127`), but the router compares them with each `BackendEntry`'s configured capabilities, explicit or from its role (`composite/config.rs:197`-`:208`, `:587`-`:594`; `composite/router.rs:353`), never with the backend's `declared_capabilities()`, and a `Primary` entry already lists both (`composite/config.rs:77`-`:95`). Cassandra is a standalone primary only (`composite/mod.rs:23`-`:25`). So declaring them changes no routing today.
    - Their only readers are tests: the contract test's `GOLDEN` and `LATER` (`tests/backend_capability_contract.rs:839`, `:849`), `C/backend.rs`'s `declared_capabilities_are_exactly_those_implemented` (`:1526`), and the shared harness, whose Cassandra `supported_capabilities()` is `declared_capabilities()` (`tests/common/cassandra_testable.rs:197`). A suite case gated on either with `require_capability!` (`tests/common/harness.rs:364`) would be skipped on Cassandra until the declaration. No test uses that macro today.
- **Decision:** Declare `DateSearch` and `CursorPagination` in the same last commit as `BasicSearch`, the Step 7 phase 4 commit, in `declared_capabilities()` (`C/backend.rs`) and the golden list of `tests/backend_capability_contract.rs`. 6b and 6d declare nothing.
- **Alternatives considered:**
    - **Declare them at 6b and 6d, as ADR-aacruzgon-0037 and the design say.** Lost because 6b and 6d can merge before the framework's engine wires them into `search()`, and then the declarations would describe implemented-but-unwired behaviour, which `core/backend.rs:67-68` forbids.
    - **Declare each once `search()` serves it, before the last commit.** Workable: the rule allows it, and since only tests read the two, it is harmless. Lost on judgement: it would declare date search and cursor paging while `BasicSearch`, and so `supports_search()`, still says the backend doesn't search, and it spreads the switch over several commits, each needing Sam and Sara, before Step 6's gate has passed (`development-roadmap.md:508`).
- **Consequences:**
    - All three search capabilities turn on together, in one commit, when search works end to end.
    - Harder: until that commit, a shared suite case gated on `DateSearch` or `CursorPagination` would skip on Cassandra, so 6b's and 6d's copies in `tests/cassandra/` must not gate on them.
    - What the last commit changes beyond `BasicSearch`: `declared_capabilities()` (`C/backend.rs:573`-`:580`) and its unit test's expected and absent lists (`:1531`-`:1543`); in `tests/backend_capability_contract.rs`, `GOLDEN` gains both, `LATER` and its loop (`:849`, `:933`) go, and the doc comments that still say "at Steps 6a to 6d" and "when Step 6d empties it" (`:829`, `:848`) change, as does `C/backend.rs:1528`-`:1530`'s; and `tests/common/capabilities.rs`'s Cassandra row moves both from `Planned` to `Implemented` (`:241`, `:263`; its comment at `:225`-`:226` says "Steps 2 to 6d"). `C/backend.rs` is Sam's (5s), and `backend_capability_contract.rs` and `capabilities.rs` are Sara's (#127, file table), so Alan's phase-4 commit asks them, as it already does for `BasicSearch`.
    - **This departed from ADR-aacruzgon-0037, the design's line 135 and roadmap Step 7 phase 4,** so it needed Alan's agreement, asked on #128 on 2026-11-26 (https://github.com/aacruzgon/hfs-Cassandra-CS4411/issues/128#issuecomment-7207204513). He agreed on 2026-11-27 (https://github.com/aacruzgon/hfs-Cassandra-CS4411/issues/128#issuecomment-7222032485) and made the text changes himself in PR #138: ADR-aacruzgon-0104 amends 0037 for these two capabilities, `docs/Cassandra/cassandra-discussion.md:135` now declares all three "in Step 6's last commit", and the roadmap names all three in Step 6's last-commit task (`development-roadmap.md:502`) and in Step 7 phase 4 (`:551`). So this entry's commit edits neither text. ADR-aacruzgon-0104 also widens the consequence above: until that commit, no Step 6 test in `tests/cassandra/` may gate on `BasicSearch`, `DateSearch` or `CursorPagination`, through either harness gate.
