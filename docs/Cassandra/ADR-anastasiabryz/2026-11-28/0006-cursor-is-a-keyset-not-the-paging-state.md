# ADR-anastasiabryz-0006: A search cursor is a keyset, the last resource's `(last_updated, id)`, never the driver's paging state

- **Date:** 2026-11-28
- **Status:** accepted
- **Context:**
    - #129 lists this as an ADR topic: "from Discussion #28, why the cursor is a keyset and not the driver's paging state. The design gives no reason." `C/` is `crates/persistence/src/backends/cassandra/`.
    - **Upstream's sketch.** In Discussion #28, the upstream maintainer's reply of 2026-01-10 (https://github.com/HeliosSoftware/hfs/discussions/28#discussioncomment-15463543) prefers cursors to offsets. It sketches `PageCursor(Vec<u8>)`, an opaque byte string: "For Cassandra, this wraps the paging state", with "Native paging state from the driver" as Cassandra's row in its table, and a keyset `(_lastUpdated, _id)` for PostgreSQL.
    - **Our design chose a keyset, with no reason given.** The design (`docs/Cassandra/cassandra-discussion.md:197`, "The cursor is a plain `PageCursor`") and walkthrough 5.10 make the cursor `sort_values = [<instant, RFC 3339 ms>, <reserved bucket slot>]` (plus `"start"` or `"end"` in a date-only search) with `resource_id = id`, and the next page reads strictly after it with `(last_updated, id) < (?, ?)`. ADR-anastasiabryz-0004 fixed the encoding. The `PageCursor` on `main` (`crates/persistence/src/types/pagination.rs:123`) is that structured form, not the sketch's bytes.
    - **What a paging state is.** The native protocol v5 spec, section 7, "Result paging" (`doc/native_protocol_v5.spec` on Cassandra's `cassandra-5.0` branch): a `Rows` result with more rows carries a `<paging_state>`, which "should be used in a QUERY or EXECUTE message (that has the *same* query as the original one or the behavior is undefined) to retrieve the next page of results", and "The <paging_state> is specific to a protocol version". It continues one statement's result set after the last row the node sent. The session already uses it that way, inside a single read (`C/session.rs:129`-`:133`, `:491`-`:493`, `rows_paged`).
    - **What a search page is** (walkthrough 5.1, 5.2, 5.7, 5.10). It is not one statement's result:
        - it can merge several queries: token's two partitions and every comma list (5.2), `_lastUpdated ne`'s two slices, and a date `ne` across `date_index` and `date_index_by_end` (5.7);
        - it reads each query in `LIMIT` batches, each re-issued with a keyset bound (5.10, step 2);
        - it drops candidates after reading them (the tag check, the residuals, the AND checks), and stops at `_count + 1` kept, usually in the middle of a batch.
- **Decision:**
    - A search cursor is a keyset: the order instant and id of the last resource the page returned, as ADR-anastasiabryz-0004 encodes it. The next page issues fresh queries bounded strictly after that position, `(last_updated, id) < (?, ?)` in the default order or `(start | end, id) > (?, ?)` in a date order, each with the one end bound G19 allows.
    - The driver's paging state never leaves `C/session.rs`. It is used only to read one statement to its end inside one operation (counts, version history, repair, the sweeper and the consistency checks: `rows_paged` and its variants), never in a link.
- **Alternatives considered:**
    - **The driver's paging state, as Discussion #28 sketches.** Lost for four reasons:
        - **A page is not one query.** A merged page would need one paging state per query plus the merge's own position, and a page that stops mid-batch has no paging state for "after this resource": the node's state points after the last row it sent, so the rest of that batch would be skipped or read again.
        - **The query can't stay the same.** The spec makes a state valid only for "the *same* query"; anything else is undefined. A `_lastUpdated` page sends the tighter of its slice's bound and the cursor (G19), so its statement changes from page to page.
        - **It is tied to a protocol version.** A link minted before a driver or node upgrade could stop working, or behave in an undefined way, with nothing to detect it. A keyset means the same on any node, driver and protocol version.
        - **It can't be checked.** Opaque node bytes can't be matched against the plan's order or date table, so a cursor of another order couldn't be refused as `InvalidCursor` (400, `coverage.md` section 5; walkthrough 5.7), and a tampered or foreign state would reach the node as undefined behaviour. `decode` checks a keyset fully (ADR 0004).
    - **A keyset plus the paging state as a hint for the driving query.** Lost because the two positions can disagree, and the paging state's limits above still apply to the part it covers.
    - **Offsets.** Refused by design: an `_offset` is 400 (#128, row 6.1). The reason is Discussion #28's own: page N costs O(N) skipped rows, and rows shift under concurrent writes.
- **Consequences:**
    - Easier: one keyset form works on every table, since every clustering order ends in `id` (5.10, spike A3). A page can stop at any candidate. A cursor is checked by `decode` and portable across nodes, drivers and upgrades, as http.html#paging's opaque links allow ("only the server understands them"). The reserved bucket slot keeps room for partition bucketing (ADR 0004).
    - Harder: each page starts its queries afresh from the bound, one seek per partition per page rather than continuing a node-side cursor. The cost isn't measured; Step 8 measures paging.
    - Unchanged either way: a resource updated during paging moves ahead of the cursor and isn't seen again (G21), which search.html#currency leaves "at the discretion of the search engine". A paging state would miss it too, since each page reads the node's current data.
    - The 100,000-resource run (#129's exit criterion) checks this cursor end to end.
