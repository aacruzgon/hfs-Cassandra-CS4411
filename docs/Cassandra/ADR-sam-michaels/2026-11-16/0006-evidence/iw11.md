### IW11. [IMPL] How a batch's size is measured, and the packing rule
- **Options:**
    - **W (the design's measure):** count every byte of the batch's statements as they go on the wire. Per statement that is 1 (kind) + 18 (prepared id) + 2 (value count) + Σ(4 + value bytes), partition-key values included. Fill each batch up to 4,864 bytes (5,120 minus a 256-byte margin).
    - **N (the node's own formula):** count 29 bytes per (table, partition), and per row 21 + clustering bytes + per cell (20 + value). Fill up to 4,864 bytes, with a 16 KiB wire backstop per batch.
    - With either measure, units (a pair, a lone insert, a lone delete) are never split. A pair larger than the bound goes alone.
- **Evidence:**
    - **The design chose W knowingly.** Design step 5 says "The backend sizes each batch itself, from every byte of its statements. The node's own check counts clustering and cell bytes but not partition-key bytes … So the thresholds are no safety net for index batches" (`cassandra-discussion.md:273`; walkthrough `:231`, checked on a 5.0.9 node on 2026-11-05).
    - **The node's formula is now exact.** I verified it on the node to the byte (5,168 and 7,680; see Measurements). It is checked only for batches with more than one mutation (`BatchStatement.java:331-367`). W is always at least N, because every row's wire form carries its partition key, and the tenant id alone is up to 64 bytes. So a W-packed batch can never trip the node's warning.
    - **What W costs** on Synthea Observation updates: 2.31 batches per write (max 19), against 1.17 (max 9) under N. Creates: 1.18 against 1.09. The batches of one write are concurrent (IW12), so W adds requests, not round trips. Throughput at 2 to 3 concurrent batches per write was not measured. It should fall between the one-batch figure (about 9.5k writes/s) and the per-partition figure (about 6.4k): **UNVERIFIED**.
    - **The oversized pair.** The design's "every row fits in one batch" (walkthrough `:231`) was written for single rows. A pair of rows exceeds 4,864 wire bytes only when its `code` and `system` together exceed about 2,100 bytes, which G35 allows (2,048 each) but no fixture or Synthea resource comes near. Such a pair is one mutation: the node neither size-checks it nor writes it to the batchlog.
    - **Roadmap section 7:** "any fixture above 5 KiB per batch → split batches further; never raise the threshold".
- **Recommendation: W, with units never split,** as the design says. Its cost is about one extra concurrent request per update, and the design's reason still holds: the threshold exists to bound what a coordinator receives, and partition keys are most of those bytes.
    - **The oversized pair** goes alone as a one-pair batch (atomic, unlogged by the node), and design step 5 states it as the one exception to "under 5 KiB". The alternative is to send its insert, then its delete, as plain statements. That keeps every batch strictly under 5 KiB at one extra round trip for that key.
    - **Measure-first trigger:** switch to N with the 16 KiB backstop if Step 8 shows index batch requests limiting write throughput. That switch reverses a design decision, so it needs its own ADR and a design edit.
    - **Exit criterion:** define "every batch under 5 KiB on the fixtures" as "every batch of more than one unit is ≤ 5,120 bytes by W". Amend progress row 5.1's wording in the same commit.
- **Performance impact:** under W, about 2 batches per update on Synthea Observations and 1 to 3 on fixture Patients. Under N, about half that.
- **Risk if wrong:** none for correctness either way. Under W, some throughput is spent on requests the node does not need. Under N, a batch may carry 2 to 3× its node-measured size in partition keys (10,194 wire bytes in the largest N-packed Synthea batch).
- **Verify before coding:**
    - a pure test that W is computed exactly from the bound values, and that W ≥ N for every row kind, with N pinned to the node's golden values (5,168 and 7,680) so the fallback is ready;
    - a test over every fixture and the largest Synthea Observation that each batch of more than one unit is ≤ 4,864 by W, and that no pair is split;
    - a live test that the node returns no warning for the largest batch. The protocol carries warnings in the response frame; **UNVERIFIED** how cdrs-tokio 10 surfaces them to the session.

*Update 2026-11-18:* the batch counts above for updates ("2.31 batches per write (max 19), against 1.17 (max 9) under N", and "about 2 batches per update" under Performance impact) measure **pair-only packing**: `iwbench/src/main.rs`'s "update option B (pairs kept together)" line keeps each insert and delete pair together but can split one partition's pairs across batches. ADR-sam-michaels-0006 chose whole partitions (IW9, IW11: a unit is one partition's rows, never split, and a unit too big on its own goes alone). `main.rs` now also prints that packing, as "update option B, whole partitions", and `iwbench-whole-partitions.txt` is its output on the same three fixtures and the 10k Synthea dataset. Every other line of that file matches `iwbench-opt.txt` except the extraction times. Under whole-partition packing, Synthea Observation updates take 2.31 batches per write (max 18) under W and 1.18 (max 10) under N. Across the 9,982 updates, 392 partitions exceed 4,864 wire bytes on their own; the largest is 8,712 bytes. Each goes alone as a one-partition batch, which is one mutation, so the node does not size-check it (`BatchStatement.java:331-367`, above). No fixture has such a partition; the largest fixture partition is 744 bytes. The counts above are left as measured; this note does not change them. The create and delete counts come from `pack_by`, which packs statement by statement, and were not re-measured with whole partitions.
