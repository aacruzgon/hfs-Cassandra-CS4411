# ADR-sara-lahourpour-0001: The race checks accept a 504 at RF 2 or more, read from the keyspace, and check the history instead

- **Date:** 2026-11-13
- **Status:** accepted
- **Context:**
    - On the three-node cluster (RF 3, row 0.3), a concurrent write can be answered 504: the `LOCAL_SERIAL` read that settles an unknown compare-and-swap outcome is superseded by a competing proposal (`hadSideEffects == MAYBE`, `Paxos.java:883-894`, Cassandra 5.0.9). ADR-aacruzgon-0050 and 0055 map it to 504, and ADR-aacruzgon-0072 decision 4 accepts it on RF 3, with no backend retry. Issue #77 asked Step 4 to make the race checks expect it before Step 8.
    - The race checks panicked on the 504 before they reached the history check. On my laptop (Windows, Docker Desktop with WSL 2), the cluster passed 150 to 152 of 154 tests; every race failure panicked at `versioned_write_race_suite.rs:96`. The single node passed 154 of 154.
    - `versioned_write_race_suite.rs` is upstream's file, and the SQLite, MongoDB and PostgreSQL tests include it too, so the change could not loosen it for them.
    - A 504 can reach the winner: in 160 races of 8 writers on the cluster, 21 had a 504, and in one of them the winner got it. A 504'd write that applied leaves its version out of `list_versions`, `vread` of it is none, `count` is stale (one too high after a delete or an overwrite, one too low after a revive), and the intent row is kept with the `resources` row's `write_id`, until Step 5's sweeper replays it. Alan reproduced this state on one node with the fault seam, and I reproduced it for revive, `create_or_update` and `delete_versioned`, and on the cluster with a real race (issue #77).
- **Decision:**
    - **When to accept a 504: the `helios` keyspace's replication factor in `helios-dc1`,** read from `system_schema.keyspaces` (`replication_factor` in `tests/common/cassandra.rs`). At RF 2 or more a 504 is an accepted outcome; at RF 1 it fails the test, as before. A superseded serial read needs more than one replica in the Paxos round, so the RF is the condition itself, not a stand-in for it.
    - **Opt-in in the shared suite.** `versioned_write_race_suite.rs` gains `RacePolicy` (`Strict`, or `AcceptTimeouts` with a `PendingWrites` probe) and a `_with` variant of each race test. The plain functions call their variant with `RacePolicy::strict()`, so `sqlite_tests.rs`, `mongodb_tests.rs` and `postgres_tests.rs` are unchanged. The four Cassandra wrappers in `step3_suites` and `create_read::cassandra_concurrent_creates_of_one_id_make_exactly_one_resource` choose the policy from the RF.
    - **Only `BackendError::Timeout`.** A 503 from the serial read leaves the same state (issue #77), but none has come up in a race, so it still fails the test.
    - **Who won is read from the stored body.** Every writer writes its own `Writer{n}` family. With a writer told it won, the stored body must be its; with none, the body must be one 504'd writer's, or nothing landed and no writer was refused (a refusal means another write landed).
    - **The history must be complete, with one exception:** it may lack its newest version only when the `resources` row's `write_id` matches an intent row kept in `pending_index_writes` for that version (`pending_version` in `tests/common/cassandra.rs`, which reads this hour's and the previous hour's buckets, all 16 shards). The concurrent-create test accepts `count` 0 for a landed create on the same condition, and 1 otherwise. When row 5.2's sweeper lands, the checks should run one sweep with the grace period at 0 and then require the exact history and `count`.
    - **Each race prints its mode,** `[race policy case=race:<test> rf=<n> accept_504=<bool>]`, beside the `[cas …]` line.
- **Alternatives considered:**
    - **An environment variable, `HFS_TEST_CASSANDRA_CLUSTER=1`:** lost. Setting it by mistake on the single node would silently loosen the check row 0.5's required job depends on, where a 504 is always a bug. Reading the RF cannot be wrong that way: the required job's keyspace is RF 1.
    - **The number of nodes the driver sees:** lost. It is a stand-in for the RF, it depends on peer discovery, which is what breaks on Docker Desktop, and a three-node cluster with an RF 1 keyspace would accept a 504 that cannot be the designed one.
    - **Accepting the 504 in the shared suite for every backend:** lost. A 504 is a bug on SQLite, MongoDB and PostgreSQL, and upstream's tests would get weaker.
    - **Accepting the 503 as well:** lost for now; it has not been seen in a race. Alan is changing every 503 from `unavailable_unless_timeout` to say the write may have been stored (issue #77).
- **Consequences:**
    - **The required CI job stays exactly as strict.** On the single node all 154 tests pass and the five race policies print `rf=1 accept_504=false`. SQLite passes 128 of 128, its five race tests included, and the MongoDB and PostgreSQL tests compile.
    - **The cluster passes the race tests.** In five runs on 2026-11-13, every race test passed with `rf=3 accept_504=true`; the only failure in four of them was `node_runs_the_docker_cassandra_configuration`, which always fails on the cluster. The first run also had four ordinary `LOCAL_QUORUM` timeouts in non-race tests while the laptop was compiling.
    - **The winner-got-the-504 path is rare,** about 1 in 160 races in my measurement, so a given cluster run probably does not exercise it. The checks for it are written from the state the fault seam and the cluster produced, but they have not been seen to pass on that path in a test run.
    - **Until Step 5, a stale `count` and a short history are accepted** only together with the intent-row rule; Step 5 should tighten them (above).
    - `docker/cassandra/README.md` now documents the policy and how to run the tests on Docker Desktop, and the root `README.md` lists `pkg-config` and `libssl-dev` for Linux.
