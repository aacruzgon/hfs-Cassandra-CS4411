# Cassandra Persistence Backend for Helios

Alan Cruz, Anastasia Bryzgalova, Diya Subhashbhai Patel, Sara Lahourpour, Samuel Michaels Rodriguez

## Background: the architecture we must respect

The Cassandra backend adds a storage technology, not a new architecture, and that architecture is set out in [Discussion #28](https://github.com/HeliosSoftware/hfs/discussions/28). Helios sits in the "extensible interface layer + polyglot persistence" quadrant: a trait-based layer that any storage technology can implement, with a unified FHIR API above it.

In #28, Cassandra is named as a fit for "web-scale data requirements without breaking the bank". The principles below come from #28, and each one constrains our implementation.

| Principle in #28 | What it means for Cassandra |
| --- | --- |
| Decompose the FHIR spec into focused traits. `ResourceStorage` "knows nothing about search, nothing about REST semantics, nothing about transactions." | Implement `ResourceStorage`, `VersionedStorage` and `SearchProvider` separately. A capability we do not support means we do not implement its trait, or we refuse it explicitly. No catch-all Cassandra interface. |
| Capabilities extend the base by trait inheritance (`VersionedStorage: ResourceStorage`; history builds on versioning). | vread goes in `VersionedStorage`. The REST layer checks `If-Match` itself and uses `ResourceStorage::update` as the compare-and-swap. History is not planned, but the server's trait bound requires the history traits, so they exist only as stubs that refuse. |
| Multitenancy is not optional. Every operation takes a `TenantContext`; there is no escape hatch. "The tenant_id must be the leading column in composite indexes." | The tenant is part of every partition key, so a query without a tenant cannot be written. |
| Search is a base trait plus extension traits (chained, terminology, text). | Implement base `SearchProvider` only. The include and revinclude providers are compile-only stubs. No chaining, `_include` or text search. Terminology modifiers on tokens are handled by the REST layer, not by us (see the `:in`/`:above`/`:below` row in the scope table). |
| Transactions only where atomic all-or-nothing semantics exist. Batch entries are independent. | No `TransactionProvider`. Batch works because the REST layer runs each entry against `ResourceStorage`. |
| Backends declare capabilities, and queries are validated at runtime: capability checking "fails fast with clear error messages". | Declare exactly token, date, URI and cursor paging. The REST layer validates modifiers against parameter types itself, but never calls the shared `validate_search_query`, so our search path refuses unsupported parameters and modifiers as well. |
| Composite storage routes operations to specialized backends (primary, search, graph, terminology). | Cassandra must work as a standalone primary. It also must not block a later "Cassandra + Elasticsearch" composite, which the README lists as planned. |
| Security first: database access must not bypass FHIR authorization. Audit goes to a separate store. | Authorization and audit stay above the backend. Cassandra never stores AuditEvents of its own. |

Two cautions about reading #28 today:

- **Its feature matrix is an early, work-in-progress example.** It shows Cassandra with keyspace-based multitenancy, `:exact` ✓, `:missing` "Limited" and history "Limited". The persistence README matrix supersedes it and "reflects the actual implementation status", so we follow the README.
- **Its code is illustrative.** The real signatures have moved on. For example, `create` now takes `resource_type`, a `Value` and a `FhirVersion`, and search returns `SearchResult`. We implement against the code at the baseline revision, listed in the traits section below.

## Scope: the Cassandra column of the capability matrix

The matrix is in the persistence README under [Backend Capability Matrix](https://github.com/aacruzgon/hfs-Cassandra-CS4411/blob/a5e74a3604b181722a2d02b11f29cc76e91520bd/crates/persistence/README.md#backend-capability-matrix). We checked the Cassandra column cell by cell: it is identical at the baseline revision and at today's HEAD.

| `:in`, `:above`, `:below` on a token parameter; `:not-in` | ✗ | Decided by the REST layer before we are called (`crates/rest/src/handlers/search.rs`): without `HFS_TERMINOLOGY_SERVER` they return 501 `TerminologyRequired`; with it, REST expands `:in`, `:above` and `:below` into a plain comma-separated token list, which we serve (200). `:not-in` always returns 501 (`search.rs:411-426`; the expansion or `TerminologyRequired` at `428-466`). When the expansion fails (the terminology server is unreachable, or answers an error, such as 404 for an unknown ValueSet), REST drops the parameter and runs the search without it, returning a wider result with no warning and no OperationOutcome, even under `Prefer: handling=strict` (`search.rs:1302-1310` for `:in`, `1401-1407` for `:above` and `:below`). Upstream closed that report as not planned ([HeliosSoftware/hfs#2019](https://github.com/HeliosSoftware/hfs/issues/2019), 2026-10-16), so we document it and do not refile. We accept that behaviour as it is (`docs/Cassandra/schema/coverage.md`, C8; ADR-aacruzgon-0027). |
| `_text`, `_content`, `_filter`, chaining, `_has`, `_include`, `_revinclude` | ✗; `_has` ◐: through the shared resolver, when its terminal parameter is token, date or URI | Rejected (see the rejection section for how each actually fails). `_text` and `_content` are 501 by name in our `search()` (C10). `_filter` is 501 by name in our `search()` too, as `BackendError::UnsupportedCapability`; REST is unchanged, since it passes `_filter` through and SQLite and MongoDB serve it (C11, ADR-aacruzgon-0027). A `_has` whose terminal parameter we serve, such as `Patient?_has:Observation:patient:code=8867-4`, is answered by REST's chain resolver through our ordinary `search()`, which cannot tell it from a token search; one whose terminal we do not serve is 400 (`docs/Cassandra/schema/coverage.md`, C7, ADR-aacruzgon-0027). #28's work-in-progress matrix marks `_has` unsupported for Cassandra; the persistence README matrix supersedes it (above), and its `_has` row for Cassandra becomes ◐ with this note at Step 8. **Known upstream defect:** the shared resolver turns each source reference into an id with `split_once('/')` (`chain_resolver.rs:739-745`), so a versioned reference (`Patient/a/_history/1`) gives the id `a/_history/1` and an absolute one is dropped, and neither finds Patient `a` on any backend ([HeliosSoftware/hfs#2499](https://github.com/HeliosSoftware/hfs/issues/2499); `coverage.md` section 6). |
| Offset pagination; single- and multi-field sorting | ✗ | Not supported. Each search has one native order: `(last_updated DESC, id DESC)`, or, for a date-only search sliced on a date table, that table's order. `_sort` is accepted only when it equals the native order: absent, or `-_lastUpdated` where that is native (C9, ADR-aacruzgon-0027) |
| Bulk submit REST worker | ✗ | Not implemented |
| Multitenancy rows | — (no backend in tree) | Shared schema with the tenant in every key, matching the other backends |

Two parameters need a note because they are not matrix rows: `_id` and `_lastUpdated`. The REST layer sends them to `search()` on its own, and chain, `_list` and include resolution are rewritten into `_id` filters before the backend is called. Both are cheap for us (`_id` is a point read on `resources`; `_lastUpdated` is a slice on `resources_by_type`), so they are in scope. Several `_id` parameters are ANDed by intersecting their id sets before any read. A `patient/` scope relies on this: it appends `_id=<launch patient>` to every Patient search (`crates/rest/src/patient_compartment.rs:172-181`). An `_id` value is compared whole with the id, as SQLite and PostgreSQL do (`backends/sqlite/search/query_builder.rs:1159-1224`, `backends/postgres/search/query_builder.rs:1870-1929`), so `_id=sys|abc` and `_id=|abc` match nothing (C2, ADR-aacruzgon-0027).

Two fields of `SearchQuery` are not parameters either, and the backend must apply both (ADR-aacruzgon-0026):
- **`compartment`**, set by REST for every non-Patient search under a SMART `patient/` scope (`patient_compartment.rs:183-201`, upstream #1618), for compartment searches and for `$everything`. Ignoring it would return other patients' resources. We serve it as a residual filter (see "Capabilities and rejection"). It confines the base query only: the hops of a chain or `_has` carry no compartment, a known upstream defect ([HeliosSoftware/hfs#2501](https://github.com/HeliosSoftware/hfs/issues/2501); "Capabilities and rejection").
- **`fhir_version`**, set when the client names a `fhirVersion` MIME parameter (`crates/rest/src/handlers/search.rs:557`, upstream #2254). Only resources stored under that version match, counts and `_total` included.

One more scoping note: we test against FHIR R4 only, but nothing in the backend is tied to R4. Helios decides the FHIR version per request and stores it on every resource, and the backend follows that mechanism so that R4B, R5 and R6 need no backend changes later. The FHIR versions section below spells this out.

Once the backend exists, the README's statement that it "reflects the actual implementation status" means the Cassandra column must change. Specifically, ○ becomes ✓ for what ships, `:exact` becomes ✗ with a note, the multitenancy rows are filled in, and the note below the table that says Cassandra has no backend is removed. The same "no Cassandra backend" statement appears in `src/backends/mod.rs`, `src/lib.rs`, `src/composite/mod.rs`, the placement table and backend list further down the README, `ROADMAP.md`, the changelog, and a hard-coded Cassandra table in `tests/common/capabilities.rs` that already disagrees with the README.

## What the FHIR specification requires

We implement and test against FHIR R4. The matrix links point to [build.fhir.org](https://build.fhir.org), the current development build. The two agree on most in-scope rules, but not all; the table marks the rows where they differ, and the list after it collects the differences that affect our tests. The REST layer formats HTTP, so the backend's job is to supply the data and the errors that make these rules hold.

| Capability | Spec | Rules the backend must make true |
| --- | --- | --- |
| CRUD | [R4 http.html#create](https://hl7.org/fhir/R4/http.html#create), [build](https://build.fhir.org/http.html#create) | On create the server assigns `id`, `meta.versionId` and `meta.lastUpdated` and SHALL ignore client values; on update the client `id` must be present and match the URL, or the server SHALL answer 400. Helios answers a mismatch with 400 but accepts a missing `id`, on every backend, and a batch PUT's id is never compared (HeliosSoftware/hfs#2524, REST-owned; ADR-aacruzgon-0064). Delete of an already-deleted or unknown id has no effect and returns 200/204. With HeliosSoftware/hfs#2529 (open upstream; issue #2523), which the fork carries (ADR-aacruzgon-0052), the shared REST layer follows this. Without it, Helios answers 404. Storage returns `NotFound` for both, and the backend does too, like SQLite, PostgreSQL and MongoDB. With no `If-Match`, `crates/rest/src/handlers/delete.rs` answers that `NotFound` with 204, or with 200 and an informational OperationOutcome under `Prefer: return=OperationOutcome`, and writes nothing. With `If-Match`, a delete of an absent or deleted resource is still 412. For servers that keep history, a delete is recorded as a history entry with no content. A read after delete returns 410 Gone (R4 states it as fact; the build says "when the server wishes to indicate that the resource is deleted"), and an unknown id returns 404. A later PUT may bring a deleted resource back. |
| vread | [R4 http.html#vread](https://hl7.org/fhir/R4/http.html#vread) | `GET [type]/[id]/_history/[vid]` returns that version. A deleted version "should return a 410". |
| Optimistic locking | [R4 http.html#concurrency](https://hl7.org/fhir/R4/http.html#concurrency) | The ETag is the weak version id, `W/"vid"`. An `If-Match` mismatch returns 412 and changes nothing. A 409 is permitted for other conflicts; a server that requires `If-Match` returns 400 when it is absent. Mapping a lost concurrent-write race to 409 is Helios's choice, not the spec's. |
| Batch | [R4 http.html#transaction](https://hl7.org/fhir/R4/http.html#transaction) | Entries SHALL have no interdependencies that change the server, and one failure SHOULD NOT alter another. The batch returns 200 with a status per entry. The build adds that two entries updating or deleting the same resource count as an interdependency. |
| Token | [R4 search.html#token](https://hl7.org/fhir/R4/search.html#token) | Four forms: `code` (any system), `system\|code`, `\|code` (no system property) and `system\|`. Values come from Coding, CodeableConcept (any coding), Identifier (system + value), ContactPoint, code, boolean, uri and string; the build adds id. Matching is literal (no subsumption) and case-sensitive unless the context says otherwise; `_id` is always case-sensitive; only when it is ambiguous SHOULD servers match case-insensitively. For ContactPoint, uri and boolean elements the pipe form SHALL NOT be used. |
| Date | [R4 search.html#date](https://hl7.org/fhir/R4/search.html#date) | Every value is a range. A partial date covers its whole year, month or day. A Period may be open-ended, and a Timing spans its earliest to latest event. The prefixes `eq ne gt lt ge le sa eb ap` compare ranges, and `eq` is the default. R4 defines the prefixes by range overlap; the build restates them as boundary tests (differs, see below). |
| URI | [R4 search.html#uri](https://hl7.org/fhir/R4/search.html#uri) | Exact whole-URI matching, case- and accent-sensitive (R4 adds escape-sensitive; the build drops that word). No normalization of trailing slashes or `urn:oid` values is specified. |
| Modifiers | [R4 search.html#modifiers](https://hl7.org/fhir/R4/search.html#modifiers), [build](https://build.fhir.org/search.html#modifiers) | `:exact` is defined for string parameters only (R4: "For string: :exact returns results that match the entire supplied parameter"; the build says it outright: "exact is only allowed on string type search parameters"). Both versions: a server **SHALL** reject a search with an unsupported modifier; the spec's example is 400 with an OperationOutcome. |
| Combining parameters | [R4 search.html#combining](https://hl7.org/fhir/R4/search.html#combining) | Different parameters, or a repeated one, are ANDed. Comma-separated values are ORed. A modifier on an OR list applies to every value. |
| Unknown parameters | [R4 search.html#errors](https://hl7.org/fhir/R4/search.html#errors) | Servers SHOULD ignore unknown or unsupported parameters by default and SHOULD honour `Prefer: handling=strict` by returning an error. The REST layer already handles this. Rejecting unsupported parameter types outright, as we do, is stricter than the default. |
| Paging | [R4 http.html#paging](https://hl7.org/fhir/R4/http.html#paging), [build](https://build.fhir.org/http.html#paging) | Page links are opaque and a `self` link is required; first, previous, next and last are "optional, but recommended" in R4. The build adds: SHOULD NOT include `previous` on the first page and SHOULD NOT include `next` when there are no more results. Both: never return more than `_count`, `_count=0` behaves as `_summary=count` (a total with no entries), `_total` is optional, and behaviour when data changes mid-paging is up to the server. Neither version defines cursor or offset paging. |

**Where R4 and the build (and R5) differ on in-scope rules.** Paging best practices (no `previous` on page one, no `next` after the last page) exist only in the build, and we follow them because MongoDB does. The build rewrites the date prefix definitions as boundary tests with half-open examples; R4 uses range overlap with inclusive-end examples. Helios's shared `range_predicate` encodes R4's overlap semantics over half-open stored ranges, and we reuse it, so all backends agree. The build drops "escape" from URI sensitivity, adds `id` to the token table and to the no-pipe rule, weakens the 410-after-delete wording, downgrades ETag and Last-Modified on update from SHALL to SHOULD, and adds `:text-advanced`, `:code-text` and `:iterate` to the modifier table. The update and delete changes are in R5 (5.0.0) as well, which HFS also builds: R5's #update drops R4's "(or brought back to life/re-created)" from the 201 rule, and its [#upsert](https://hl7.org/fhir/R5/http.html#upsert) adds "A server SHALL not return a 201 response if it did not create a new resource" (the build: SHALL NOT). A revive stays 201 in every version (ADR-aacruzgon-0064). None of these changes what the backend must store.

## Traits, structs and enums the backend must respect

Turning from the specification to the code, the server accepts a primary backend only if it implements 12 traits. Of these, only `ResourceStorage` and `SearchProvider` carry our scope, along with `VersionedStorage`, which the history traits and the vread handler require. The other ten we stub with explicit "unsupported" errors. `create_app` in `crates/rest/src/lib.rs` takes a generic `S: ResourceStorage + ConditionalStorage + SearchProvider + IncludeProvider + RevincludeProvider + InstanceHistoryProvider + TypeHistoryProvider + SystemHistoryProvider + BundleProvider + ExportDataProvider + PatientExportProvider + GroupExportProvider`; `create_app_with_config`, `create_app_with_auth` and `build_app` carry the same bound.

Paths below are relative to `crates/persistence/src` unless stated.

### Traits

| Trait (file) | Required methods | Cassandra |
| --- | --- | --- |
| `ResourceStorage` (`core/storage.rs`) | `backend_name`, `create`, `create_or_update`, `read`, `update(tenant, current, resource)`, `delete`, `count(tenant, Option<type>)` | Real. `update` is the compare-and-swap that If-Match relies on. `count` with `None` means all types. |
| `VersionedStorage` (`core/versioned.rs`) | `vread`, `update_with_match`, `delete_with_match`, `list_versions` | Real. A supertrait of `InstanceHistoryProvider` and required directly by the vread handler. `update_with_match` may return `OptimisticLockFailure` (412) or `VersionConflict` (409) per its doc; `delete_with_match` returns `VersionConflict`. REST does not call either for If-Match. |
| `SearchProvider` (`core/search.rs`) | `search`, `search_count`, `search_param_registry` | Real for token, date and URI. `search_param_registry` is called on every search, by capabilities, batch, compartment, `$everything`, bulk export and SQL-on-FHIR. |
| `SearchCapabilityProvider` (`core/capabilities.rs`) | `resource_search_capabilities`, `global_search_capabilities` | Real. Declares token, date and URI with no modifiers, plus `Count` and `Cursor` paging. Not in the server bound, and not consulted by the CapabilityStatement handler (see rejection section). |
| `Backend` (`core/backend.rs`) | `type Connection`, `kind`, `name`, `supports`, `capabilities`, `acquire`, `release`, `health_check`, `initialize`, `migrate` | Real. `kind()` returns `BackendKind::Cassandra`, which already exists as a reserved variant. Not in the server bound; required by the capability contract test. `initialize` only checks that the ten tables exist; it never applies `schema.cql`, which one process applies (a setup command or the test harness; P6, ADR-aacruzgon-0027). |
| `ConditionalStorage` (`core/storage.rs`) | `conditional_create`, `conditional_update`, `conditional_delete` | Stub. Override `supports_conditional` to `false`: the default claims support for create, update and delete. |
| `IncludeProvider`, `RevincludeProvider` (`core/search.rs`) | `resolve_includes`, `resolve_revincludes` | Compile-only stubs. REST resolves includes through `resolve_includes_iterative` over `SearchProvider`, never through these traits, so the real refusal lives in `search()`. |
| `InstanceHistoryProvider`, `TypeHistoryProvider`, `SystemHistoryProvider` (`core/history.rs`) | `history_*` and `history_*_count` | Stub |
| `BundleProvider` (`core/transaction.rs`) | `supports_atomic_transactions`, `supports_conditional_in_transaction`, `process_transaction_with_patch_validator` | Stub: `false`, `false`, `TransactionError::AtomicityUnsupported { backend_name }`, as S3 does. Batch never touches this trait. |
| `ExportDataProvider`, `PatientExportProvider`, `GroupExportProvider` (`core/bulk_export.rs`) | listing, counting and fetching for export | Stub, since bulk export is out of scope |

Every other stub returns `StorageError::Backend(BackendError::UnsupportedCapability { backend_name: "cassandra".into(), capability })`, which the REST layer maps to 501. That is "refuse explicitly" from #28, enforced by the compiler.

### Defaults we must override

Beyond the required methods, several provided defaults are wrong for a networked store, so we override them.

| Default | Problem | Override |
| --- | --- | --- |
| `ResourceStorage::readiness_check` returns `Ok` | `/_readiness` would report ready while Cassandra is down; the doc says networked backends MUST override | Delegate to `Backend::health_check` |
| `ResourceStorage::is_cluster_shared` returns `false` | Under-reports a networked store | Return `true` |
| `ResourceStorage::bulk_write_concurrency` returns 1 | Batch bundles and `create_many` run one entry at a time | Return 8, matching PostgreSQL and MongoDB. Batch further caps this at `HFS_BATCH_MAX_CONCURRENCY` (default 16) and forces 1 when any entry is conditional. |
| `ResourceStorage::delete_versioned` reads, then deletes | Not atomic, so an If-Match delete can race | Override with a lightweight transaction: `UPDATE resources SET deleted_at = ?, version_id = N+1, last_updated = ?, write_ts = ?, write_id = ? IF version_id = N AND deleted_at = 0` (soft delete, never a CQL `DELETE`; `0` means live, ADR-aacruzgon-0027) |
| `ResourceStorage::create_many` loops over `create` | Startup seeds about 1,400 conformance resources per tenant through it (see startup section) | Keep the loop but run it at `bulk_write_concurrency`, as the default already does; measure boot time |
| `ResourceStorage::read_batch` reads sequentially | Include resolution and `_id` lists would issue N round trips | Fan out concurrent point reads |
| `ConditionalStorage::supports_conditional` returns `true` for create, update and delete | Advertises conditional operations we do not have | Return `false` |

### Structs and enums

The traits above exchange the following types, and each has a contract we must also respect.

| Type (file) | What we must respect |
| --- | --- |
| `TenantContext`, `TenantId` (`tenant/context.rs`, `tenant/id.rs`) | Every key starts with `tenant.tenant_id().as_str()`. Ids are case-sensitive, up to 64 bytes, ASCII letters, digits and `- _ . /`, with no empty segment, and must never be folded or truncated. `__system__` is reserved by `TenantId::parse` and comes from `TenantId::system()`; for us it is just another partition value. |
| `TenantContext::check_permission` (`tenant/context.rs`), `Operation` (`tenant/permissions.rs`) | Call `tenant.check_permission(Operation::…, resource_type)?` at the start of every write, as PostgreSQL and MongoDB do in create, update, delete and revive. `create_or_update` checks per turn, after its pre-read, `Create` or `Update` for the branch the read picks (ADR-aacruzgon-0063) |
| `StoredResource` (`types/stored_resource.rs`) | Build rows with `StoredResource::from_storage(…)`. Versions are numeric strings ("1", "2", …) at this boundary and the ETag is always `W/"<version_id>"`. A deleted version has `deleted_at` set. We store `version_id` as a CQL `int` so that versions sort numerically. |
| `ResourceError` (`error.rs`) | `NotFound` maps to 404, `Gone` to 410 (`read` must return it for a deleted resource), and `AlreadyExists` to 409 |
| `ConcurrencyError` (`error.rs`) | `VersionConflict` maps to 409 and `OptimisticLockFailure` to 412 |
| `SearchError` (`error.rs`) | `UnsupportedModifier`, `UnsupportedParameterType`, `InvalidCursor`, `QueryParseError` and `InvalidDateValue` map to 400; `ChainedSearchNotSupported`, `ReverseChainNotSupported`, `IncludeNotSupported` and `TextSearchNotAvailable` map to 501 |
| `BackendError` (`error.rs`) | `Unavailable`, `ConnectionFailed` and `PoolExhausted` map to 503, `Timeout` to 504, and `UnsupportedCapability` to 501 |
| `BackendKind::Cassandra`, `BackendCapability` (`core/backend.rs`) | Declare exactly one placement capability, `SharedSchema`, from Step 2, and each other capability in the step that implements it: `Crud` and `OptimisticLocking` at Step 3, `Versioning` at Step 4, `BasicSearch`, `DateSearch` and `CursorPagination` at Steps 6a to 6d. The end state is those seven (ADR-aacruzgon-0037). There is no `TokenSearch` or `UriSearch` variant; `BasicSearch` covers token. The contract test in `tests/backend_capability_contract.rs` enforces one placement, but only for backends with a module there, so we add a Cassandra module with a golden capability list. |
| `SearchQuery`, `SearchParameter`, `SearchValue`, `SearchModifier`, `SearchPrefix` (`types/search_params.rs`) | The parsed query we receive. Multiple values are ORed, and multiple parameters are ANDed. |
| `PageCursor`, `CursorValue`, `PageInfo`, `Page<T>` (`types/pagination.rs`) | Reuse `PageCursor::new`/`encode`/`decode` as they are. A malformed cursor returns `SearchError::InvalidCursor`. Always mint a `next_cursor` when there is a next page: if a backend reports a next page without one, REST falls back to `_offset` links, which we refuse. |
| `SearchParamFullCapability`, `PaginationCapability` (`types/search_capabilities.rs`) | Declare token, date and URI with an empty modifier set, and paging as `Count`, `Cursor`, `MaxPageSize(1000)` and `DefaultPageSize`, as the other backends do. REST clamps `_count` to `HFS_MAX_PAGE_SIZE` (default 1000, `crates/rest/src/config.rs:1331-1332`) before we are called, and we add no limit of our own (C6, ADR-aacruzgon-0027) |
| `FhirVersion` (`crates/fhir/src/lib.rs`) | Stored on every resource and version row as `as_mime_param()`, read back with `from_storage`, defaulted with `default_enabled()`. Never hard-coded to `R4`. See the FHIR versions section. |

### Shared helpers we reuse instead of rewriting

- **Extraction:** `SearchParameterExtractor::extract` (`search/extractor.rs`) returns `ExtractedValue`s whose `IndexValue` (`search/converters.rs`) is `Token { system, code, display, … }`, `Date { value, precision, end }` or `Uri(String)`. PostgreSQL and MongoDB call it on every create and update and replace the old rows.
- **Dates:** `indexed_range(&IndexValue, StorageResolution::Millis)` (`search/date_value.rs`) gives each stored value a half-open `[start, end)`. `FhirDateValue::parse(raw)?.range_predicate(prefix, res)` turns a query into a `RangePredicate`. `validate_date_values(&query)` must run at the start of every search, next to `reject_unsupported_metadata_modifier` as its doc says.
- **Tokens:** follow MongoDB's split on `|` (`build_token_filter` in `backends/mongodb/search_impl.rs`). `IMPLICIT_TOKEN_SYSTEM` (`search/converters.rs`) marks `code`-typed elements. PostgreSQL, SQLite and MongoDB agree: `|code` matches system null, `''` or the marker; `sys|code` matches `sys` or the marker; `sys|` matches `sys` only; bare `code` matches any system. We do the same. The pipe form on ContactPoint and boolean elements, which clients SHALL NOT send, is not refused. It matches by the same rules, as SQLite and PostgreSQL do, since neither has a case for those types (`backends/sqlite/search/parameter_handlers/token.rs:12-19`; `backends/postgres/search/query_builder.rs:2344-2394`; C4, ADR-aacruzgon-0027). **Decision: token matching is case-sensitive.** That is the spec default (case-insensitive matching is a SHOULD only when the code system's case rules are unknown) and it is what PostgreSQL and MongoDB do, so all backends agree.
- **Rejection:** nothing in the REST layer calls `SearchCapabilityProvider::validate_search_query`. MongoDB's `validate_query_support` refuses chains, `_has` and modifiers it cannot serve from inside `search()`; it never refuses a parameter type because MongoDB supports them all. Our `search()` refuses both, and also runs `validate_value_presence` and `reject_unsupported_metadata_modifier` as the other backends do.

## FHIR versions: R4 now, R4B, R5 and R6 without rework

We test against R4 only, but Helios is a multi-version server and the backend must not become the one R4-only component in it. The plumbing already exists, so the rule for us is simply to use it everywhere and hard-code nothing.

**What the code already provides.**

- `FhirVersion` (`crates/fhir/src/lib.rs`) has the variants `R4`, `R4B`, `R5` and `R6`, each behind a cargo feature of the same name. The persistence, rest and hfs crates default to `R4`; the book builds all four with `--features R4,R4B,R5,R6`. Helpers: `as_str()` gives `"R4"`, `as_mime_param()` gives `"4.0"`, `"4.3"`, `"5.0"` or `"6.0"`, `from_storage(&str)` accepts either form, `enabled_versions()` lists what this build has, and `default_enabled()` is the safe default (`FhirVersion::default()` is itself gated on the `R4` feature and does not compile in an R4B-only build).
- The version is decided per request, not per server. `create.rs` calls `storage_version_or(config.default_fhir_version)`, which takes the `fhirVersion` parameter of the request's `Content-Type` and falls back to `HFS_DEFAULT_FHIR_VERSION` (default `R4`). One server can therefore hold resources of several versions in one store, and `create`, `create_many` and `create_or_update` all receive the version as an argument. A resource's version is fixed when it is created: `create_or_update` uses the argument only when it creates, and an update or a revive keeps the stored version (`update` takes none, and `restore_deleted` reads it from the row in SQLite, PostgreSQL and MongoDB; ADR-aacruzgon-0024).
- `StoredResource` carries `fhir_version`, and `from_storage(...)` requires it. PostgreSQL stores it in a `fhir_version` column written with `as_mime_param()` and read back with `from_storage`, falling back to `default_enabled()`; MongoDB stores the same string in a `fhir_version` field with the same fallback (`extract_fhir_version(doc, fallback)`).
- Each backend's config carries the server default as `fhir_version`, set from `server_config.default_fhir_version` in `main.rs`. The backends use it for `ResourceTypeScope::version(...)` (the resource-type name table that `:[type]` qualifiers and error messages are judged against), for the SQL-on-FHIR runner, and in PostgreSQL for one R4-only fast path guarded by `#[cfg(feature = "R4")]`.
- The spec data is already per version: `data/search-parameters-{r4,r4b,r5,r6}.json` and `compartment-definitions-*.json`. `SearchParameterLoader::new(fhir_version)` loads the right bundle, `seed_conformance_resources` seeds it per tenant, and `SearchParameterExtractor::new(registry)` is version-neutral because the registry it wraps was built from that loader.

**What the Cassandra backend does with it.**

- `resources` and `resource_versions` carry a `fhir_version text` column, written with `as_mime_param()` and parsed with `from_storage`, with `default_enabled()` as the fallback, exactly as PostgreSQL and MongoDB do. Tables and keys are shared across versions, as in every other backend; the version is a property of the row, not of the keyspace.
- Index tables do not need the version, with one exception. Search loads the `resources` row for the tag check anyway, builds the `StoredResource` from it, and applies `SearchQuery.fhir_version` (upstream #2254) to its `fhir_version`. `count` and an unfiltered `search_count` load no `resources` rows, so `resources_by_type` also carries `fhir_version`, and they drop rows of other versions while they scan (ADR-aacruzgon-0026). A resource's version never changes, so that column is stable across rewrites.
- No `FhirVersion::R4` literal appears outside tests. Defaults come from `default_enabled()` and `self.config().fhir_version`; version-specific behaviour, if any is ever needed, goes behind `#[cfg(feature = ...)]` the way PostgreSQL does it.
- The search-parameter registry is the one the server hands us through `TenantSearchRegistries`, so R4B, R5 and R6 parameter definitions arrive without backend changes.
- CI runs `cargo check -p helios-persistence --no-default-features --features cassandra,R4B` on the self-hosted runner (roadmap item 0.4, PR #17), next to the default R4 build that `.github/workflows/coverage.yml` compiles. It is the cheapest proof that nothing in the backend assumes R4. **Decision:** functional tests stay on R4 fixtures for this project, and the R4B compile check is the gate: a required status check on `main` since 2026-10-14 (ADR-aacruzgon-0019). Running the shared suites under an R5 build is a follow-up once the R4 backend is accepted.

## Proposed Cassandra data model

We propose ten tables, nine of them led by `tenant_id`; the tenth is the internal outbox, explained below. Each table answers one access pattern, which is how Cassandra wants to be modelled. Leading with `tenant_id` follows #28's "`tenant_id` must be the leading column" rule, carried into partition keys.

**Decision: shared schema.** #28's early matrix suggested a keyspace per tenant for Cassandra. We use one keyspace and one set of tables with the tenant in every partition key, matching every other backend and the `SharedSchema` capability. A keyspace per tenant would multiply tables, prepared statements and repair work per tenant, and Helios's placement model has no counterpart for it. On types, `id` is `text` (bytewise order matches Rust string order; the `uuid` type sorts by version and time and would not), `version_id` is `int`, and `last_updated` is a CQL `timestamp`, which has millisecond precision.

| Table | Partition key | Clustering | Serves |
| --- | --- | --- | --- |
| `resources` | `(tenant_id, resource_type, id)` | — | `read`, `exists`, `_id`, and the compare-and-swap on `version_id` and `deleted_at` for every write. Also holds `fhir_version`; `write_ts`, the timestamp of the current version's index writes; and `index_keys`, the index rows the current version writes, set by every compare-and-swap, so a later write deletes exactly those (ADR-aacruzgon-0027). |
| `resource_versions` | `(tenant_id, resource_type, id)` | `version_id DESC` | `vread`, `list_versions`, and delete markers (a version row with no content). Each row also carries its `fhir_version`; the `write_id` of the compare-and-swap that created it, which decides a superseded unknown outcome (ADR-aacruzgon-0026); and `index_keys`, the index rows that version wrote, from which the sweeper takes the previous version's keys (ADR-aacruzgon-0027). |
| `pending_index_writes` | `(bucket, shard)` | `enqueued_at, tenant_id, resource_type, id` | Intent rows for the index sweeper: written before every compare-and-swap, deleted after the index writes complete, `default_time_to_live` 24 h. `bucket` is the UTC hour, `shard` is `hash(tenant_id, id) mod 16`, and each row carries the request's `write_id` and the `version_id` its compare-and-swap will create. |
| `resources_by_type` | `(tenant_id, resource_type)` | `last_updated DESC, id DESC` | A type search with no filters, `_lastUpdated`, `count`, and cursor paging in the default order. Carries `fhir_version`, so `count` can apply `SearchQuery.fhir_version` (ADR-aacruzgon-0026) |
| `token_code_index` | `(tenant_id, resource_type, param, code)` | `last_updated DESC, id DESC, system` | The bare `code` form (any system) |
| `token_system_code_index` | `(tenant_id, resource_type, param, system, code)` | `last_updated DESC, id DESC` | `system\|code` and `\|code` |
| `token_system_index` | `(tenant_id, resource_type, param, system)` | `last_updated DESC, id DESC, code` | `system\|` |
| `date_index` | `(tenant_id, resource_type, param)` | `start, id, end` | Date-only search for prefixes that bound the range start |
| `date_index_by_end` | `(tenant_id, resource_type, param)` | `end, id, start` | Date-only search for prefixes that bound the range end |
| `uri_index` | `(tenant_id, resource_type, param, uri)` | `last_updated DESC, id DESC` | Exact URI match |

The six index tables are rewritten on every create, update and delete from `SearchParameterExtractor::extract`, less the rows no query reads, which are dropped before the keys are computed: the `_id` token and `_lastUpdated` date rows, display-only tokens (no system, empty code), `token_system_index` rows for the implicit-system marker or for system `''`, and URI rows for an empty string (P5, ADR-aacruzgon-0027). Every index row carries the resource's `version_id` as a regular column. `pending_index_writes` is not an index; it is the outbox that lets a background sweeper finish any write that crashed between the compare-and-swap and the index writes (see failure handling). It is the one table not led by `tenant_id`, deliberately: the sweeper has to find pending work without a tenant list, and this project has no tenant registry to enumerate from. Keying by hour bucket and a 16-way shard gives the sweeper 32 fixed partitions to poll and keeps any one of them small. `enqueued_at` leads the clustering key because almost every intent row is deleted seconds after it is written: the sweeper reads only a time slice past its last poll, so it never scans the tombstones of rows already finished. With `tenant_id` first, as first proposed, it would have to read whole partitions; on a 5.0.9 node, one such read of a partition with 3,000 finished intents scanned 3,000 tombstones and logged the tombstone warning, while the time slice scanned none. Tenant isolation is not weakened, because the table holds keys, a `write_id` and a `version_id`, never resource content, and only the sweeper reads it; every row carries its `tenant_id`, so the rows it finds are applied under that tenant's context.

**Why these keys:**

- **Every token form reads one or two partitions, with no `ALLOW FILTERING`.** Filtering on a regular column needs `ALLOW FILTERING` and reads every non-matching row in the slice. So each form gets its own table, at the cost of writing each token value up to three times (twice for a `code`-typed element, whose implicit-system row in `token_system_index` is not written, P5).
    - "No system" is stored as the sentinel `''`, because primary-key columns cannot be null. An empty string is valid as one component of a composite partition key.
    - `code`-typed elements are stored under `IMPLICIT_TOKEN_SYSTEM`. As a result, `sys|code` reads two partitions (`sys` and the marker) and merges two sorted streams, and `|code` reads `''` and the marker. This is exactly what PostgreSQL and MongoDB match.
- **Clustering keys keep distinct values apart.** `system` is in `token_code_index`'s clustering key, so two codings with the same code and different systems stay two rows. `end` is in `date_index`'s, so two ranges with the same start stay two rows.
- **The default order is `(last_updated DESC, id DESC)`.** That is MongoDB's default keyset. Sorting is ✗, so the only other order is a date-only search's: its date table's own order, `(start, id)` or `(end, id)` ascending, with each resource once, at its first matching row (below, G20). `last_updated` is truncated to milliseconds on write and in the cursor, matching `StorageResolution::Millis`; ties within a millisecond are broken by `id`.
- **The cursor is a plain `PageCursor`.** `sort_values = [last_updated as RFC 3339 with millisecond precision, <reserved bucket slot>]` and `resource_id = id`, encoded with the existing `PageCursor::encode`. The page key is `(last_updated, id, bucket)`; the bucket slot is the second element of `sort_values` (see the partition-growth decision below). A date-only search's cursor adds a third element, `"start"` or `"end"`, naming its date table (below).
- **A single-parameter token or URI search pages natively** with `WHERE … AND (last_updated, id) < (?, ?) LIMIT n`. Multi-column relations compare by value, so on our `DESC, DESC` order this is exactly the rows after the cursor, and it excludes every row of the cursor's own resource. Because `token_code_index` and `token_system_index` add a third clustering column, one resource can have several adjacent rows (two LOINC codes in one system, for example), and the two-partition merge for `sys|code` can yield one id from both streams. We therefore collapse rows on `(last_updated, id)` while streaming and keep reading until we have `_count + 1` distinct resources whose version tag matches the `resources` row. The extra one decides the `next` link. `LIMIT` counts rows, not resources, so it is a batch size, not the page size.
- **Multi-parameter searches stream in the shared order.** `resources_by_type` and every token and URI table share `(last_updated DESC, id DESC)`. One partition drives, starting at the cursor, chosen by a fixed order with no statistics so that the most specific key drives: `_id`; `system|code` and `|code` tokens; identity URIs (a canonical resource's own `url`, listed in `docs/Cassandra/schema/walkthrough.md` 5.8); code-only tokens, `_profile`, `_source` and other URIs, whose values many resources share; `system|` tokens; and `_lastUpdated` only when nothing else can drive. Ties go by query order, and the order is revisited only if the Step 8 benchmarks show it matters (C5, ADR-aacruzgon-0027). The spec leaves the order of results without `_sort` to the server. #28 asks for "a (hopefully lightweight) query planner", warns against post-filtering "millions of rows only to discard most of them", and notes that "Cassandra's data model essentially forces you to pre-plan your queries"; its cost hooks (`QueryCostEstimator`, `estimated_cost`) do not exist in the code, so the rule is fixed. Each candidate is checked against the other token and URI parameters with a clustering point read (`WHERE <partition> AND last_updated = ? AND id = ?`), one per partition the form reads (two for `sys|code` and `|code`) and per comma value, and we stop at `_count + 1` distinct matches. Commas within a parameter are a union of partitions merged in the same order. Nothing is materialized beyond one page.
- **Date predicates combined with any other parameter are residual filters.** We already load the `resources` row for the tag check, so we re-extract its dates and apply `RangePredicate::matches`. Only a date-only search touches the date tables.
- **Date-only searches slice whichever date table has the tighter bound, then check every row with `RangePredicate::matches`.** The slices follow Helios's `range_predicate`: `eq` bounds `start` on both sides; `lt`, `le` and `ap` give an upper bound on `start`; `sa` gives a lower bound on `start`. `gt` and `eb` are slices on `end` in `date_index_by_end`; `ge` is the single slice `end > s` with the full predicate as residual; `ne` is the union of a `start` slice and an `end` slice.
    - **Paging (ADR-aacruzgon-0027).** A date-only page uses the date table's own order, `(start, id)` or `(end, id)` ascending, keyset-paged with the cursor `[<start or end>, <reserved bucket slot>, "start" | "end"]`. A resource with several values is emitted once, at its first matching row.
    - **Several dates.** A search with several date parameters, a repeated date or a date with `_lastUpdated` slices one and checks the rest as residuals: `_lastUpdated` if present, otherwise the first date parameter in query order.
    - **`ne`, and a comma list that slices both tables.** They read `date_index`'s slices first, then `date_index_by_end`'s, each in its own order. A resource is emitted once, at its first matching row in that order, and the cursor's third element names the table being read (G20, ADR-aacruzgon-0027).
    - **Cap.** Every date-only search runs under the candidate cap (see rejection section). A range is allowed on only one clustering prefix per query, which is why the two date tables exist.
- **Index rows carry `version_id`.** Search checks that tag against the `resources` row it loads anyway, so a stale or orphaned index row never surfaces a resource or stale content. The tag check does not remove orphans; that is covered under failure handling.
- **Delete markers live in `resource_versions`.** A deleted resource keeps its `resources` row with `deleted_at` set to the delete's time, so `read` can return `ResourceError::Gone` (410). A later `create_or_update` brings it back by writing `deleted_at = 0`, the value a live row always carries.
- **`resources` writes no tombstone (ADR-aacruzgon-0027, walk-through G39).** `deleted_at` is always written: `0` (1970-01-01) on create and revive, the delete's own time on delete. A revive once cleared it with a literal `null`, a cell tombstone. CodeRabbit's review of PR #33 showed the fault, and we reproduced it on a three-node 5.0.9 cluster. A replica that missed the revive and its hint kept the delete's value. Once the other replicas purged the tombstone, a read that included that replica reconciled to it, and read repair spread it. The revived resource then read as deleted (410), vanished from search, and its next update missed its compare-and-swap (404). With the sentinel, the revive's cell is simply newer, and it wins on every replica whatever the repair schedule. Paxos v2 does not prevent the fault: a commit is hinted like any write (`PaxosCommit.java:219-231`), and a prepare refreshes stale replicas with the latest commit only (`PaxosPrepare.java:852-857`). Every reader that decides "deleted" tests `deleted_at > 0`; the walk-through lists them (section 2). We say "delete marker", not tombstone, because Cassandra tombstones are a different thing that this design has to manage separately.

Replication is set on the keyspace, which uses `NetworkTopologyStrategy`, with replication factor 3 on the three-node cluster and 1 on a single local node. `LOCAL_SERIAL` is linearizable only within one data centre, which matches our deployment; a multi-DC deployment would need `SERIAL`.

**Decision: measure partition growth first, bucket on a trigger.** At 100,000 resources our largest partitions (`resources_by_type`, the two date tables, hot token values such as `status=final`) are about 5 to 15 MB, well under the 2-billion-cell limit and 4.1's 100 MiB large-partition warning (5.0 replaces that setting with a guardrail that is off by default). The real costs are different: each such partition is a hot spot served by one replica set, full-partition reads (`count`, the `end`-side date slices) cost O(rows), and every update leaves a row tombstone per index row. We keep single partitions for this project and add a time bucket to a partition key only when a measured trigger fires: tombstones scanned per read above 1,000 (the warn threshold), or a `count` or date scan above the p95 budget. So that bucketing can be added without breaking clients, the cursor reserves room for the bucket from day one: the keyset is `(last_updated, id, bucket)`, with `sort_values = [last_updated, bucket]` and `id` in `resource_id`. The page walker is written to iterate buckets newest first.

## Consistency, failure handling and rejection

The data model splits a resource across several tables, so the resource row and its index rows need different guarantees. Every write to a `resources` row goes through a lightweight transaction (LWT), including revive. Index tables are never written with an LWT.

- **The REST layer checks `If-Match` itself** for single PUT, PATCH and DELETE. It returns 412 on a mismatch, then calls `ResourceStorage::update(tenant, current, resource)` or `delete_versioned`, and relies on that call as the compare-and-swap.
- **Losing the race is a 409.** A writer that changed the row after the REST layer's read must get `ConcurrencyError::VersionConflict`. A row soft-deleted in that gap must make the swap miss (404). `tests/search/versioned_write_race_suite.rs` states this contract.
- **`create_or_update` absorbs the race.** Every unconditional PUT goes through `create_or_update`: a single PUT without `If-Match`, and every batch PUT without `ifMatch`. A batch PUT with `ifMatch` goes through `update`, a compare-and-swap against the row its gate checked, as a single PUT with `If-Match` does (upstream #2527, carried ahead of upstream as #2530, ADR-aacruzgon-0056). Its trait contract (`crates/persistence/src/core/storage.rs`, "# Concurrency", upstream #2111) makes an unconditional PUT last-writer-wins. Callers racing on one id must all succeed, with distinct versions and a complete history, and a `VersionConflict`, `AlreadyExists` or `NotFound` from a lost race must never reach the caller (ADR-aacruzgon-0024). So `create_or_update` is a loop of attempts:
    - **Each attempt** reads the row and picks create (C1), update (C2) or revive (C4). It takes a fresh `write_id`, computes `last_updated` and `write_ts` from that read, writes its own intent row (step 2, with a new `enqueued_at`), and runs the compare-and-swap.
    - **A definite miss** deletes that attempt's intent row and starts the next attempt at once, with no pause. A miss means another writer has committed, so the next read sees it.
    - **The bound.** At most 3 retries after definite misses, so 4 attempts in all. A fourth definite miss is returned as `VersionConflict` (409), whatever it was; SQLite, PostgreSQL and MongoDB return that miss's own error instead (ADR-aacruzgon-0063). This is the bound they use (`MAX_CAS_RETRIES = 3`), and the one `tests/search/versioned_write_race_suite.rs` relies on: a writer can lose three times and succeed on its fourth attempt.
    - **An unknown outcome** is resolved before any further attempt, as in "When the LWT outcome is unknown" below. It has its own budget of 2 re-runs, separate from the 3 retries.
    - **Why it matters on one node.** Batch entries run concurrently (`bulk_write_concurrency` 8), so two entries on one id race through this loop inside a single request.
- **Why every write.** Without an LWT on every write, two concurrent unconditional PUTs would both write version N+1. The cost is a Paxos round on every write, which our benchmarks will show next to PostgreSQL.

**Consistency levels.** Every statement sets its consistency explicitly; `cdrs-tokio` defaults to `ONE` and leaves serial consistency unset. Reads, plain writes and the commit phase of each LWT use `LOCAL_QUORUM`; the Paxos phase uses `serial_consistency = LOCAL_SERIAL`. A `LOCAL_QUORUM` read after an acknowledged LWT therefore sees it. We run `paxos_variant: v2` (two round trips per write; v1, the default in the 4.1 and 5.0 `cassandra.yaml`, needs four) and say so in every benchmark report.

**Decision: driver.** We use `cdrs-tokio` 10 (locked 10.0.0, upgraded from 8.1.9 on 2026-11-06, ADR-aacruzgon-0044: 9.1.0 fixed a single-node session lost after a restart and the reuse of in-flight stream ids). It is essentially a single-maintainer project, and the two advisories `audit.toml` ignores for it (`derivative` and `fxhash`, both "unmaintained") remain in 10.0.0, but it exposes everything this design needs: per-statement serial consistency, typed write-timeout errors with `write_type`, prepared statements and manual paging. The `scylla` driver (1.9, monthly releases, CI against a three-node Apache Cassandra cluster, protocol v4 only) is the named fallback if a blocking bug appears; because it speaks v4, an unknown CAS outcome would then arrive as `WriteTimeout` with `write_type = CAS` rather than `CAS_WRITE_UNKNOWN`, which the timeout handling below already covers.

**Write path (update shown):**

1. Check `tenant.check_permission(Operation::Update, type)`. Extract the index rows for the new content. Read the old ones from the `resources` row's `index_keys`, one point read at `LOCAL_QUORUM`. The compare-and-swap that made N current wrote them, so they are exactly the rows N writes (ADR-aacruzgon-0027). `update` is the only operation that needs this read: `delete`, `update_with_match` and `create_or_update` already pre-read `resources`, and the read must show version N (walkthrough section 2 says what to do when it does not).
    - **Why stored keys (G22).** The registry changes at runtime, per tenant: a `SearchParameter` write invalidates the tenant's registry (`crates/persistence/src/backends/sqlite/storage.rs:520-529`). Re-extracting N's rows with today's registry would miss rows N wrote, and those orphans would cost point reads, count against the candidate cap, and never be cleaned.
    - **Why on `resources`, not only on row N (CodeRabbit's review of PR #33).** Row N of `resource_versions` is written at step 4, after the compare-and-swap. If N's writer pauses between the two while the registry changes, a writer that found row N missing and re-extracted its keys would miss rows N's writer inserts later, and they would stay as orphans. The compare-and-swap writes `index_keys` atomically with `version_id`, and the next compare-and-swap is conditioned on that `version_id`, so the next writer always deletes what N inserts. The walk-through gives the sequence step by step, checked on a 5.0.9 node.
    - **Cost.** About 300 bytes more in every compare-and-swap's Paxos proposal and in the `resources` row: 289 bytes for the worked example's key set, next to the resource's `data`, which the same compare-and-swap already carries. One extra read for `update`; none for any other operation, the sweeper or repair. The encoding, the sizes and the count per operation are in `docs/Cassandra/schema/walkthrough.md` section 2, "Stored key sets".
    - **Size check (ADR-aacruzgon-0026).** Every `code`, `system` and `uri` value of the new rows is measured in UTF-8 bytes. If any is longer than 2,048 bytes, the write is refused before step 2 with `StorageError::Validation(ValidationError::InvalidResource { message, details })`, one `ValidationDetail` per offending element. REST answers 400 with OperationOutcome issue code `invalid` (`crates/rest/src/error.rs:1048`, `570-571`), and nothing is written.
    - **Why it is needed.** Cassandra refuses a partition key over 65,535 bytes, the whole composite key, and a clustering value over 65,535 bytes ("Key length of 70021 is longer than maximum of 65535", on a 5.0.9 node). Such an index batch would fail only at step 5, after the compare-and-swap had applied. No retry, sweep or repair could then finish the write, and the resource would stay hidden from search.
    - **Why each value is measured, not the whole key.** The values are what the client controls. The other key components are bounded by the server: the tenant id at 64 bytes, the id at 64, the resource type at 34, and the parameter code at 128 by the rule below. So the largest key, `token_system_code_index`'s with a 2,048-byte system and code, is 4,337 bytes. That is far below the limit, small enough for one row to fit a 5 KiB batch, and the same for every tenant.
    - **A custom parameter's code is bounded where it is stored (ADR-aacruzgon-0027, G38).** A client can create a SearchParameter, and its `code` becomes the `param` component of every index key under it. FHIR sets no length limit on it: [`SearchParameter.code`](https://hl7.org/fhir/R4/searchparameter-definitions.html#SearchParameter.code) is a [`code`](https://hl7.org/fhir/R4/datatypes.html#code), whose string base may reach 1 MB, and the shared loader checks only its characters (`crates/fhir/src/search/loader.rs:31-36`). On a 5.0.9 node a 61,328-byte `param` overflows the key limit, and a `param` over about 1 KB already breaks the batch sizing above. So the backend refuses to store a SearchParameter whose `code` is longer than 128 bytes in UTF-8, with the same `ValidationError::InvalidResource` and 400 as the size check. That is a stated server restriction. The longest code in the spec data is 46 bytes (R6), so seeding and every spec parameter pass.
    - **What is not checked.** The old rows are not checked: they were checked when that version was written. Each row's `param` is measured too, as a backstop, for a registry that still holds a longer code stored before the bound.
    - **Payload bound (ADR-aacruzgon-0053).** A write whose serialized resource and key set exceed 8 MiB is refused with 400 before anything is written: the node refuses larger messages, and a CAS over its mutation limit fails only after consensus, as an unknown outcome.
2. For an update, delete or revive, first rewrite the `resource_versions` row for N (described under step 4), then write the intent row. Writing the rewrite before the compare-and-swap means row N exists whenever a compare-and-swap creating N+1 has applied (ADR-aacruzgon-0027, walk-through G40). If the rewrite fails, nothing has changed: it only rewrites row N at an older timestamp. The intent row: `INSERT INTO pending_index_writes (bucket, shard, enqueued_at, tenant_id, resource_type, id, write_id, version_id)` at `LOCAL_QUORUM`, with the `write_id` this attempt will use in its compare-and-swap and the version N+1 it will create. This is a plain write, not an LWT. The request keeps the row's full key, `enqueued_at` included, so a retry of this same write rewrites the same row and step 6 can delete it even if the hour has rolled over. A new compare-and-swap attempt in `create_or_update` writes a new row with its own `enqueued_at` instead, and never rewrites an earlier attempt's row with a different version. If it fails, return the driver error, which Helios maps to 503 (`BackendError::Unavailable`) or 504 (`BackendError::Timeout`) in `crates/rest/src/error.rs`; nothing has changed.
3. Run the compare-and-swap. If it is not applied, this attempt has written only its rewrite of row N, which changes nothing (step 2), and its intent row. Delete the intent row: an answer of "not applied" is decided, so this attempt will not apply. An earlier attempt of the same request whose outcome was unknown may still have applied, so before the miss is mapped it is checked against every such attempt (ADR-aacruzgon-0051, under "When the LWT outcome is unknown" below). Cassandra returns the current values of the condition columns when a CAS is not applied (the whole row for `IF NOT EXISTS`), so the miss is classified without a second read. On a missing row the answer is `[applied]` alone, so "no row" is detected by the condition columns being absent from the answer, not by a null value (ADR-aacruzgon-0050):
    - no row means `NotFound` (404);
    - `deleted_at > 0` means the resource was deleted in the gap, also `NotFound` (404), which `tests/search/versioned_write_race_suite.rs` accepts;
    - an existing row on `IF NOT EXISTS` means `AlreadyExists` (409);
    - any other version means `VersionConflict` (409).

    `update` and `delete_versioned` return that error. A plain `delete` that loses to a live version retries once (see "Delete" below). Inside `create_or_update` every one of them means only "start the next attempt", as described under "`create_or_update` absorbs the race". 410 is only ever returned by `read` and `vread`. The CAS also sets a `write_id`, fresh for every attempt, and the new version's times, computed from that attempt's read:
    - `last_updated(N+1) = max(now_ms, last_updated(N) + 1 ms)`, so `last_updated` strictly increases per resource;
    - `write_ts(N+1) = last_updated(N+1) × 1000`, in microseconds.

    Deriving `write_ts` from `last_updated` matters because `update` receives `current` as a `StoredResource`, which carries `last_updated` but not `write_ts`. Any version's `write_ts` can therefore be recomputed from what is in hand, with no extra read. Timestamps only need to increase per resource, because every index key contains the resource `id`.
    - **Update:** `UPDATE resources SET …, version_id = N+1, write_ts = ?, write_id = ?, index_keys = ? IF version_id = N AND deleted_at = 0`. Every compare-and-swap writes the new version's `index_keys`: the new rows on a create, update or revive, and the empty set on a delete.
    - **Create:** `INSERT … IF NOT EXISTS`, with `deleted_at = 0`. Do not use a CAS whose only conditions are null checks: on a missing row those are true and would create a ghost row.
    - **Delete and `delete_versioned`:** `UPDATE … SET deleted_at = ?, version_id = N+1, last_updated = ?, write_ts = ?, write_id = ? IF version_id = N AND deleted_at = 0`, with `deleted_at` bound to the delete's `last_updated`. A delete is a version like any other, with its own `last_updated` and `write_ts`, so a later revive computes its timestamps from it. Do not use a CQL `DELETE`, which would erase the row and break 410.
    - **A plain `delete` that loses to an update retries once (G25, ADR-aacruzgon-0024).** "Delete whatever is current" still means the same thing after the other writer commits, so this follows MongoDB (#1405).
        - The retry is immediate, because a definite miss means the winner has committed.
        - It starts again from the pre-read: a new intent row, then C3 on the version the new read returns.
        - If the retry misses again, the result is `VersionConflict` (409). If the new read finds the resource deleted, the result is `NotFound`, which REST answers as a no-op 204 (ADR-aacruzgon-0052).
        - `delete_versioned` never retries, because its caller named the version it saw.
    - **Revive:** `create_or_update` drops the `deleted_at` condition but keeps `IF version_id = N`, and sets `deleted_at = 0`.
        - Every write increments `version_id`, so that condition alone pins the delete marker the attempt read. A miss means another writer revived or changed the row first, and the attempt ends like any other miss.
        - Never drop the condition: two revivers would both write N+1 (upstream #2111).
        - A revive keeps the resource's original `fhir_version`, bound from the row the attempt read, never the request's. Every other backend does the same, so a resource's FHIR version is fixed at create (G13).
        - It writes `deleted_at = 0`, not the literal `SET deleted_at = null` that ADR-aacruzgon-0024 allowed, so "never bind null" has no exception and the revive writes no tombstone (ADR-aacruzgon-0027, G39).
        - A revive returns `created = true` (201). The trait says "Restoring a soft-deleted resource counts as created", and R4 and R4B require it: "a `201` Created status code if the resource was created (or brought back to life/re-created)" ([R4 http.html#update](https://hl7.org/fhir/R4/http.html#update), [R4B](https://hl7.org/fhir/R4B/http.html#update)).
4. Write the `resource_versions` row for N+1, `USING TIMESTAMP write_ts(N+1)`, with this attempt's `write_id` and its new index rows as `index_keys`. **The rewrite of row N** runs at step 2, before the intent row and the compare-and-swap, not here: for an update, delete or revive, the row for N is rewritten from the writer's read of `resources` at version N (R1), `USING TIMESTAMP write_ts(N) − 1`.
    - **Why before the compare-and-swap (CodeRabbit's review of PR #33, ADR-aacruzgon-0027).** It used to be written here, after the compare-and-swap. Then N's writer could pause after its compare-and-swap, and N+1's writer could apply its own and crash before this step. The only copy of N's key set was then in the paused writer's memory, because N+1's compare-and-swap had overwritten `resources.index_keys`. The sweeper read the missing row N as an empty set and deleted nothing, and N's late inserts stayed as orphans, a `resources_by_type` row among them. Written before the compare-and-swap, the rewrite leaves row N with its exact `index_keys` before anything can supersede N.
    - **Cost.** One more sequential round trip on `update`, `update_with_match`, `delete`, `delete_versioned` and a `create_or_update` turn on a live row or a delete marker: the rewrite no longer shares a single-partition batch with the N+1 row. A compare-and-swap that misses wastes its rewrite, which changes nothing. Every rewrite is built from a read of `resources`, `update`'s own R1 included, so it carries that read's `write_id` (ADR-aacruzgon-0026, 0061). The rewrite carries the `index_keys` step 1 read from `resources` at version N, so every version row has them, and they are exact (ADR-aacruzgon-0027). The rewrite is one microsecond older than the original, so if the row already exists the original wins every cell and nothing changes, even if the content re-serialises differently. If the row does not exist, because the request that created N crashed or paused between its CAS and its step 4, the rewrite restores it. If N is a delete marker, the rewrite sets `deleted_at` and leaves `data` unset (a content row leaves it unset; the live sentinel 0 is only for `resources`), although `resources.data` still holds the old content. Without this, the next update would overwrite N's content in `resources`, and N would be lost from history for good (`vread` of N would return 404). Resource content never goes into a multi-partition batch.
5. Write the index changes, all `USING TIMESTAMP write_ts(N+1)`: delete the index and `resources_by_type` rows whose keys are no longer produced, and upsert the rows that are. A key present in both the old and new sets is upserted only. Because `last_updated` is part of most clustering keys, almost every key changes on every update, so this is one delete and one insert per index row. We group them into logged batches kept under `batch_size_warn_threshold` (5 KiB; the fail threshold is 50 KiB and applies to any multi-partition batch) and send the batches concurrently. The backend sizes each batch itself, from every byte of its statements. The node's own check counts clustering and cell bytes but not partition-key bytes, which are most of an index row: on a 5.0.9 node, a 30-partition `uri_index` batch carrying about 120 KB of partition keys was accepted with no warning. So the thresholds are no safety net for index batches.
6. Once every batch is acknowledged, delete the intent row and return success. On a batch failure, retry with the same timestamps. A `WriteTimeout` of type `BATCH` needs no retry, because the batchlog guarantees replay; `BATCH_LOG` means the batchlog write itself failed, so retry. If the intent-row delete fails, return success anyway: the sweeper will replay the same writes, which changes nothing, and delete it. If the version row or an index write still fails after its retries (3 tries, ADR-aacruzgon-0034), return success too, and leave the intent row for the sweeper (G23). That holds for every operation, not only `create`: after an applied compare-and-swap, a 5xx would turn a client's retried PUT into an extra version, and a retried If-Match PUT into a 412 (ADR-aacruzgon-0050).

**Why the fixed timestamp matters.** Two concurrent updates N+1 and N+2 are ordered by the LWT, but their index writes race. Without a fixed timestamp, each batch would get the coordinator's clock and last-write-wins would let a late N+1 batch resurrect rows N+2 deleted, or overwrite tag N+2 with N+1 in a table whose key did not change. With `write_ts` strictly increasing per version, a delete at `write_ts(N+2)` beats an insert at `write_ts(N+1)` whatever order they arrive in, and a retry is genuinely idempotent. Separately, do not bind `null` for absent columns; leave them unset, or every write adds cell tombstones.

**When the LWT outcome is unknown.** Every error that does not prove the compare-and-swap was not executed leaves its outcome open (ADR-aacruzgon-0024, amended 2026-11-05; ADR-aacruzgon-0034). The same rule holds for every compare-and-swap, C1 to C4, because they share one engine (ADR-aacruzgon-0050). The errors are:
- a `WriteTimeout` with `write_type = CAS`, or with `write_type = SIMPLE` (ADR-aacruzgon-0035), and a `ReadTimeout`;
- a `WriteFailure` with `write_type = CAS`, and a `ReadFailure`;
- `CAS_WRITE_UNKNOWN` (below);
- `Server` and `Overloaded`, which can be raised after the proposal was accepted, and every other server error not listed below as mapped directly, including a code the driver cannot name and any a later driver adds (ADR-aacruzgon-0034);
- an answer with no readable `[applied]` column;
- a client-side timeout or a dropped connection after the CAS was sent. This is treated exactly like a server `WriteTimeout`/CAS. In cdrs-tokio 10, as in 8.1.9, it is:
    - `Error::General("Connection closed when writing data!")`, `Error::General("Connection closed while waiting for response!")`, `Error::General("Write channel failure!")` or `Error::General("Unmatched stream id: …")`;
    - `Error::Io`;
    - the backend's own request deadline elapsing around the CAS, once the CAS was handed to the driver;
    - any other driver error, such as a frame that cannot be decoded, and any error variant a later driver adds.

  Only the errors that prove nothing was sent, or that the coordinator refused the CAS before acting, are mapped directly (ADR-aacruzgon-0034):
    - `Error::Timeout`, which the driver raises only while connecting, and `Error::InvalidProtocol`, raised while opening a node's pool;
    - the deadline elapsing before the CAS was sent (while preparing);
    - "No nodes available in query plan!" and "No active connections to: …", which the driver raises before writing;
    - the server codes `Unavailable`, `IsBootstrapping`, `Syntax`, `Invalid`, `Unauthorized`, `Config`, `Authentication`, `Protocol` and `Unprepared`.

  The backend does not retry a CAS that was refused this way. After `Unavailable` the coordinator refused before acting, so the request answers 503 at once (ADR-aacruzgon-0050).

Every CAS statement is sent as non-idempotent. The driver's default retry session re-sends an idempotent statement to the next node after `Io`, `General`, `Overloaded`, `Server` or `Truncate`, and speculative execution runs only for idempotent statements. A CAS re-sent that way, after it may have applied, is the duplicate this rule exists to prevent. Non-idempotence alone does not stop every re-send: the default retry policy also re-sends any statement after `Unavailable` and `IsBootstrapping`, idempotent or not, so every CAS also carries `FallthroughRetryPolicy`, which never retries (ADR-aacruzgon-0032).

`WriteFailure` is real on 5.0.9: with `paxos_variant: v2`, `Paxos.java` throws it when replicas answer with failures, including in the commit phase after the proposal has reached consensus (`markAndThrowAsTimeoutOrFailure`, called at lines 794-799). Returning an error there without resolving it would let a client's retry write a second version.

What cdrs-tokio 10 surfaces for each (it re-exports `cassandra-protocol` 5.0.0's error types): `error::Error::Server { body, .. }` with `body.ty` either `frame::message_error::ErrorType::WriteTimeout(WriteTimeoutError { write_type: WriteType::Cas, contentions, .. })` or `ErrorType::WriteFailure(WriteFailureError { write_type: WriteType::Cas, failure_info, .. })`.

Protocol v5's `CAS_WRITE_UNKNOWN` (0x1700) is sent only by the legacy Paxos v1 path (`StorageProxy.java:771` on 5.0.9), so with v2 it does not occur. `cdrs-tokio` 10 decodes it as `ErrorType::CasWriteUnknown`, and the backend treats it as unknown (ADR-aacruzgon-0044; `cassandra-protocol` 3.3.0, under 8.1.9, had no variant for it).

On every compare-and-swap (`create`, `create_or_update`, `update`, `delete` and `delete_versioned`) we read the row back at `LOCAL_SERIAL`, which completes or permanently cancels the in-flight proposal, and compare `version_id` and `write_id` with what this request's attempts wrote: every attempt's `write_id` is kept for the whole request, because an earlier attempt can still apply after the serial read found no row (ADR-aacruzgon-0034). Contention alone can end a CAS this way with nothing committed, so this is expected under concurrent writes, not only during failures. For an attempt that targeted version V (version 1 for a create):
- **Our `write_id` at version V:** the write succeeded, and we continue at step 4. A create returns 201.
- **Version still N, or no row for a create:** ours had not applied when the serial read ran, and no other writer has changed the row. That does not mean it never will: after a dropped connection or the client deadline its coordinator may still be running it, and it can apply after the serial read (ADR-aacruzgon-0034). So the request keeps its `write_id`, the same write runs again as a new attempt after a random pause of 5 to 25 ms, and what that attempt sees is first checked against this one (ADR-aacruzgon-0051, below). A create runs again with the same `id`, so its retry can never make a second resource. Its intent row is left for the sweeper. These re-runs have their own budget of 2, separate from the 3 retries for definite misses, because they are not caused by another writer's commit and must not use up those 3. When the 2 re-runs are used up, the last error is returned, mapped as below.
- **Another `write_id` at version V:** another writer won V, and ours did not apply. This is a definite miss and is handled as in step 3:
    - `create` returns `AlreadyExists`, which REST answers with 409 (`crates/rest/src/error.rs`, `From<ResourceError>`);
    - `update` and `delete_versioned` return 409;
    - `create_or_update` and a plain `delete` retry as described above.
- **A version past V:** ours may have applied and been superseded. We read `resource_versions` row V, which carries the `write_id` of the attempt that created it (ADR-aacruzgon-0026, refining ADR-aacruzgon-0024):
    - **Our `write_id`:** ours applied and was then superseded. We return success with version V, as for an applied write. We write no index rows, because a late insert of V's keys could outlive the later version's tombstones. The intent row is left to the sweeper, whose superseded case deletes V−1's keys.
    - **Another `write_id`:** another writer won V. This is a definite miss, handled as in step 3.
    - **No row V, or no `write_id` on it:** nothing this request holds tells the two apart. Retrying could write our body as a second version, so we do not retry; we return an error and leave the intent row to the sweeper.
      - Row V carries a `write_id` whenever V's own step 4 ran, the sweeper replayed V, or the next writer rewrote it, since every rewrite is built from a read of `resources` (`update` included since Step 3, ADR-aacruzgon-0061). Row V always exists once a later compare-and-swap applied, since that writer rewrote it first (G40).
      - So it stays undecidable only when row V's `write_id` cannot be decoded; with the code as built that is unreachable in practice.
- **The serial read times out, or fails:** we return an error rather than retrying and reporting a false 409 against our own success. The intent row is kept. The serial read's own error, and that of the version-row read after it, never goes through the compare-and-swap classification, so it is never taken for a new unknown write (ADR-aacruzgon-0050). A timeout is 504; every other error is 503, even one the table for plain statements would make 500, because the write may have applied (ADR-aacruzgon-0055). On Paxos v2 the serial read can itself fail with a `WriteTimeout` of `write_type = CAS` (`Paxos.java:893-901`); that is the serial read timing out, 504.

**A later attempt first checks the earlier ones (ADR-aacruzgon-0051).** Once an attempt's outcome was unknown, every later look at the row in the same request is matched against every earlier attempt before it is acted on. There are two such looks:
- the next attempt's pre-read of `resources` (R1), which returns `version_id` and `write_id`;
- a definite miss of the next attempt's compare-and-swap. C2, C3 and C4 return only `version_id` and `deleted_at`, so the miss is followed by the serial read, which returns `write_id` too. C1 needs no read: `IF NOT EXISTS` returns the whole row, `write_id` included.

The row is then decided as above, for each earlier attempt k with an unknown outcome, against the version V_k that attempt targeted:
- at V_k with attempt k's `write_id`: attempt k applied, and the request returns its success with attempt k's values;
- past V_k: row V_k of `resource_versions` decides, as under "A version past V", undecidable included;
- otherwise attempt k did not apply, and the look is acted on as usual: the miss is mapped, or the attempt goes ahead.

Without this check, an attempt that applied late would make the request report a lost race against itself. `create_or_update` would take another turn and write the body a second time, `update` and `delete_versioned` would answer 409, and a plain `delete` would answer `NotFound` or 409 after deleting. The check runs only after an unknown outcome, which is already the slow path, and it changes no statement.

**Which error, and why.** The status follows the mapping Helios already gives (`crates/rest/src/error.rs`, `From<BackendError>`): `BackendError::Timeout` is 504, and `Unavailable`, `ConnectionFailed` and `PoolExhausted` are 503 (G26). So an outcome left open by a timeout is a timeout, and one left open by replica failures is unavailability:
- after a `WriteTimeout`/CAS, a client-side timeout or a dropped connection, the undecidable case is `BackendError::Timeout` (504);
- after a `WriteFailure`/CAS, it is `BackendError::Unavailable` (503), because `Write_failure` is "a non-timeout exception during a write request": replicas answered with failures, which is the 503 family ("this instance cannot serve right now");
- a serial read that times out is 504, and one that fails (`ReadFailure`, `Unavailable`) is 503;
- when the 2 re-runs are used up, the last attempt's error decides the same way: 504 after a `WriteTimeout`, 503 after a `WriteFailure`.

A `WriteTimeout` with `write_type = SIMPLE` is treated as an unknown outcome and confirmed by the serial read, like `WriteTimeout`/CAS. It usually means the CAS was decided and only its commit timed out, but that commit can be another coordinator's proposal that our prepare had to finish first, so only the read tells whose `write_id` was applied (ADR-aacruzgon-0035).

**The failure window.** In Cassandra 4.x and 5.0 an LWT is limited to one partition, and a logged batch is atomic (eventually all or nothing) but isolated only within a single partition. Multi-partition ACID transactions (Accord, CEP-15) are targeted at 6.0, which is not generally available, and we do not depend on them. So step 3 and steps 4 to 6 cannot be one operation, and nothing in Cassandra replays steps 4 to 6 if the Helios process dies between them.

- **During every update, briefly.** Between the CAS and the index writes, the resource is hidden from search: its old index rows fail the tag check and its new rows are not yet written. PostgreSQL would return one version or the other. We state this as intended behaviour.
- **What a crash between them leaves.** The resource row is correct and `read` and `vread` are right, but its index rows carry tag N, so the tag check hides the resource from search. Search never returns wrong content. The N rows are never cleaned by a later update either, because the update to N+2 deletes the keys computed from N+1, which were never written.
- **Decision: an intent row and a sweeper close the window.** This is the dual-write problem, and the documented Cassandra pattern for it is the transactional outbox: record the intent in a table Cassandra can write cheaply, do the work, and let a poller finish anything left behind. Step 2 writes that intent row before the compare-and-swap, step 6 deletes it afterwards, and a background task in the backend polls `pending_index_writes` every few seconds (configurable).
    - **What it reads.** For each `(bucket, shard)` of the current and previous hour, the sweeper keeps a low-water mark in memory and reads only rows with `enqueued_at` after the mark and older than a short grace period (30 s by default, so in-flight requests are left alone). An intent's bucket is always the hour of its own `enqueued_at`, so a row is in the bucket its time says. After each successful poll the mark moves to the slice's upper bound, `now − grace`, whether or not any rows came back; otherwise, when every intent has already been finished, the mark would never move and every poll would re-read the hour's tombstones. An intent whose processing fails goes to an in-memory retry list instead of holding the mark back, so one failing intent does not make every later poll re-read the tombstones behind it. When the sweeper starts, it first scans the 25 most recent buckets (a 24 h TTL can span 25 hour buckets), one short time slice per query, so no intent is missed after an outage of any length up to the TTL.
    - **What it does with an intent for version V.** It reads the `resources` row at `LOCAL_SERIAL`, which also settles any in-flight Paxos proposal.
        - If there is no row, or the row's version is below V, the compare-and-swap never applied, and the intent row is simply deleted.
        - If V is the current version, V's keys are the `index_keys` of the `resources` row it just read. It replays step 4 for V's own row, at `write_ts(V)`, with V's content, `write_id` and `index_keys` from that row; this writes the same cells V's writer did, so an existing row is unchanged. If `deleted_at > 0`, V is a delete marker: its row gets `deleted_at` and no `data`, and its key set is empty. Then it replays step 5 at `write_ts(V)`. The sweeper never does step 4's rewrite of V−1. The previous keys are V−1's `index_keys` (ADR-aacruzgon-0027). They are empty for version 1 and for a delete marker. Row V−1 always exists for V > 1, because V's writer rewrote it at step 2, before its compare-and-swap (G40). A missing row V−1 used to be read as "its writer never reached step 5", but a paused writer could still get there.
        - If V has been superseded, the sweeper only deletes V−1's keys at `write_ts(V)`. It writes no inserts: V's keys were already deleted by a later version, and once those tombstones are purged (after `gc_grace_seconds`, 3 h on the index tables, ADR-aacruzgon-0009) a late insert would bring them back.
        - It then deletes the intent row.
    - **Why replaying is safe, whichever request created V.** Every write in the replay carries `write_ts(V)`, and a later version's writes carry a higher timestamp, so they win whatever order they arrive in. A delete at an older timestamp never removes a newer row, even after that row's own tombstones are purged. The deletes of V−1's keys are what remove the orphans a crash would otherwise leave behind once a later update supersedes it.
    - **V's version row is never missing once V is superseded,** since the next writer rewrote it before its compare-and-swap (G40). The earlier rule for that case (two crashes in a row: delete V−1's keys at `write_ts(V−1) + 1`) is gone.
    - **Clocks.** The grace period is the one clock comparison, and it is also what keeps the low-water mark safe. It assumes that clock skew between Helios processes, plus the time from a request's intent row to its compare-and-swap, stays under the grace period. A request that stalls longer can have its intent swept before its compare-and-swap applies. If it then also crashes before its index writes, only repair on read can heal what it left, and only for an update or delete: a create in that state, or one whose intent expired during a sweeper outage longer than the 24 h TTL, has no index rows for repair to find, and stays unsearchable (though readable by id) until it is next written. The same holds for a revive of a deleted resource. We state these as known limitations, together with one more:
        - **A request paused for longer than `gc_grace_seconds` between its compare-and-swap and its index writes** can bring back index rows a later version deleted. The tag check hides them from search, but `count` includes them until a search repairs them.
    - **One sweeper per process (G12, ADR-aacruzgon-0027).** This project runs one Helios process. Several processes would run several sweepers, each re-reading and replaying the same intents; their writes carry the same fixed timestamps, so the only cost is duplicate reads. We accept that and take no lease row, which would add an LWT per poll and stall every intent while a crashed holder's lease ran out.
    - **Bounds.** Every step is idempotent because the timestamps are fixed, so a sweeper and a slow request can both run the same writes without harm. The intent rows have a 24-hour TTL, so a sweeper outage cannot grow the table without bound; the tag check still guarantees that nothing wrong is ever returned in the meantime.
- **Repair on read stays as the second line of defence.** When search finds an index row whose tag disagrees with the `resources` row, it re-runs the index maintenance for the current version inline, at that version's `write_ts`, with the current version's `index_keys` from the `resources` row the tag check just read, so it reads nothing more. It deletes the stale key only if the current version does not produce it; a key the current version does produce is upserted with the current tag instead. Otherwise a delete could collide with the writer's own insert at the same timestamp, which a delete wins, and remove a key the current version needs. This heals orphans the sweeper could not know about, such as rows left by a crash older than the TTL. It is a write made from a read request, and is logged as such.
- **A new SearchParameter does not reindex (known limitation, ADR-aacruzgon-0027).** Index rows are written only when a resource is written. A resource written before a `SearchParameter` was added is found by it only after its next write; there is no reindex in this project. Removing a parameter leaves no orphans, because deletes use each version's stored `index_keys`.
- **Alternatives we considered.** Cassandra 5.0's Storage-Attached Indexes remove the dual write entirely ("when a write is acknowledged to the client, the data is already indexed"), but a query without a partition key scans the token ring, there is no `ORDER BY` on non-vector columns so keyset paging by `last_updated` is lost, and the default cap is 10 indexes per table against hundreds of FHIR search parameters. Materialized views have been experimental and disabled by default since 3.0.15 and have no reconciliation mechanism. Change data capture would move index maintenance out of process, which is the right shape for a later Elasticsearch composite but not for the primary store's own search tables. Accord (CEP-15) would make the whole write one transaction, but it is not generally available.
- **How we test it.** The controlled failure tests kill the Helios process at these points:
    - **Killed between the intent row and the compare-and-swap:** the sweeper must delete the intent and change nothing else.
    - **Killed between the compare-and-swap and the index writes:** `read` must be correct immediately. `vread` of the new version is 404 until the sweeper runs (or the next write rewrites the version row), and correct after it. Search must hide the resource until the sweeper runs, and then return it. `count` is checked before and after.
    - **Paused, then a crashed successor (G40):** N's writer is paused after its compare-and-swap; N+1's compare-and-swap applies and its writer is killed before step 4; the sweeper runs both intents; N's writer resumes. No index or `resources_by_type` row of N may remain, and `count` must be correct.
    - **Crashed, then superseded:** the resource is updated again before the sweeper runs. `vread` must still return the crashed version, and after the sweep no index row of the version before it may remain.
    - **Sweeper restarted after an outage:** intents older than two hours are still processed.

**Tombstones.** Because `last_updated` is in the clustering keys, every update leaves one row tombstone per old index row, and the `resources_by_type` row moves to the head of its partition leaving a tombstone behind. `count` and the date scans read through them; a mass update of one type is a named benchmark case for that (roadmap Step 8, G8). The defaults are `tombstone_warn_threshold: 1000` and `tombstone_failure_threshold: 100000` per query. Tombstones stay until `gc_grace_seconds` (10 days by default) passes and, with replication factor 3, repair has run on every node. A node offline longer than a table's `gc_grace_seconds` must not rejoin at all, since repair would spread its deleted rows back ("its deleted data will be repaired back to the other nodes and reappear in the cluster", [tombstones](https://cassandra.apache.org/doc/5.0/cassandra/managing/operating/compaction/tombstones.html#deletion)); for the index tables and `resources_by_type` that is 3 h. **Operations rules (ADR-aacruzgon-0027):** on the cluster, a replica back from an outage shorter than `max_hint_window` (3 h), or after a spike of `Unavailable` errors, timeouts or dropped mutations, is repaired promptly, within 3 h of the outage's start; a replica down longer than `max_hint_window` is replaced (`replace_address_first_boot`), never rejoined, even after repair; and the replacement node is repaired once it has bootstrapped, since Cassandra's replace procedure says "you **MUST** run repair to make the replaced node consistent again" when "The node is down for longer than `max_hint_window` before being replaced" ([replacing a dead node](https://cassandra.apache.org/doc/5.0/cassandra/managing/operating/topo_changes.html#replacing-a-dead-node)). These rules narrow resurrection; they do not rule it out. Hints are best effort ("Hints are best effort, however, and do not guarantee eventual consistency like anti-entropy repair does", [hints](https://cassandra.apache.org/doc/5.0/cassandra/managing/operating/hints.html)), and a hint expires at the smallest `gc_grace_seconds` of its tables (`Hint.java:131-158` in `cassandra-5.0.9`), 3 h here. So a delete a replica missed in a short outage, a dropped mutation or a lost hint can come back once the tombstone is purged before repair reaches that replica. The exposure is `count` on the three-node cluster, one too many per resurrected `resources_by_type` row until a search repairs it; search itself stays correct, because the tag check hides the row, and RF 1 is not exposed. Search can fail, though not return a wrong result: each resurrected or orphan row a search point-reads and hides counts against the candidate cap, so enough of them ahead of the live matches in one partition make that page return 422 `TooManyResults`. That needs many missed deletes in one partition, all purged before repair, and repair on read deletes each such row before the cap is checked, so a retry gets further. We accept that rather than set `only_purge_repaired_tombstones` (tombstones never purged without regular repair) or raise `gc_grace_seconds` (the G8 tombstone cost for days); walk-through G7 gives the reasons. With these rules `gc_grace_seconds` stays at 3 h on `resources_by_type` too. The tag check makes a resurrected index row harmless to search, so `gc_grace_seconds` is lowered to 3 h, the node's hint window, on the six index tables, `resources_by_type` and `pending_index_writes`; `resources` and `resource_versions` keep 10 days (ADR-aacruzgon-0009). Neither holds a tombstone since the revive writes `deleted_at = 0` (G39), so their grace period no longer affects correctness; repair within it stays routine practice on the cluster ("At a minimum, repair should be run often enough that the gc grace period never expires on unrepaired data", [repair](https://cassandra.apache.org/doc/5.0/cassandra/managing/operating/repair.html)). We reset data between benchmark runs and record tombstones scanned per read.

**Search visibility.** Step 6 returns only after the index writes are acknowledged, so a write whose index batches were acknowledged is searchable on return, and `read` and `vread` at `LOCAL_QUORUM` see it immediately. When step 6's retries run out after the compare-and-swap applied, the write returns success and the sweeper finishes it. Such a write is searchable within one poll interval plus the grace period, not on return (G23, ADR-aacruzgon-0027). A 5xx there would make a client's retried POST create a second resource. These guarantees cover a crash of Helios; a crash of the Cassandra node at replication factor 1 loses up to about 10 s of acknowledged writes, lightweight transactions included (`spike-findings.md`, B4 and C; ADR-aacruzgon-0005).

A related default also needs justification. The default no-op `ensure_writes_visible` is documented as valid only when the index is written in the same transaction as the resource, which is not true here. Its callers are conditional references and `If-None-Exist`, both out of scope and unreachable once `supports_atomic_transactions` is false. We keep the no-op and document why it still holds.

**Capabilities and rejection.** Rejection is split between REST and the backend, and we need to be clear about which does what:

- The REST layer already validates modifiers against parameter types for every registered parameter (`validate_modifier` in `search/value_parser.rs`, called from `extractors/search_query_builder.rs`), so `:exact` on a token, date or URI parameter is a 400 before `search()` runs. It also handles unknown parameters and `Prefer: handling=strict`.
- The REST layer rewrites chains, `_has` and `_list` into `_id` filters by running per-hop searches first (`resolve_chains_with`). A chain on a Cassandra primary therefore fails at the hop that needs a reference parameter, as 400 `UnsupportedParameterType`, not as 501 from `ChainedSearchNotSupported`; but the resolver runs the terminal search first and stops when it matches nothing, so a chain whose terminal is served and matches nothing answers 200 with an empty searchset (`chain_resolver.rs:583-585`). A `_has` needs no reference search: the resolver runs its terminal search through our `search()` and reads the references from each match in Rust (`crates/persistence/src/search/chain_resolver.rs:693-771`). So a `_has` whose terminal is a token, date or URI parameter is answered, and one whose terminal is another type fails at that hop with 400 `UnsupportedParameterType`, issue `invalid` (C7). That is allowed: R4 says "Servers are not required to implement any of the standard search parameters" and gives no `_has`-specific rule, and REST already ignores unknown or unsupported parameters by default and refuses them under `Prefer: handling=strict`. The cost is ours: the resolver drains every page of the terminal search into memory (`search_all_pages`, `chain_resolver.rs:268`, called at `758`) before reading references, so a broad terminal such as a common Observation code is expensive; roadmap Step 8 measures it. The `_id` filter itself must work, which is why `_id` is in scope. **Under a scope, neither is safe yet** ([HeliosSoftware/hfs#2501](https://github.com/HeliosSoftware/hfs/issues/2501), C7): REST confines only the base query, the resolver runs each hop with no compartment, and only the path's resource type is checked against the scopes. So `Patient?_has:Observation:focus:code=X` under one patient's `patient/` scope can reveal another patient's Observation, and on Cassandra a scoped chain's 400 or 200 reveals whether any resource in the tenant matches its terminal. Four Step 6 rows gate Cassandra search on it; if upstream has not fixed it by then, the fork carries a REST patch that refuses chains and `_has` under a confined grant with 403 and checks each hop's type against the scopes (roadmap Step 6, ADR-aacruzgon-0027).
- Inside `search()` and `search_count()` we run `validate_date_values`, `validate_value_presence` and `reject_unsupported_metadata_modifier` first; refuse `_text` and `_content` by name with `TextSearchNotAvailable` (501), and `_filter` by name with `BackendError::UnsupportedCapability` (501, issue `not-supported`, `crates/rest/src/error.rs:1209-1211`, `656-659`; C11), before the type check, because the R4 registry types both as `string` and the type check would otherwise answer 400; refuse any other parameter type than token, date and URI with `UnsupportedParameterType` (400); refuse any modifier with `UnsupportedModifier` (400), which keeps the backend correct when it is called directly rather than through REST; refuse `_include` and `_revinclude` when `query.includes` is non-empty with `IncludeNotSupported` (501), which works because `search()` runs before include resolution; and refuse `_offset` and any `_sort` other than the search's native order with `QueryParseError` (400): only an absent `_sort`, or `-_lastUpdated` where the native order is `(last_updated DESC, id DESC)`, is accepted (C9). MongoDB uses that error for a cursor on a sort it cannot key; unlike MongoDB we do not honour `_offset` at all.
- **The compartment filter is a residual, never ignored (ADR-aacruzgon-0026).** When `query.compartment` is set, every candidate that passes the tag check is re-extracted with `SearchParameterExtractor::extract`, under its own `fhir_version` and the tenant's registry. It is kept only if one of its reference values for the parameters in `compartment.params` equals `strip_reference_version(compartment.reference)` or starts with it followed by `/_history/`.
    - This is the membership rule SQLite and MongoDB apply to their reference index rows (`backends/sqlite/search/query_builder.rs:863-896`, `backends/mongodb/search_impl.rs:847-862`).
    - The parameters are the bundled CompartmentDefinition's, from `helios_fhir::get_compartment_params` (for R4 Patient and Observation, `subject` and `performer`, the [R4 Patient CompartmentDefinition](https://hl7.org/fhir/R4/compartmentdefinition-patient.html)).
    - The other parameters drive as usual; with none, `resources_by_type` drives.
    - The rows read count against the same candidate cap as a date-only search. Past it, the search or count fails with `SearchError::TooManyResults`, which REST maps to 422 (`crates/rest/src/error.rs:1123-1125`). It never returns a page or a count that was only partly filtered.
    - `search_count` and `_total` under a compartment run the same filter to the end.
- **`SearchQuery.fhir_version` is a residual too.** It is applied to `resources.fhir_version` after the tag check, and by `count` to `resources_by_type.fhir_version`.
- A date-only or otherwise unbounded search whose candidate set exceeds a configured limit is refused instead of timing out. The refusal is `SearchError::TooManyResults`, which REST maps to 422 with issue `processing` (`crates/rest/src/error.rs:1123-1125`, `591-595`). No search produces `too-costly`; its one producer is the batch handler's 500 for a transaction too large for MongoDB's cache (`crates/rest/src/handlers/batch.rs:3818`). The limit counts distinct candidates point-read, per page or per `search_count`, and the compartment filter follows the same rule (G27, ADR-aacruzgon-0027).
- `SearchCapabilityProvider` and `BackendCapability` describe the same surface, and the README matrix will be updated to match. The CapabilityStatement handler (`crates/rest/src/handlers/capabilities.rs`) does not read either: it lists every registered search parameter of every type and hard-codes `vread`, the three history interactions, `versioning: versioned` and `readHistory: true`. A Cassandra deployment would therefore over-advertise, and a client that trusts the statement would discover string or reference search and history as 400s and 501s at run time. **Decision: we patch the handler as part of this project.** The patch follows the pattern the handler already uses for `supports_conditional`, `supports_contained_search` and `modifiers_for_param_type`: defaulted hooks on traits already in the server bound, so no existing backend changes.
    - `SearchProvider::supported_param_types()` returns every `SearchParamType` by default; Cassandra returns token, date and URI. `build_search_params` drops parameters of other types, and `build_resource_capability` drops `_include`/`_revinclude` entries when the backend returns `None` from the include hooks.
    - `InstanceHistoryProvider::supports_history()` returns `true` by default; Cassandra returns `false`. The handler then omits `history-instance`, `history-type` and `history-system`, while keeping `vread`, `versioning: versioned` and `readHistory: true`, which we do support. `build_capability_statement` adds `InstanceHistoryProvider` to its own bound, which costs nothing because `create_app` already requires it.
        - **Why `readHistory` stays `true`** (ADR-aacruzgon-0025). It is not the history interactions. R4, R4B and R5 all define it as "A flag for whether the server is able to return past versions as part of the vRead operation" ([R4 `readHistory`](https://hl7.org/fhir/R4/capabilitystatement-definitions.html#CapabilityStatement.rest.resource.readHistory)).
        - Cassandra's `vread` returns any past version from `resource_versions`; a delete marker answers 410.
        - The history interactions are advertised separately, as `history-instance`, `history-type` and `history-system`, and those are what we omit.
    - We do not put `SearchCapabilityProvider` in the server bound: S3 does not implement it, so that route would break an existing backend. The two hooks delegate to the same `SearchCapabilityProvider` data inside the Cassandra backend, so there is one source of truth.
    - Tests: the existing `crates/rest/tests/capabilities_search_params.rs` and `rest_conformance.rs` gain a stub backend that overrides both hooks and asserts the statement omits what the backend refuses; the default-path tests stay green for the other backends.
    - The patch goes upstream as its own pull request, separate from the backend, because it fixes the same over-reporting for any backend that refuses what the handler hard-codes.

**Open questions.** ADR-aacruzgon-0027 decided every question the Step 1 sessions and the schema audit left:
- `count` (G7), including `count(tenant, None)` and how far it may differ from a filtered `search_count`;
- the mass-update benchmark case (G8) and several sweepers (G12);
- the rows nobody reads (P5, G18);
- `_lastUpdated` beside the cursor (G19, the rule above);
- date-only paging, `ne` and comma lists included (G20);
- old keys after a registry change (G22, stored `index_keys`);
- the write that applied but could not be indexed (G23);
- the cap's error (G27);
- a custom SearchParameter's `code`, bounded at 128 bytes (G38, raised in review of PR #33);
- `resources.deleted_at` without a tombstone (G39) and the rewrite of row N before the compare-and-swap (G40), raised in review of PR #33;
- the intent row's `write_id` (G32, kept as a diagnostic);
- `_id` with a pipe (C2), the AND driver order (C5), `MaxPageSize` (C6), the composite 400 and `_has` through the shared resolver (C7), and `_filter` (C11).

Batch `ifMatch` (G28), the upstream window ADR-aacruzgon-0024 recorded, is closed by the backport of upstream #2530 (ADR-aacruzgon-0056). Nothing else is open.

## What else the server expects from a primary backend

Beyond the matrix and the traits, the server expects several further things from a primary backend. The items below are not in the matrix; they surfaced while reading `crates/hfs/src/main.rs` and the other `start_*` functions.

- **Backend selection.** `HFS_STORAGE_BACKEND` is parsed into `StorageBackendMode` in `crates/rest/src/config.rs`, which needs a Cassandra variant with `Display`, `FromStr` and `primary_backend_kind`. `main.rs` dispatches to feature-gated `start_*` functions with `#[cfg(not(feature))]` fallbacks, and an exhaustive match for `patient_name_search_support` needs a Cassandra arm (`IdOnly`, like S3). The `cassandra` cargo feature exists only in the persistence crate today; `crates/rest/Cargo.toml` and `crates/hfs/Cargo.toml` must thread it through as they do for `mongodb`.
- **Conformance seeding at startup.** `seed_conformance_resources` writes about 1,400 SearchParameter and CompartmentDefinition resources per provisioned tenant through `create_many`. With an LWT on every write that is about 1,400 Paxos rounds per tenant at boot, fanned out at `bulk_write_concurrency`. Measured at Step 2: 1.3 to 4.5 s of seeding per fresh tenant on the single node, under the provisional budget of 10 s, so `create_many` keeps its default (ADR-aacruzgon-0043).
- **Search parameter registry.** Backends own a `TenantSearchRegistries` (`search/tenant_registries.rs`) and refresh stored SearchParameters periodically, as `spawn_mongodb_search_param_refresh` does. Cassandra needs the same to implement `search_param_registry`. With no tenant registry, it lists the tenants by a `SELECT DISTINCT tenant_id, resource_type` scan of `resources_by_type`'s partition keys, paged, and reloads every tenant with a SearchParameter partition before it serves; startup fails if that load fails (ADR-aacruzgon-0041). Between reloads, the writing instance keeps its overlay current on every write (ADR-aacruzgon-0062): it holds every stored definition per `url` and picks the one in force when the registry is built; a delete, or an update to a body it does not hold, records a removal `(id, last_updated)` that hides that id's older versions from any reload, and invalidates the tenant's registry. Two limitations are left to Step 5: a registry build that began before an invalidation can be cached after it (PR #50, r4497056726), and a SearchParameter whose `resources_by_type` row failed after its compare-and-swap is missing from the next reload until the sweeper replays it (r4497056824).
- **The `start_cassandra` arm**, modelled on `start_s3`, must decide `SessionPersistence` (or warn that login sessions are in-process), `SettingsStore` (501 if `None`), `BulkProviderStore`, `OperationsBundle` (`PurgableStorage` for `$purge`, `ReindexableStorage` for `$reindex`, or `None` for 501), `WriteObservability`, and export and submit bundles (`None`). Our first version passes `None` for every store and bundle the backend does not implement (all of them except `WriteObservability`), because S3's `Some` arms each need a trait the Cassandra backend lacks (ADR-aacruzgon-0040).
- **Database audit.** `HFS_AUDIT_BACKEND=database` fails at startup for a Cassandra primary, which is consistent with "Cassandra never stores AuditEvents" but should be documented. It fails with an error that names both settings and points at `file` or `cloudwatch` (ADR-aacruzgon-0040).
- **SQL-on-FHIR.** The backend has no `sof_runner`, so `start_cassandra` turns `HFS_SOF_ENABLED` off when it was left at its default, and fails startup when it was set explicitly to true; `$viewdefinition-run` and `$sql-run` answer 501 (ADR-aacruzgon-0040).
- **`_count=0` and `count`.** `_count=0` must behave as `_summary=count` in both spec versions, so it needs a total. Our `count` is a full scan of the `resources_by_type` partition and reads through its tombstones; it is a stated cost and a benchmark case. It does not apply the tag check, so it also counts writes still in flight. On the three-node cluster it can also count a row resurrected after a replica missed a delete (a short outage, a dropped mutation or a lost hint) and the tombstone was purged before repair reached it. `count` is not tag-checked; a filtered `search_count` is, under the candidate cap. The two differ while a write is in flight, while a crashed write waits for the sweeper, and in the stated limitations above (an expired intent, a stalled or paused request), where an orphan row stays counted until a search repairs it. `count(tenant, None)` sums `count` over the resource type names of every enabled FHIR version (`FhirResourceTypeProvider::get_resource_type_names`, as `ResourceTypeScope` uses, `crates/persistence/src/search/type_qualifier.rs:98-118`); the registry's `resource_types()` would include `Resource` and miss `Binary`. The cluster's operations rules (repair a replica back from a shorter outage within 3 h; replace a replica down longer than `max_hint_window`, never rejoin it; repair the replacement once it has bootstrapped) narrow that risk but do not rule it out, and the residual over-count is accepted (Tombstones above, G7, ADR-aacruzgon-0027).
- **Tenant registry.** The admin tenant API returns 501 unless `supports_tenant_registry` is true, and the tenant extractor skips the provisioned-tenant check when a backend has no registry, as it does for Elasticsearch today. **Decision:** no registry in this project. `supports_tenant_registry` stays `false`, tenants are whatever the request's tenant context names, and `register_tenant`, `deregister_tenant` and `purge_tenant_data` keep their default unsupported behaviour. A registry table is a natural follow-up and needs no schema change elsewhere.
- **Conformance testing with Inferno.** The fork inherits a complete Inferno pipeline (`.github/disabled-workflows/inferno-us-core.yml`, `crates/hfs/tests/inferno/install.sh` and fixtures) that runs the ONC US Core server suites v3.1.1 to v8.0.0 against every backend. Upstream treats it as a weekly tracking signal rather than a gate, and it was built for upstream's pool of self-hosted runners (`runs-on: [self-hosted, Linux]`, with a remote Docker host); this fork has a single runner, Sam's desktop, since 2026-10-14 (ADR-sam-michaels-0001). US Core is also the wrong yardstick for a standalone Cassandra primary: its tests search by `patient` reference and by `name`, and add `_revinclude=Provenance:target`, so against our scope almost every group fails or skips by construction, as it does for standalone MongoDB upstream. **Decision:** we write a small Inferno test kit of our own, from `inferno-template`, whose tests are derived line by line from the rejection table above: a capability-truth group that checks `/metadata` advertises exactly what we support, CRUD and versioning, supported search with keyset paging, and a declared-rejection group where each unsupported request must return its documented status with an OperationOutcome. The kit needs no profile validation, so it runs without the validator service. We run it against PostgreSQL once as a check on the kit itself, and we run US Core v3.1.1 once against Cassandra as a documented negative result with every failure mapped to a rejection. A green US Core run needs the Cassandra + Elasticsearch composite and is future work.
- **Composite role.** The README lists a planned "Cassandra + Elasticsearch" composite. **Decision:** standalone primary only in this project. Nothing here blocks the composite later: the composite layer feeds its search backend from the primary's write path, and our index tables are internal to the primary, so a composite would simply route search elsewhere and leave them unused.

## Implementation order

The ordered plan, with milestones, exit criteria, test gates, failure tests, the measure-first triggers, file ownership and an indicative schedule, lives in [`development-roadmap.md`](development-roadmap.md). In one paragraph: the trait hierarchy sets the order, so the whole team designs the schema first, one owner wires the skeleton and stubs to a create/read round trip through REST (milestone A), CRUD and versioning follow, then the index writes and sweeper, then the search framework, after which token, date, URI, cursor paging and the CapabilityStatement hooks proceed in parallel in their own files, and benchmarks, failure tests and the demonstration close it out (milestones B and C). The benchmark harness, Docker files, CI and the PostgreSQL baseline start on day one because they need no Cassandra code.
